# TC-07 Una sola suscripción para guardar y publicar

## Requisitos del proyecto

### Trabajo solicitado

* Eliminar la suscripción manual de `postOrderFromEmail()`.
* Componer conversión, persistencia y publicación dentro de una sola cadena reactiva.
* Definir si la publicación ocurre antes o después del guardado.
* Garantizar que cada petición produzca únicamente un guardado y una publicación.
* Mantener el flujo preparado para una futura implementación con outbox.

### Restricciones técnicas obligatorias

* El controlador no debe reutilizar un `Mono` y suscribirse manualmente.
* La publicación debe participar en la cadena reactiva.
* Si `OrderMessagingService` continúa retornando `void`, su efecto debe encapsularse temporalmente.
* No asumir atomicidad entre MongoDB y el sistema de mensajería.

### Criterios de aceptación

* [x] Una petición produce un guardado y una publicación.
* [x] Un error durante la conversión no persiste ni publica.
* [x] Un error durante el guardado no publica.
* [x] El flujo de creación desde correo no contiene suscripciones manuales.

### Pruebas mínimas

* [x] Verificación de exactamente una conversión, un guardado y una publicación.
* [x] Prueba de error durante conversión y guardado.
* [x] Prueba con publisher frío para comprobar que el trabajo no se duplica.

> **Pregunta para defender la solución**
>
> ¿“Guardar y luego publicar” es atómico? ¿Qué ventana de fallo sigue abierta?
>
> No. En TC-07 se utiliza la política `save-then-send`: primero se confirma el guardado en MongoDB y posteriormente se publica la orden. Esto evita publicar una orden cuyo guardado haya fallado, pero sigue existiendo una ventana en la que MongoDB puede guardar correctamente y la publicación fallar posteriormente. Resolver esa consistencia entre persistencia y mensajería corresponde a una solución como outbox, prevista para TC-29.

## Modificaciones y su cumplimiento de los retos

Para completar TC-07 se modificaron o agregaron los siguientes archivos:

```text
tacocloud-api/src/main/java/tacos/web/api/
├── OrderApiController.java
└── OrderService.java

tacocloud-api/src/test/java/tacos/web/api/
├── OrderApiControllerTest.java
└── OrderServiceTest.java
```

### `OrderService.java`

Se agregó `OrderService` para retirar del controlador la coordinación de conversión, persistencia y publicación.

El método principal implementado es:

```java
public Mono<TacoOrder> createOrderFromEmail(
    Mono<EmailOrder> emailOrder) {

  return emailOrderService
      .convertEmailOrderToDomainOrder(emailOrder)
      .flatMap(repo::save)
      .flatMap(savedOrder ->
          Mono.fromRunnable(() ->
              orderMessages.sendOrder(savedOrder))
              .thenReturn(savedOrder));
}
```

El flujo queda definido de la siguiente forma:

```text
EmailOrder
    ↓
convertEmailOrderToDomainOrder()
    ↓
repo.save()
    ↓
sendOrder()
    ↓
TacoOrder
```

Se eligió la política **guardar primero y publicar después**.

De esta manera, si falla la conversión no se intenta guardar ni publicar. Si falla `repo.save()`, la cadena termina con error antes de alcanzar `sendOrder()`.

Como `OrderMessagingService.sendOrder()` actualmente retorna `void`, el efecto se incorporó temporalmente a la cadena mediante:

```java
Mono.fromRunnable(() ->
    orderMessages.sendOrder(savedOrder))
```

y `thenReturn(savedOrder)` permite continuar emitiendo la orden guardada una vez realizada la publicación.

### `OrderApiController.java`

El método anterior de `postOrderFromEmail()` creaba un `Mono`, realizaba una suscripción manual para publicar y después retornaba otra cadena basada en el mismo publisher.

El endpoint fue simplificado a:

```java
@PostMapping(
    path="fromEmail",
    consumes="application/json")
@ResponseStatus(HttpStatus.CREATED)
public Mono<TacoOrder> postOrderFromEmail(
    @RequestBody Mono<EmailOrder> emailOrder) {

  return orderService
      .createOrderFromEmail(emailOrder);
}
```

El controlador ya no coordina conversión, guardado y publicación y tampoco realiza `subscribe()` manual.

Su responsabilidad queda limitada a recibir la petición HTTP y delegar el caso de uso en `OrderService`.

### `OrderApiControllerTest.java`

El archivo fue actualizado para utilizar `OrderService` como dependencia del controlador:

```java
@Mock
private OrderService orderService;
```

Esto mantiene compatibles las pruebas creadas para TC-04 y TC-05 después del cambio realizado en el constructor de `OrderApiController`.

Las pruebas específicas de TC-07 no fueron agregadas a este archivo, ya que el comportamiento nuevo se encuentra concentrado en `OrderService` y se prueba directamente mediante `OrderServiceTest`.

### `OrderServiceTest.java`

Se implementaron únicamente las tres pruebas mínimas solicitadas para TC-07.

#### Una sola invocación

`shouldSaveAndPublishExactlyOnce()` comprueba que una petición produzca exactamente:

```text
1 conversión
1 guardado
1 publicación
```

utilizando verificaciones de Mockito:

```java
verify(emailOrderService, times(1))
    .convertEmailOrderToDomainOrder(emailOrder);

verify(repo, times(1))
    .save(convertedOrder);

verify(orderMessages, times(1))
    .sendOrder(savedOrder);
```

Esto comprueba que ya no existe la doble ejecución provocada anteriormente por dos suscripciones.

#### Error de conversión y guardado

`shouldNotPublishWhenConversionOrSaveFails()` cubre los dos escenarios solicitados dentro de la misma prueba.

Cuando falla la conversión:

```text
conversión → error
guardado   → no ejecutado
publicación → no ejecutada
```

Cuando falla el guardado:

```text
conversión → correcta
guardado   → error
publicación → no ejecutada
```

Esto demuestra el comportamiento definido por la política `save-then-send`.

#### Publisher frío

`shouldNotDuplicateColdPublisherExecution()` utiliza `Mono.defer()` y contadores para comprobar cuántas veces se ejecutan realmente la conversión y el guardado.

Después de consumir el flujo con `StepVerifier`, ambos contadores deben contener:

```text
conversionSubscriptions = 1
saveSubscriptions       = 1
```

y Mockito comprueba adicionalmente una única publicación.

Esta prueba reproduce directamente el problema que existía cuando el mismo publisher frío tenía más de un suscriptor.

## Cambios que no se realizaron

### No se modificó `EmailOrderService`

`EmailOrderService` ya fue corregido durante TC-06 para producir una única cadena reactiva sin `subscribe()` internos.

TC-07 únicamente consume ese `Mono<TacoOrder>` y agrega las etapas de persistencia y publicación, por lo que modificar nuevamente la conversión no era necesario.

### No se cambió `OrderMessagingService` para retornar `Mono`

La interfaz continúa utilizando:

```java
void sendOrder(TacoOrder order);
```

TC-07 permite mantener temporalmente una interfaz `void` siempre que su efecto sea incorporado dentro de la cadena.

Por esta razón se utilizó `Mono.fromRunnable()` en lugar de modificar los distintos adaptadores de mensajería.

Cambiar el contrato común y los adaptadores excedería el alcance inmediato de TC-07 y se relaciona con retos posteriores de mensajería.

### No se implementó Outbox

No se intentó hacer atómicas las operaciones de MongoDB y el broker.

Actualmente sigue existiendo este posible escenario:

```text
repo.save()
    ↓
correcto
    ↓
sendOrder()
    ↓
error
```

En ese caso la orden queda persistida pero no publicada.

TC-07 exige reconocer esta limitación, no resolverla. La solución mediante un patrón Outbox corresponde a TC-29.

### No se modificó el `POST /api/orders` normal

El método:

```java
postOrder(...)
```

continúa con su comportamiento existente.

TC-07 especifica como contrato:

```text
POST /api/orders/fromEmail
```

y su resultado funcional se refiere a la orden proveniente de correo.

Modificar también el flujo de creación normal ampliaría el alcance del reto sin ser necesario para satisfacer sus criterios.

### No se implementaron mecanismos de reintento o idempotencia

No se agregaron:

* retries de publicación,
* identificadores de evento,
* deduplicación,
* DLQ,
* transacciones distribuidas,
* idempotencia del consumidor.

Estos mecanismos pertenecen a retos posteriores relacionados con mensajería confiable y no son necesarios para demostrar el objetivo específico de TC-07.

## Resultado

Con los cambios realizados, la creación de una orden proveniente de correo utiliza una única secuencia:

```text
convertir → guardar → publicar
```

sin suscripciones manuales y sin duplicar la ejecución de publishers fríos.

Los errores de conversión y persistencia impiden la publicación y las tres pruebas mínimas solicitadas verifican el comportamiento sin introducir funcionalidades correspondientes a retos posteriores.
