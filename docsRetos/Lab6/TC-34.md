# TC-34 — Idempotency-Key en creación de órdenes

## Descripción del TC

TC-34 protege exclusivamente `POST /api/orders` frente a doble clic y retries. La intención queda identificada por usuario autenticado, key y hash canónico; el flujo existente de pricing, inventario y outbox se reutiliza sin duplicarlo.

### Resultado funcional

`Idempotency-Key` es obligatorio. La primera creación devuelve `201 Created`; un replay completado devuelve `200 OK` con el mismo `orderId`. Una key reutilizada con otro payload devuelve `409`, y una petición concurrente mientras el ganador trabaja devuelve `409 IDEMPOTENCY_IN_PROGRESS`.

### Archivos modificados o creados

- `IdempotencyRecord.java`: documento Mongo mínimo, estados e índices.
- `IdempotencyRecordRepository.java`: lookup por usuario/key sin exportación Data REST.
- `OrderRequestHasher.java`: representación canónica y SHA-256.
- `OrderIdempotencyService.java`: claim, replay, conflictos, recuperación, transacción y retención.
- `OrderService.java`: envuelve el placement existente con la coordinación idempotente.
- `OrderApiController.java`: recibe el header y diferencia creación/replay.
- `application.yml`: retención y timeout externalizados.
- Pruebas de hash, controller, servicio y Mongo replica set.

### Trabajo solicitado

Aceptar una key validada y acotada al usuario; almacenar sólo su hash de intención y metadatos; impedir duplicados secuenciales y concurrentes; coordinar el resultado con inventario, orden y outbox; definir recuperación de `IN_PROGRESS`/`FAILED` y TTL.

### Restricciones técnicas obligatorias

- El scope es `(userId,key)` y posee un índice único Mongo.
- El hash no depende del JSON textual ni incluye campos controlados por servidor.
- No se usa `synchronized`, memoria local, Redis, espera bloqueante ni suscripción manual.
- El claim único se confirma antes del placement. Inventario, orden, outbox y transición a `COMPLETED` participan después en la transacción reactiva Mongo existente.
- La protección no se aplica a GET, PATCH, DELETE ni al contrato específico de reorder de TC-24.

### Criterios de aceptación

- Un retry completado recupera la misma orden sin reservar ni crear otro outbox.
- Dos peticiones concurrentes permiten un solo placement.
- La misma key con otro hash produce `409 IDEMPOTENCY_KEY_REUSED`.
- La misma key puede utilizarse por dos usuarios distintos.
- `IN_PROGRESS` reciente devuelve conflicto; uno abandonado se reclama tras dos minutos.
- Un fallo revierte los efectos transaccionales, deja `FAILED` y permite retry limpio.
- Los registros expiran después de 24 horas y la lógica no depende de la puntualidad del monitor TTL.

### Pruebas mínimas

- Hash estable frente a distinto orden textual de propiedades y distinto ante un cambio semántico.
- Doble ejecución secuencial, conflicto de payload y scope por usuario.
- Carrera controlada contra Mongo real con índice único.
- Conteo de orden, reserva, outbox y registro; stock descontado una sola vez.
- Rollback real y recuperación desde `FAILED`.
- `IN_PROGRESS` reciente/abandonado y registro expirado con `Clock.fixed`, sin sleeps.
- Formato de key, índices compuesto/TTL y política HTTP 201/200.

## Cambios de código

- `IdempotencyRecord`: persiste `id`, `userId`, `key`, `requestHash`, `orderId`, estado y timestamps. El índice único cierra la carrera y `expiresAt` tiene TTL.
- `IdempotencyRecordRepository`: ofrece sólo la consulta necesaria; no publica un CRUD automático.
- `OrderRequestHasher`: concatena en orden fijo campos de entrega, pago, cupón normalizado y líneas. Usa valores delimitados por longitud y SHA-256; no guarda el body.
- `OrderIdempotencyService`: inserta el claim, resuelve duplicados, carga la orden completada y recupera estados fallidos, abandonados o expirados mediante eliminación condicional. No registra la key.
- `OrderService`: obtiene `userId` desde Authentication, calcula el hash y pasa el `orderId` reservado al mismo método privado que ya ejecutaba pago, pricing, inventario y outbox.
- `OrderApiController`: exige semánticamente el header mediante validación uniforme TC-09; responde 201 con `Location` en creación y 200 en replay.
- `application.yml`: configura `retention=24h` e `in-progress-timeout=2m` mediante variables de entorno.
- Pruebas: usan `StepVerifier`, señales Reactor, `Clock.fixed` y Mongo Testcontainers en replica set. No usan `Thread.sleep`.

¿La respuesta repetida debe ser 200 o repetir 201? Ambas políticas son válidas. Se eligió `201 Created` para el primer commit y `200 OK` para el replay porque así el cliente distingue el efecto nuevo del resultado recuperado; ambos conservan el mismo `orderId` y ningún efecto se repite.

## Cambios que no se realizaron

TC-35:
versionado de API y OpenAPI.

TC-36:
suite global de integración.

No se agregó Redis, locking distribuido, un framework genérico de idempotencia ni infraestructura adicional porque Mongo, el índice único y la transacción existente son suficientes para TC-34. Tampoco se modificó la idempotencia específica de reorder, se añadieron métricas por key ni se confundió `Idempotency-Key` con `X-Correlation-Id`.

## Relación entre requisitos e implementación

| Requisito | Implementación |
| --- | --- |
| Header | `Idempotency-Key` obligatorio en `POST /api/orders` |
| Validación | 8–128 caracteres `[A-Za-z0-9._-]` |
| Scope | `userId + key` |
| Record | `IdempotencyRecord` |
| Unique constraint | índice compuesto Mongo único |
| Canonical hash | `OrderRequestHasher` + SHA-256 |
| Same key/same body | misma orden, replay 200 |
| Same key/different body | `409 IDEMPOTENCY_KEY_REUSED` |
| Secuencial | registro `COMPLETED` |
| Concurrente | claim por inserción e índice único |
| IN_PROGRESS | 409 reciente; reclaim condicional tras 2m |
| FAILED | rollback, estado durable y retry con mismo hash |
| TTL | `expiresAt`, índice TTL y retención 24h |
| Inventario | reserva TC-16 dentro de la transacción de placement |
| Outbox | `OrderOutboxService` TC-29 sin segunda publicación |
| Error contract | `ApiException` TC-09 |
| Usuario | identidad autenticada; nunca viene del body |

## Resultado

TC-34 queda implementado con un claim Mongo único y una sola cadena reactiva. El ganador ejecuta el caso de uso existente; los retries recuperan el resultado o reciben un conflicto estable. Las pruebas con Mongo replica set demuestran una sola orden, reserva y entrada outbox, además del rollback y la recuperación temporal.

Clases existentes reutilizadas:
`OrderService`, `InventoryService`, `OrderOutboxService`, `OrderCreateRequest`, `ApiMapper`, `ApiException`, `TransactionalOperator` y `Clock`.

Clases nuevas realmente necesarias:
`IdempotencyRecord`, su repositorio, `OrderRequestHasher` y `OrderIdempotencyService`.

Índices nuevos:
único `(userId,key)` y TTL sobre `expiresAt`.

Dependencias nuevas:
ninguna.

Abstracciones que se decidió NO crear:
framework genérico, locks distribuidos, Redis, command bus, replay engine o coordinadores adicionales.

Retos posteriores no adelantados:
TC-35 y TC-36.
