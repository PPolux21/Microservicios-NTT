# TC-06 Convertir órdenes de correo sin carreras ni nulls sorpresa

## Requisitos del proyecto

### Trabajo solicitado

* Eliminar los `subscribe()` internos y las listas modificadas desde callbacks.
* Resolver usuario y método de pago con errores explícitos cuando no existan.
* Convertir los tacos e ingredientes utilizando operadores reactivos.
* No emitir la orden hasta que todos los ingredientes hayan sido obtenidos.
* Rechazar IDs de ingredientes inexistentes indicando cuál produjo el error.

### Restricciones técnicas obligatorias

* Mantener una sola cadena reactiva desde `EmailOrder` hasta `TacoOrder`.
* No utilizar `block()`, `sleep()` ni estado mutable compartido.
* Preservar el orden de los tacos.
* Mantener definido el comportamiento respecto al orden de los ingredientes.

### Criterios de aceptación

* [x] La orden resultante contiene todos los tacos e ingredientes solicitados.
* [x] Usuario, método de pago o ingrediente faltante produce un error controlado.
* [x] No existe `subscribe()` dentro de `EmailOrderService`.
* [x] Las pruebas no dependen de tiempos arbitrarios.

### Pruebas mínimas

* [x] `StepVerifier` para el caso exitoso con varios tacos.
* [x] Prueba de ingrediente inexistente.
* [x] Prueba de usuario y método de pago ausentes.

Estos puntos corresponden a los requisitos establecidos específicamente para TC-06.

> **Pregunta para defender la solución**
>
> ¿Qué diferencia hay entre “ejecutar en paralelo” y “terminar antes de construir el objeto”?
>
> Ejecutar operaciones de forma reactiva no implica que el objeto pueda construirse antes de que dichas operaciones terminen. Para obtener una orden consistente es necesario componer las consultas dentro de la misma cadena y construir el `TacoOrder` únicamente después de que todos los usuarios, métodos de pago, tacos e ingredientes requeridos hayan sido resueltos.

### `EmailOrderService.java`

El método `convertEmailOrderToDomainOrder()` fue modificado para realizar toda la conversión mediante una única cadena reactiva.

Primero se obtiene el usuario utilizando el correo incluido en la orden:

```java
userRepo.findByEmail(eOrder.getEmail())
    .switchIfEmpty(
        Mono.error(
            new UserNotFoundException(
                eOrder.getEmail())))
```

Después se obtiene el método de pago asociado al usuario:

```java
paymentMethodRepo
    .findByUserId(user.getId())
    .switchIfEmpty(
        Mono.error(
            new PaymentMethodNotFoundException(
                user.getId())))
```

De esta manera, la ausencia de usuario o método de pago ya no produce una orden incompleta, sino un error controlado.

Para convertir los tacos se utiliza:

```java
Flux.fromIterable(emailTacos)
    .concatMap(this::convertTaco)
    .collectList();
```

`concatMap()` permite resolver cada taco dentro de la cadena reactiva preservando su orden, mientras que `collectList()` espera a que todos hayan sido convertidos antes de continuar.

Cada taco resuelve también sus ingredientes mediante:

```java
Flux.fromIterable(
        emailTaco.getIngredients())
    .concatMap(ingredientId ->
        ingredientRepo
            .findById(ingredientId)
            .switchIfEmpty(
                Mono.error(
                    new IngredientNotFoundException(
                        ingredientId))))
    .collectList();
```

La construcción del taco ocurre únicamente después de disponer de todos sus ingredientes. Además, si algún ID no existe, se genera una excepción que conserva el identificador que produjo el fallo.

Finalmente, el `TacoOrder` se construye sólo después de obtener usuario, pago y todos los tacos:

```java
convertTacos(eOrder.getTacos())
    .map(tacos ->
        buildOrder(
            user,
            paymentMethod,
            tacos))
```

El método `buildOrder()` asigna los datos de usuario y pago y agrega al pedido la lista de tacos ya completamente construida.
Con esto se elimina el problema original donde `subscribe()` agregaba ingredientes a una lista mientras la orden podía ser retornada antes de que las consultas terminaran.

### Excepciones de dominio

Se agregaron tres excepciones para representar de forma explícita los recursos necesarios que pueden faltar durante la conversión.

#### `UserNotFoundException.java`

Se utiliza cuando no existe ningún usuario registrado con el correo recibido.

La excepción conserva el correo causante del error mediante:

```java
private final String email;
```

#### `PaymentMethodNotFoundException.java`

Se utiliza cuando el usuario existe pero no posee un método de pago disponible.

La excepción conserva el identificador del usuario:

```java
private final String userId;
```

#### `IngredientNotFoundException.java`

Se utiliza cuando uno de los IDs incluidos en un taco no existe en el repositorio.

La excepción conserva el ID problemático:

```java
private final String ingredientId;
```

Esto permite identificar exactamente qué ingrediente produjo el fallo.

### `EmailOrderServiceTest.java`

Se implementaron únicamente las tres pruebas mínimas indicadas para TC-06.

#### Caso exitoso con varios tacos

Se crea una orden con dos tacos y cuatro ingredientes diferentes.

La prueba utiliza:

```java
StepVerifier.create(
    service.convertEmailOrderToDomainOrder(
        Mono.just(emailOrder)))
```

y comprueba que:

* El usuario de la orden es el esperado.
* Existen dos tacos.
* Los tacos conservan su orden.
* Cada taco contiene todos sus ingredientes.
* Los ingredientes también conservan el orden solicitado.

#### Ingrediente inexistente

Se configura uno de los tacos con:

```text
FLTO
UNKNOWN
```

El repositorio devuelve `Mono.empty()` para `UNKNOWN` y la prueba verifica que se produzca:

```java
IngredientNotFoundException
```

y que el ID almacenado en la excepción sea:

```text
UNKNOWN
```

#### Usuario y método de pago ausentes

La tercera prueba cubre los dos escenarios solicitados.

Cuando el correo no corresponde a ningún usuario se comprueba:

```java
UserNotFoundException
```

Cuando el usuario existe pero no posee un método de pago se comprueba:

```java
PaymentMethodNotFoundException
```

Ambos casos se verifican directamente con `StepVerifier`, sin utilizar esperas ni tiempos arbitrarios.
