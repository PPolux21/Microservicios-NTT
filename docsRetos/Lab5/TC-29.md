# TC-29 — Outbox transaccional para no perder órdenes

## Descripción del TC

TC-29 elimina el dual write entre MongoDB y el broker. La orden y su evento de integración se confirman o se abortan juntos en MongoDB; la entrega al transporte seleccionado por TC-28 ocurre después mediante un publicador durable.

### Resultado funcional

La creación por API, la creación por correo y las transiciones de TC-25 ya no publican directamente. Cada operación guarda `TacoOrder` y un `OutboxEvent` `NEW` dentro de la misma transacción reactiva. Un publisher reclama registros de forma atómica y los envía por el único `OrderMessagingService`. La garantía resultante es **at-least-once**: una caída después del envío y antes de marcar `PUBLISHED` puede causar una repetición legítima.

### Archivos modificados o creados

- `tacocloud/pom.xml`: administra la versión de Testcontainers.
- `tacocloud/tacocloud-api/pom.xml`: incorpora Testcontainers MongoDB/JUnit para pruebas reales.
- `tacocloud/tacocloud-data-mongodb/pom.xml`: permite persistir el contrato compartido de TC-27 sin depender de un broker.
- `tacocloud/tacocloud-data-mongodb/src/main/java/tacos/data/outbox/*`: documento, estados y repositorio del outbox.
- `tacocloud/tacocloud-api/src/main/java/tacos/web/api/outbox/*`: transacción, propiedades, persistencia coordinada, claim y publicación.
- `OrderService`, `OrderWorkflowService` y `OrderApiController`: eliminan la publicación directa y la dependencia innecesaria del controller.
- `application.yml`: externaliza replica set y parámetros operativos del outbox.
- Pruebas de API afectadas: adaptadas para comprobar el nuevo límite de persistencia sin alterar los comportamientos de TC-01 a TC-28.
- `OutboxMongoIntegrationTest`: prueba la transacción y el publisher contra un Mongo real en replica set.

### Trabajo solicitado

- Persistir orden y evento de TC-27 atómicamente.
- Mantener un outbox durable con estados e intentos visibles.
- Separar persistencia y publicación.
- Reclamar trabajo de forma segura ante varios publishers.
- Reintentar con backoff y recuperar claims abandonados.
- Probar commit, rollback, fallo/recuperación del broker, concurrencia, reinicio y seguridad del payload.

### Restricciones técnicas obligatorias

- MongoDB debe ejecutarse como replica set; una instancia standalone no ofrece la transacción requerida.
- Se usan `ReactiveMongoTransactionManager` y `TransactionalOperator`; no se llama `block()` ni `subscribe()` desde casos de uso.
- El outbox persiste `OrderEvent`, no `TacoOrder`, `User` ni datos de pago.
- El publisher depende sólo de `OrderMessagingService`, no de JMS, RabbitMQ o Kafka.
- No se promete exactly-once.
- La única suscripción explícita está en `OutboxPublisherScheduler`, frontera técnica que activa periódicamente el pipeline reactivo en Spring 5.3.

### Criterios de aceptación

- No existe un estado confirmado con orden sin outbox, ni outbox sin orden, para los flujos migrados.
- Un fallo del broker conserva el registro y programa otro intento.
- Un claim es atómico y no puede ser tomado simultáneamente por dos publishers.
- Los intentos agotados quedan en `FAILED` para diagnóstico.
- Un `PUBLISHING` vencido vuelve a ser reclamable tras una caída.
- `eventId`, versión, correlation ID y payload siguen siendo los definidos por TC-27.

### Pruebas mínimas

- Commit y rollback reales con `MongoDBContainer` replica set.
- Reintento después de fallo del broker y transición a `PUBLISHED`.
- Backoff persistido, reinicio con `NEW` pendiente y máximo de intentos a `FAILED`.
- Claim concurrente y recuperación de `PUBLISHING` abandonado.
- Dos eventos de la misma orden con `eventId` diferentes.
- Ausencia de PAN, CVV, password, token de pago y datos de entrega en el documento persistido.
- Regresiones unitarias de creación, reorder, workflow y controller.

## Cambios de código

- `OutboxEvent.java`: modela el registro durable con `eventId` único, tipo, versión, contrato TC-27, estado, intentos, tiempos, propietario del claim y error resumido. Los índices apoyan publicación por antigüedad y recuperación de claims; no contiene entidades Mongo de negocio ni datos sensibles.
- `OutboxStatus.java`: limita el ciclo a `NEW`, `PUBLISHING`, `PUBLISHED` y `FAILED`.
- `OutboxEventRepository.java`: ofrece persistencia reactiva y consulta por el ID global del evento; no introduce dependencias de transporte.
- `MongoTransactionConfiguration.java`: registra el transaction manager reactivo de Mongo y el `TransactionalOperator` que delimita el commit común.
- `OrderOutboxService.java`: guarda `TacoOrder`, construye el snapshot confirmado y guarda `OutboxEvent` dentro del mismo operador. Centraliza `ORDER_CREATED`, `STATUS_CHANGED` y `CANCELLED` sin publicar.
- `OrderService.java`: reemplaza `save → send` por `OrderOutboxService.saveCreated`. La compensación de inventario de TC-16 se mantiene cuando la transacción orden/outbox aborta.
- `OrderWorkflowService.java`: reemplaza la publicación directa de TC-25 por guardado transaccional del cambio y su evento. La liberación de inventario al cancelar permanece después del commit, como responsabilidad existente de TC-16.
- `OrderApiController.java`: elimina la referencia histórica a `OrderMessagingService`; el controller nunca participa en la publicación.
- `OutboxProperties.java`: centraliza lote, máximo de intentos, backoff inicial/máximo y timeout del claim.
- `OutboxPublisher.java`: usa `findAndModify` para cambiar atómicamente un registro elegible a `PUBLISHING`, incrementa `attempts`, publica por el puerto TC-27/TC-28 y actualiza a `PUBLISHED`, `NEW` con backoff o `FAILED`. La misma operación reclama claims vencidos.
- `OutboxPublisherScheduler.java`: es la única frontera de suscripción. Evita ciclos solapados dentro de una instancia; la protección entre instancias corresponde al claim Mongo atómico.
- `OutboxConfiguration.java`: habilita scheduling y binding de propiedades sin elegir ni conocer el broker.
- `application.yml`: recibe `MONGODB_URI` con replica set y externaliza lote, polling, reintentos, backoff y timeout mediante variables de entorno.
- POMs: el módulo de datos depende del contrato seguro, no de adaptadores; API añade sólo dependencias de prueba para el replica set efímero.
- Pruebas existentes: sustituyen el mock del broker en los casos de uso por el límite `OrderOutboxService`, conservando sus verificaciones funcionales previas.
- `OutboxMongoIntegrationTest.java`: comprueba con Mongo real la atomicidad, el índice único, estados, retries, backoff, claims concurrentes, reinicio, claim abandonado y payload seguro.

## Cambios que no se realizaron

TC-30:
deduplicación del consumidor, retry de procesamiento y DLQ.

TC-31:
propagación completa de correlation ID.

TC-32:
métricas operacionales completas.

Tampoco se añadieron Kafka transactions, change streams, una outbox SQL ni una afirmación de entrega exactly-once. La selección runtime de broker de TC-28 no cambió.

## Relación entre requisitos e implementación

| Requisito | Implementación |
| --- | --- |
| Order + outbox atómico | Mongo transaction en `OrderOutboxService` |
| Replica set | `MONGODB_URI` y `MongoDBContainer` |
| Transaction manager | `ReactiveMongoTransactionManager` |
| Contrato seguro | `OrderEvent` TC-27 |
| eventId | contrato TC-27 + índice único |
| NEW | persistencia inicial |
| PUBLISHING | claim atómico |
| PUBLISHED | envío exitoso |
| FAILED | intentos agotados |
| attempts | `OutboxEvent` incrementado al reclamar |
| timestamps | `OutboxEvent` |
| Publisher | `OutboxPublisher` separado |
| Claim concurrente | `findAndModify` atómico |
| Batch | `tacocloud.outbox.batch-size` |
| Retry | backoff exponencial configurable y acotado |
| Reinicio | estado durable `NEW` |
| PUBLISHING abandonado | `claim-timeout` y reclaim |
| Sin publish directo | servicios de orden escriben sólo el outbox |
| At-least-once | posible reenvío tras caída post-send documentado |
| Broker runtime | `OrderMessagingService` TC-28 |

## Resultado

El código implementa el patrón outbox sin acoplarlo a un transporte concreto y conserva el contrato seguro de TC-27. `OutboxMongoIntegrationTest` se ejecutó contra un `MongoDBContainer` en replica set: 7 pruebas, 0 fallos y 0 omitidas.
