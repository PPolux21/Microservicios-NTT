# TC-24 — Reordenar una compra anterior con reglas actuales

## Descripción del TC

### Resultado funcional

El propietario de una orden puede solicitar `POST /api/orders/{id}/reorder` con un método de pago actual y una `Idempotency-Key`. El servidor reconstruye explícitamente la intención de compra, cotiza con catálogo, reglas y cupones actuales y, si existen diferencias sin confirmar, devuelve `REORDER_QUOTE` sin efectos secundarios. Cuando procede, delega en el mismo caso de uso de creación normal y produce una orden nueva sin modificar la histórica.

### Trabajo solicitado

Se añadió el contrato de reorder con ownership, reconstrucción de un comando nuevo, validación y pricing actuales, revalidación del cupón, confirmación de diferencias, método de pago elegido expresamente, reserva actual de inventario e idempotencia específica y persistente. La respuesta diferencia cotización de creación y la orden histórica se utiliza sólo como fuente de intención.

### Restricciones técnicas obligatorias

- La orden histórica se consulta por `orderId + userId` obtenido de `Authentication`.
- No se clona ni se guarda de nuevo la `TacoOrder` original.
- Sólo se reconstruyen datos de entrega, nombre/diseño de tacos, ingredientes, cantidades y código de cupón histórico.
- Precio, reglas, disponibilidad, cupón, inventario y pago se vuelven a resolver con los servicios actuales.
- Una cotización no guarda orden, no reserva inventario y no publica eventos.
- El método de pago se recibe en el request y debe existir, pertenecer al usuario y estar tokenizado.
- La idempotencia queda limitada a reorder; no se implementa todavía la solución HTTP general de TC-34.
- El flujo permanece reactivo y no añade `block()` ni `subscribe()` en servicios.

### Criterios de aceptación

- [x] Existe `POST /api/orders/{id}/reorder` y requiere autenticación.
- [x] Sólo el propietario puede reordenar; orden ajena e inexistente producen `404`.
- [x] Se construye un `OrderCreateCommand` nuevo sin clonar el documento Mongo.
- [x] La orden nueva tiene ID, fecha y estado inicial nuevos.
- [x] La orden original permanece inmutable.
- [x] Los diseños se validan con `TacoDesignValidator` y catálogo actuales.
- [x] Los precios actuales se calculan mediante el mismo pricing de TC-14.
- [x] Un cambio económico sin confirmar devuelve `REORDER_QUOTE`.
- [x] La confirmación permite continuar, pero no omite reglas, pago ni inventario.
- [x] El cupón histórico se revalida y su descuento histórico nunca se copia.
- [x] La creación confirmada utiliza `InventoryService.reserve` y el caso de uso normal.
- [x] Stock insuficiente o ingrediente no disponible impiden crear la orden.
- [x] El pago histórico no se copia ni se expone; se valida `paymentMethodId` actual.
- [x] Repetir la misma operación lógica devuelve la misma orden sin duplicarla.
- [x] La respuesta no contiene PAN, CVV ni token de pago.
- [x] No se adelantaron TC-25, TC-27, TC-29 ni TC-34.

## Cambios de código

### `OrderApiController.java`

Expone el contrato HTTP y delega íntegramente en el servicio:

```java
@PostMapping(path="/{orderId}/reorder", consumes="application/json")
public Mono<ReorderResponse> reorder(
    @PathVariable String orderId,
    @RequestHeader(name="Idempotency-Key", required=false) String key,
    @Valid @RequestBody ReorderRequest request,
    Authentication authentication) {
  return orderService.reorder(orderId, request.getPaymentMethodId(),
      request.isConfirmPriceChange(), key, authentication)
      .map(ApiMapper::toResponse);
}
```

El controlador no acepta `userId`, no recupera datos de pago históricos y no contiene lógica paralela de creación.

### `ApiDtos.java`

Añade un request mínimo y una respuesta que distingue cotización y creación:

```java
public static class ReorderRequest {
  @NotBlank
  private String paymentMethodId;
  private boolean confirmPriceChange;
}

public static class ReorderResponse {
  private String status;
  private boolean requiresConfirmation;
  private BigDecimal originalTotal;
  private BigDecimal currentTotal;
  private BigDecimal difference;
  private List<String> differences;
  private OrderResponse order;
}
```

No hay campos para token, PAN, CVV, precio impuesto por cliente ni propietario.

### `ApiMapper.java`

Transforma el resultado de dominio de aplicación al DTO seguro. Sólo incluye `OrderResponse` cuando una nueva orden fue creada; el quote devuelve `order = null`.

### `OrderService.java`

El comando se reconstruye campo por campo desde la intención histórica:

```java
return new OrderCreateCommand(
    original.getDeliveryName(), original.getDeliveryStreet(),
    original.getDeliveryCity(), original.getDeliveryState(),
    original.getDeliveryZip(), paymentMethodId, items,
    original.getAppliedCouponCode());
```

Cada línea utiliza únicamente nombre, IDs de ingredientes y cantidad. No se copian ID, fecha, estado, reserva, versión, precios, descuento, total ni datos de pago.

El ownership reutiliza la política de TC-23:

```java
repo.findByIdAndUserId(originalOrderId, user.getId())
    .switchIfEmpty(Mono.error(ApiException.notFound(
        "ORDER_NOT_FOUND", "Order does not exist.")))
```

La cotización llama al `quote` existente. Si el cupón histórico ya no aplica, vuelve a cotizar sin él y registra `COUPON_NOT_APPLICABLE`; nunca conserva `discountAmount` como verdad actual. Una diferencia produce `REORDER_QUOTE` mientras `confirmPriceChange` sea falso.

La creación confirmada termina en el mismo método privado utilizado por `createOrder`:

```java
createOrder(command, authentication, newOrderId)
```

Por ello vuelve a validar el método de pago, precio, diseño, disponibilidad e inventario; guarda nuevos snapshots y utiliza la mensajería existente.

La key se acota mediante `userId + originalOrderId + key`. De ese scope se derivan IDs deterministas para el intento y la nueva orden. `insert` reclama el intento; un retry recupera la orden ya creada en lugar de ejecutar otra vez el flujo.

### `ReorderAttempt.java`

Documento persistente mínimo para la idempotencia específica:

```java
@Document(collection="reorderAttempts")
public class ReorderAttempt {
  @Id private String id;
  private String userId;
  private String originalOrderId;
  private String newOrderId;
  private Status status;
}
```

No almacena la key en claro ni una copia de la orden. Los estados se limitan a `PENDING` y `CREATED`; no constituyen la máquina de estados de TC-25.

### `ReorderAttemptRepository.java`

`ReactiveMongoRepository` aporta `insert` para reclamar de manera única el ID determinista del intento. Una colisión representa el mismo intento lógico y se resuelve recuperando su resultado.

`OrderReorderServiceTest` usa dobles reactivos con almacenamiento concurrente para demostrar que la misma key sólo reserva, guarda y publica una vez. También comprueba explícitamente:

```java

    created.getItems().get(0).getUnitPriceAtPurchase());
```

Las pruebas existentes recibieron únicamente la nueva dependencia del repositorio de intentos. La prueba de seguridad añadió la ruta reorder al controlador de prueba sin cambiar la matriz de seguridad productiva: `/api/orders/**` ya exigía USER o ADMIN.

## Cambios que no se realizaron

- **TC-25:** no se creó una máquina completa de estados ni historial de transiciones.
- **TC-27:** no se modificó el contrato final de eventos.
- **TC-29:** no se implementó outbox ni consistencia distribuida adicional.
- **TC-34:** no se creó un framework general de `Idempotency-Key`; la protección sólo cubre reorder.
- No se creó un motor de sustituciones para ingredientes eliminados/no disponibles: se rechaza usando las reglas actuales.
- No se clonó `TacoOrder`, no se copiaron snapshots económicos históricos y no se reutilizaron datos de pago históricos.
- No se añadió un segundo algoritmo de pricing, cupones o reserva de inventario.

Reordenar significa reconstruir y ejecutar nuevamente un comando de creación a partir de la intención histórica. La fase de quote informa diferencias; tras confirmarlas se ejecuta el caso de uso normal. No significa copiar el documento persistido.

## Relación entre requisitos e implementación

| Requisito | Implementación |
| --- | --- |
| Sólo orden propia | `findByIdAndUserId` con usuario autenticado |
| Nueva orden | `OrderCreateCommand` reconstruido explícitamente |
| Nuevo ID/fecha/estado | caso de uso normal con ID determinista nuevo |
| Original inmutable | sólo lectura y prueba de recarga/valores históricos |
| No clonar Mongo | `rebuildCommand` copia sólo intención permitida |
| Reglas actuales | `priceItems` + `TacoDesignValidator` |
| Precio actual | `quote`/pricing de TC-14 |
| Cupón actual | `CouponService` y fallback sin cupón inválido |
| Inventario actual | `InventoryService.reserve` de TC-16 |
| Pago actual | `paymentMethodId` requerido y validación de owner/token |
| Cambio de precio | `originalTotal`, `currentTotal`, `difference` |
| Confirmación | `confirmPriceChange` |
| Stock agotado | propagación de `INSUFFICIENT_STOCK` sin guardar orden |
| Quote vs creación | `REORDER_QUOTE` / `REORDER_CREATED` |
| Idempotencia | `ReorderAttempt` con scope usuario+orden+key |
| Sin datos de tarjeta | DTO/mapeo seguro de TC-12 |

## Resultado

TC-24 queda implementado: una orden propia se convierte en un comando nuevo, se cotiza y valida con las condiciones actuales y sólo se crea tras las confirmaciones necesarias. La creación reutiliza pago, pricing, cupones, inventario, persistencia y eventos existentes; el documento histórico no cambia. La key específica evita duplicar la nueva orden ante retries, y tanto quotes como errores de reglas o stock quedan sin efectos finales.
