# TC-08 — Separar DTOs de entrada, respuesta y persistencia

## Requisitos del proyecto

### Trabajo solicitado

* Crear contratos específicos para la entrada y salida de ingredientes y órdenes.
* Crear `OrderCreateRequest`, `OrderResponse`, `IngredientRequest` e `IngredientResponse`.
* Evitar utilizar directamente entidades Mongo como contrato HTTP.
* Excluir de las respuestas información sensible o interna como password, autoridades, PAN, CVV y objetos `User`.
* Utilizar identificadores y valores de negocio estables.
* Mantener los mappers libres de consultas a repositorios y lógica de negocio.
* Impedir que el cliente establezca campos controlados por el servidor.

### Restricciones técnicas obligatorias

* Los DTO no utilizan `@Document`, `@Id` ni interfaces relacionadas con Spring Security.
* Los campos controlados por el servidor no aparecen en los DTO de creación.
* Los mappers solamente transforman información ya disponible.
* Los controladores no reciben `TacoOrder` directamente como cuerpo de una petición de creación.

### Criterios de aceptación

* [x] La serialización pública de una orden no contiene `password`, `authorities`, `ccNumber` ni `ccCVV`.
* [x] El cliente no puede asignar directamente `id`, `placedAt`, `status`, `total` o `userId`.
* [x] Existen pruebas JSON que documentan el contrato público.
* [x] `POST /api/orders` ya no recibe un `TacoOrder` directamente.
* [x] Los endpoints modificados responden utilizando DTOs en lugar de exponer directamente las entidades.

### Pruebas mínimas

* [x] Serialización negativa de campos sensibles.
* [x] Mapeo `request → command` y `entity → response`.
* [x] Prueba de mass assignment con campos adicionales.

> **Pregunta para defender la solución**
>
> ¿Una entidad de persistencia es automáticamente un buen contrato público?
>
> No. Una entidad de persistencia representa cómo se almacena y relaciona la información internamente y puede contener campos técnicos, relaciones, información sensible o propiedades controladas por el servidor. Si se utiliza directamente como contrato HTTP, cualquier cambio del dominio puede modificar accidentalmente la API y también puede permitir exposición de información o mass assignment. Los DTO permiten definir explícitamente qué puede enviar y recibir el cliente.

## `ApiDtos.java`

Para evitar crear un archivo independiente por cada DTO, los contratos relacionados con TC-08 se agruparon como clases estáticas dentro de `ApiDtos`.

Se agregaron:

```java
IngredientRequest
IngredientResponse

OrderCreateRequest
OrderTacoRequest

OrderResponse
OrderTacoResponse
```

### DTO de ingredientes

`IngredientRequest` contiene únicamente:

```java
private String id;
private String name;
private Type type;
```

mientras que `IngredientResponse` define esos mismos valores para la respuesta pública.

De esta forma, `IngredientController` ya no necesita utilizar directamente `Ingredient` como request o response HTTP.

### `OrderCreateRequest`

La creación de una orden utiliza:

```java
private String deliveryName;
private String deliveryStreet;
private String deliveryCity;
private String deliveryState;
private String deliveryZip;

private List<OrderTacoRequest> tacos;
```

No existen dentro de este DTO campos controlados por el servidor como:

```text
id
placedAt
status
total
user
userId
```

Por lo tanto, esos valores no pueden ser asignados directamente desde el JSON recibido.

Los campos correspondientes a PAN, expiración y CVV tampoco se incorporaron finalmente al DTO de creación.

### `OrderResponse`

Las respuestas de órdenes exponen:

```java
id

deliveryName
deliveryStreet
deliveryCity
deliveryState
deliveryZip

placedAt
status

tacos
```

No contiene referencias a `User` ni propiedades como:

```text
password
authorities
ccNumber
ccCVV
ccExpiration
```

De esta forma, la estructura pública de la respuesta queda separada de `TacoOrder`.

### DTO anidados

`OrderTacoRequest` y `OrderTacoResponse` permiten representar los tacos que forman parte de una orden sin devolver directamente la estructura completa de persistencia como contrato del endpoint.

La decisión de agrupar estos DTO en un único archivo reduce la cantidad de archivos creados sin eliminar la separación conceptual entre entrada, salida y dominio.

## `ApiMapper.java`

Se creó `ApiMapper` como único punto de transformación entre los DTO, los comandos internos y las entidades.

### IngredientRequest → Ingredient

```java
public static Ingredient toEntity(
    IngredientRequest request) {

  return new Ingredient(
      request.getId(),
      request.getName(),
      request.getType());
}
```

### Ingredient → IngredientResponse

```java
public static IngredientResponse toResponse(
    Ingredient ingredient) {

  return new IngredientResponse(
      ingredient.getId(),
      ingredient.getName(),
      ingredient.getType());
}
```

Esto permite que los controladores trabajen con contratos HTTP específicos mientras los repositorios siguen utilizando las entidades originales.

### OrderCreateRequest → OrderCreateCommand

La creación de órdenes se divide en dos pasos.

Primero:

```text
OrderCreateRequest
        ↓
OrderCreateCommand
```

El mapper copia únicamente los campos permitidos y transforma también tacos e ingredientes a sus respectivos comandos internos.

El comando no contiene:

```text
id
placedAt
status
total
userId
```

por lo que esos valores no pueden propagarse desde la petición hasta la entidad.

### OrderCreateCommand → TacoOrder

Posteriormente:

```text
OrderCreateCommand
        ↓
TacoOrder
```

El mapper crea una nueva entidad y copia solamente los datos presentes en el comando.

No establece:

```text
id
placedAt
status
user
```

Estos valores quedan bajo control del dominio o del servicio.

### TacoOrder → OrderResponse

Para las respuestas se implementó:

```java
public static OrderResponse toResponse(
    TacoOrder order)
```

que transforma también los tacos e ingredientes internos antes de producir el objeto público.

El resultado es:

```text
TacoOrder
     ↓
ApiMapper
     ↓
OrderResponse
     ↓
JSON
```

sin serializar directamente la entidad Mongo.

### Ausencia de lógica de persistencia

`ApiMapper` no utiliza:

```java
repo.findById(...)
repo.save(...)
repo.delete(...)
```

ni depende de ningún repositorio.

Por lo tanto, su responsabilidad permanece limitada a transformar objetos.

## `IngredientController.java`

El controlador de ingredientes fue actualizado para utilizar los nuevos DTO.

### GET de ingredientes

Anteriormente los endpoints podían devolver directamente `Ingredient`.

Ahora:

```java
@GetMapping
public Flux<IngredientResponse> allIngredients() {

  return repo.findAll()
      .map(ApiMapper::toResponse);
}
```

y la consulta individual también transforma la entidad antes de responder:

```java
@GetMapping("/{id}")
public Mono<IngredientResponse> byId(
    @PathVariable String id) {

  return repo.findById(id)
      .map(ApiMapper::toResponse);
}
```

### PUT

El PUT ahora recibe:

```java
@RequestBody IngredientRequest request
```

y lo transforma mediante:

```java
Ingredient ingredient =
    ApiMapper.toEntity(request);
```

Se mantiene el comportamiento de TC-01:

```text
200 → ingrediente actualizado
400 → ID inconsistente
404 → ingrediente inexistente
```

### POST

El POST utiliza:

```java
Mono<IngredientRequest>
```

como entrada y devuelve:

```java
ResponseEntity<IngredientResponse>
```

La creación sigue utilizando la URL de la petición real:

```java
ServletUriComponentsBuilder
    .fromRequestUri(request)
    .pathSegment(savedIngredient.getId())
```

por lo que se conserva la solución implementada anteriormente en TC-03.

### DELETE

El DELETE no fue convertido a DTO porque:

```text
DELETE /api/ingredients/{id}
```

no recibe una entidad y responde únicamente mediante estados HTTP.

Por ello continúa retornando:

```java
Mono<ResponseEntity<Void>>
```

con los comportamientos 204 y 404 definidos previamente.

## `OrderApiController.java`

El controlador de órdenes dejó de exponer `TacoOrder` como contrato HTTP en las operaciones modificadas.

### GET

Ahora retorna:

```java
Flux<OrderResponse>
```

mediante:

```java
return repo.findAll()
    .map(ApiMapper::toResponse);
```

### POST de una orden

Anteriormente la creación recibía directamente:

```java
@RequestBody TacoOrder order
```

Ahora recibe:

```java
@RequestBody OrderCreateRequest request
```

y el flujo es:

```text
OrderCreateRequest
        ↓
ApiMapper.toCommand()
        ↓
OrderCreateCommand
        ↓
OrderService
        ↓
TacoOrder
        ↓
ApiMapper.toResponse()
        ↓
OrderResponse
```

Esto elimina la posibilidad de realizar mass assignment directamente sobre `TacoOrder`.

### Orden recibida por correo

El endpoint:

```text
POST /api/orders/fromEmail
```

conserva el flujo creado en TC-07, pero ahora transforma el resultado final a:

```java
OrderResponse
```

antes de devolverlo al cliente.

### PUT y PATCH

Los endpoints PUT y PATCH continúan utilizando:

```java
OrderDeliveryRequest
```

creado anteriormente para TC-04/TC-05.

No se creó otro DTO para estas operaciones porque `OrderDeliveryRequest` ya contiene exclusivamente la lista blanca de campos de entrega:

```text
deliveryName
deliveryStreet
deliveryCity
deliveryState
deliveryZip
```

Las respuestas sí fueron modificadas de:

```java
ResponseEntity<TacoOrder>
```

a:

```java
ResponseEntity<OrderResponse>
```

manteniendo las validaciones de ownership, campos permitidos y códigos HTTP implementadas anteriormente.

### DELETE

DELETE continúa utilizando:

```java
Mono<ResponseEntity<Void>>
```

porque no devuelve una entidad.

## `OrderService.java`

Se agregó el método:

```java
public Mono<TacoOrder> createOrder(
    OrderCreateCommand command)
```

para convertir el comando interno en la entidad que realmente se persiste.

El flujo es:

```text
OrderCreateCommand
        ↓
ApiMapper.toEntity()
        ↓
TacoOrder
        ↓
placedAt generado por servidor
        ↓
repo.save()
        ↓
sendOrder()
```

La fecha se establece dentro del servidor:

```java
order.setPlacedAt(new Date());
```

por lo que el cliente no puede proporcionar su propio `placedAt`.

Después se mantiene la política de TC-07:

```text
guardar → publicar
```

utilizando:

```java
repo.save(order)
    .flatMap(savedOrder ->
        Mono.fromRunnable(() ->
            orderMessages.sendOrder(savedOrder))
            .thenReturn(savedOrder));
```

El flujo existente de creación desde correo permanece separado en `createOrderFromEmail()`.

## `DtoContractTest.java`

Se implementaron únicamente las tres pruebas mínimas correspondientes a TC-08.

### Serialización negativa de campos sensibles

La prueba:

```java
shouldNotSerializeSensitiveOrderFields()
```

crea un `TacoOrder`, lo transforma mediante:

```java
ApiMapper.toResponse(order)
```

y posteriormente serializa el `OrderResponse` con Jackson.

Se comprueba que el JSON no contenga:

```text
password
authorities
ccNumber
ccCVV
ccExpiration
user
```

Esto demuestra que la respuesta pública no depende directamente de la serialización completa de `TacoOrder` o `User`.

### Request → Command y Entity → Response

La prueba:

```java
shouldMapRequestCommandAndEntityResponse()
```

comprueba ambas direcciones requeridas.

Primero:

```text
OrderCreateRequest
        ↓
OrderCreateCommand
```

validando que los datos de entrega, tacos e ingredientes sean transformados correctamente.

Después:

```text
TacoOrder
        ↓
OrderResponse
```

comprobando:

```text
id
deliveryName
status
tacos
ingredientes
```

Esto documenta mediante prueba el contrato utilizado por los mappers.

### Mass assignment

La prueba:

```java
shouldIgnoreServerOwnedFields()
```

intenta deserializar el siguiente tipo de información:

```json
{
  "deliveryName": "Jose",
  "id": "ORDER-HACK",
  "placedAt": "2000-01-01T00:00:00Z",
  "status": "PREPARING",
  "total": 0,
  "userId": "OTHER-USER",
  "ccNumber": "4111111111111111",
  "ccCVV": "321"
}
```

Jackson está configurado para ignorar campos que no pertenecen al DTO.

Después del flujo:

```text
JSON
 ↓
OrderCreateRequest
 ↓
OrderCreateCommand
 ↓
TacoOrder
```

se verifica que:

```text
deliveryName = "Jose"
id           != "ORDER-HACK"
placedAt     != fecha enviada por el cliente
user         = null
status       != PREPARING
```

`placedAt` no se comprueba contra `null` porque `TacoOrder` puede inicializar la fecha automáticamente. La garantía relevante para TC-08 es que no tenga el valor enviado por el cliente.

De esta manera la prueba demuestra que los campos adicionales no pueden modificar propiedades controladas por el servidor.

# Cambios que no se realizaron

## No se creó un archivo independiente para cada DTO

Aunque conceptualmente existen:

```text
IngredientRequest
IngredientResponse
OrderCreateRequest
OrderResponse
OrderTacoRequest
OrderTacoResponse
```

todos fueron agrupados dentro de:

```text
ApiDtos.java
```

Esto se hizo para evitar aumentar innecesariamente la cantidad de archivos del proyecto.

La separación de responsabilidades se mantiene porque siguen siendo tipos independientes y ninguno funciona como entidad de persistencia.

## No se creó un mapper por cada entidad

Las transformaciones de ingredientes y órdenes se agruparon dentro de:

```text
ApiMapper.java
```

El reto requiere mappers, pero no exige un archivo individual para cada uno.

La implementación mantiene la responsabilidad del mapper limitada a transformaciones y evita consultas a repositorios.

## No se reemplazó `OrderDeliveryRequest`

`OrderDeliveryRequest` ya había sido creado para TC-04/TC-05 y cumple la función de DTO específico para actualizar los datos de entrega.

Crear un segundo DTO con exactamente la misma lista blanca habría duplicado código sin aportar comportamiento nuevo.

Por esa razón se reutiliza en:

```text
PUT /api/orders/{orderId}
PATCH /api/orders/{orderId}
```

## No se añadieron validaciones Bean Validation

No se agregaron todavía anotaciones como:

```java
@NotNull
@NotBlank
@Size
@Pattern
@Valid
```

ni manejo global de errores.

TC-09 solicita explícitamente validación y respuestas uniformes mediante Problem Details, por lo que implementarlo durante TC-08 adelantaría el siguiente reto.

## No se creó `ApiProblem` ni `@RestControllerAdvice`

Los errores continúan utilizando el comportamiento existente de los controladores.

La normalización de errores, códigos funcionales y respuestas `application/problem+json` corresponde a TC-09.

## No se implementó autenticación deny-by-default

La lógica de ownership previamente creada para PUT, PATCH y DELETE se conserva, pero TC-08 no modifica la configuración global de Spring Security.

La política de autorización completa pertenece a TC-11.

## No se implementó tokenización de pago

No se agregaron:

```text
PaymentToken
PaymentGateway
tokenización
redacción de eventos
migración de PAN/CVV
```

Estos cambios corresponden específicamente a TC-12.

Para TC-08 únicamente se garantiza que la respuesta pública no exponga propiedades de pago sensibles y que dichos campos adicionales no sean aplicados por mass assignment.

## No se permitió controlar `placedAt` desde el request

`placedAt` no forma parte de `OrderCreateRequest`.

La fecha pertenece al servidor y se establece durante la creación de la orden.

La prueba de mass assignment comprueba que una fecha proporcionada en el JSON no sustituye la fecha generada internamente.

## No se modificó el contrato DELETE

Los DELETE de ingredientes y órdenes continúan retornando:

```java
ResponseEntity<Void>
```

porque no existe una entidad que deba transformarse en DTO para esas respuestas.

## No se realizó una refactorización adicional del controlador

Se conservaron dependencias y estructura previamente utilizadas cuando eliminarlas no era necesario para satisfacer TC-08.

El objetivo fue limitar los cambios a la separación entre:

```text
HTTP Request
     ↓
DTO
     ↓
Command
     ↓
Dominio / persistencia
     ↓
DTO de respuesta
     ↓
HTTP Response
```

sin introducir modificaciones arquitectónicas pertenecientes a retos posteriores.

---

## Cumplimiento del reto

Con estos cambios, los endpoints modificados dejan de utilizar directamente las entidades principales como contrato público.

Los ingredientes siguen el flujo:

```text
IngredientRequest
      ↓
Ingredient
      ↓
IngredientResponse
```

y la creación de órdenes sigue:

```text
OrderCreateRequest
      ↓
OrderCreateCommand
      ↓
TacoOrder
      ↓
OrderResponse
```

Los campos controlados por el servidor no forman parte del DTO de creación, las respuestas no contienen información sensible del usuario o del pago y los mappers permanecen independientes de los repositorios.

Las tres pruebas mínimas de TC-08 comprueban la serialización segura, el mapeo entre capas y la protección contra mass assignment, sin implementar anticipadamente las funcionalidades correspondientes a TC-09, TC-11 o TC-12.
