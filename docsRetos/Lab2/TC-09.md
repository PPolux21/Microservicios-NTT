# TC-09 — Validación y errores tipo Problem Details

## Requisitos del proyecto

### Trabajo solicitado

* Agregar validaciones de campos requeridos, tamaños, formatos y cantidades.
* Crear un DTO propio `ApiProblem` compatible conceptualmente con Problem Details.
* Incluir en los errores:

  * `type`
  * `title`
  * `status`
  * `detail`
  * `instance`
  * `code`
  * `violations`
* Mapear de forma uniforme:

  * errores de validación;
  * recursos inexistentes;
  * conflictos;
  * errores de autorización;
  * reglas de negocio.
* Evitar exponer stack traces, excepciones internas o mensajes provenientes de drivers.
* Ejecutar la validación antes de cualquier efecto externo.

### Restricciones técnicas obligatorias

* No utilizar `ProblemDetail` de Spring 6, ya que el proyecto utiliza Spring Boot 2.5.3 / Spring 5.3.
* Mantener códigos funcionales estables.
* La validación debe ocurrir antes de guardar o publicar.
* Los errores funcionales conocidos no deben transformarse accidentalmente en HTTP 500.

### Criterios de aceptación

* [x] Los errores controlados utilizan una estructura común.
* [x] Una orden inválida informa los campos y motivos de validación.
* [x] Los errores 404, 409 y 422 conservan su semántica y no terminan como 500.
* [x] `instance` identifica la ruta donde ocurrió el problema.
* [x] Las respuestas de error no exponen stack traces ni detalles de drivers.
* [x] La validación ocurre antes de ejecutar el servicio o repositorio.

### Pruebas mínimas

* [x] Validación simultánea de varios campos.
* [x] Excepciones funcionales traducidas correctamente a 409/422.
* [x] Comprobación de que un error interno no expone stacktrace ni nombre del driver.

> **Pregunta para defender la solución**
>
> ¿Cuándo utilizar 400, 409 y 422?
>
> La política utilizada en el proyecto es:
>
> * **400 Bad Request:** la petición no cumple el contrato de entrada, contiene JSON inválido, campos con formato incorrecto o campos no permitidos.
> * **409 Conflict:** la petición es válida, pero no puede ejecutarse debido al estado actual del recurso. Por ejemplo, intentar eliminar una orden que ya está en preparación.
> * **422 Unprocessable Entity:** la petición es sintácticamente válida, pero no puede completarse porque viola una regla de negocio, como utilizar un ingrediente inexistente dentro de una orden.
>
> Esta separación permite que la UI diferencie entre errores del request, conflictos de estado y reglas de negocio.

# Modificaciones realizadas

La implementación de TC-09 se concentra en los contratos HTTP y el manejo uniforme de errores.

La estructura utilizada es:

```text
tacocloud-api/src/main/java/tacos/web/api/
├── IngredientController.java
├── OrderApiController.java
├── OrderDeliveryRequest.java
│
├── dto/
│   └── ApiDtos.java
│
└── error/
    ├── ApiProblem.java
    └── ApiExceptionHandler.java

tacocloud-api/src/test/java/tacos/web/api/
└── ApiExceptionHandlerTest.java
```

Los DTO introducidos durante TC-08 continúan utilizándose y fueron ampliados únicamente con las validaciones necesarias para TC-09.

---

## `ApiDtos.java`

Los DTO de entrada creados durante TC-08 fueron complementados con Bean Validation.

Se utilizaron anotaciones de:

```java
javax.validation.*
```

en lugar de `jakarta.validation.*`, debido a la versión de Spring utilizada por el proyecto.

### `IngredientRequest`

Se agregaron validaciones para:

```text
id
name
type
```

Por ejemplo:

```java
@NotBlank
@Pattern(...)
private String id;

@NotBlank
@Size(...)
private String name;

@NotNull
private Type type;
```

De esta manera se evita que un ingrediente llegue al repositorio con identificador vacío, nombre inválido o sin tipo.

### `OrderCreateRequest`

Los datos de entrega se validan antes de construir el `OrderCreateCommand`.

Se validan:

```text
deliveryName
deliveryStreet
deliveryCity
deliveryState
deliveryZip
tacos
```

Las restricciones incluyen:

```java
@NotBlank
@NotNull
@Size
@Pattern
@Valid
```

La lista de tacos también tiene un mínimo y máximo permitido.

Esto permite detectar una orden incompleta antes de ejecutar:

```java
orderService.createOrder(...)
```

### `OrderTacoRequest`

También se agregaron validaciones a los tacos internos.

Se comprueba:

```text
name
ingredients
```

y mediante:

```java
@Valid
```

la validación continúa recursivamente hacia cada `IngredientRequest`.

Por lo tanto, una petición puede informar en una sola respuesta múltiples problemas ubicados en diferentes niveles del JSON.

---

# `OrderDeliveryRequest.java`

El DTO creado originalmente para TC-04/TC-05 se mantiene y se reutiliza.

TC-09 únicamente agrega restricciones compatibles con PUT/PATCH.

Por ejemplo:

```java
@Size(max=50)
private String deliveryName;

@Pattern(...)
private String deliveryZip;
```

No se utilizaron anotaciones como:

```java
@NotBlank
```

sobre todos los campos porque PATCH permite enviar solamente una parte de los datos.

Un campo puede estar ausente, pero si está presente debe cumplir las restricciones correspondientes.

La lista blanca implementada previamente mediante:

```java
@JsonAnySetter
```

también se conserva para detectar propiedades que el cliente no tiene permitido modificar.

---

# `ApiProblem.java`

Se creó un contrato común para las respuestas de error.

La estructura contiene:

```java
type
title
status
detail
instance
code
violations
```

El resultado HTTP puede tener una forma equivalente a:

```json
{
  "type": "urn:tacocloud:problem:validation_error",
  "title": "Invalid request",
  "status": 400,
  "detail": "The request contains invalid fields.",
  "instance": "/api/orders",
  "code": "VALIDATION_ERROR",
  "violations": [
    {
      "field": "deliveryName",
      "reason": "deliveryName is required"
    }
  ]
}
```

### `Violation`

Dentro de `ApiProblem` se agregó una estructura pequeña para representar errores de campo:

```java
field
reason
```

Esto permite que la interfaz de usuario pueda asociar cada problema al campo correspondiente sin analizar mensajes internos de Spring.

### Motivo de utilizar un DTO propio

No se utilizó:

```java
org.springframework.http.ProblemDetail
```

porque esa API pertenece a versiones posteriores de Spring.

Actualizar Spring únicamente para obtener dicha clase habría modificado innecesariamente la base tecnológica del proyecto.

Por eso se creó un DTO propio compatible conceptualmente con Problem Details.

---

# `ApiExceptionHandler.java`

Se creó un manejador global utilizando:

```java
@RestControllerAdvice
```

Su responsabilidad es convertir las excepciones de la aplicación a una representación `ApiProblem`.

De esta forma los controladores ya no necesitan construir una respuesta de error diferente para cada escenario.

Conceptualmente:

```text
Controller / Service
        │
        │ error
        ▼
ApiExceptionHandler
        │
        ▼
ApiProblem
        │
        ▼
HTTP 4xx / 5xx
```

## Error de Bean Validation

`MethodArgumentNotValidException` se transforma en:

```text
HTTP 400
code = VALIDATION_ERROR
```

Los errores encontrados por Bean Validation se recorren para construir una lista de:

```text
field → reason
```

Por ejemplo:

```text
deliveryName  → deliveryName is required
deliveryZip   → deliveryZip has an invalid format
tacos         → order must contain between 1 and 20 tacos
```

Esto permite devolver varios errores dentro de la misma respuesta.

---

## JSON inválido

`HttpMessageNotReadableException` se transforma en:

```text
HTTP 400
code = MALFORMED_JSON
```

El mensaje que se devuelve es controlado por la aplicación.

No se utiliza directamente:

```java
exception.getMessage()
```

porque podría contener detalles internos de Jackson o de las clases Java.

---

## Excepciones funcionales

Se agregó una excepción común que contiene:

```text
status
code
detail
```

Esto permite producir errores de forma simple desde los controladores.

Por ejemplo:

```java
ApiException.notFound(...)
ApiException.forbidden(...)
ApiException.conflict(...)
ApiException.unprocessable(...)
```

El handler transforma posteriormente la excepción al formato común.

---

## Recursos inexistentes

Un recurso que no existe se representa mediante:

```text
HTTP 404
```

con códigos funcionales como:

```text
ORDER_NOT_FOUND
INGREDIENT_NOT_FOUND
USER_NOT_FOUND
```

El objetivo es evitar que un `Mono.empty()` termine produciendo respuestas ambiguas o que una excepción asociada termine convertida en 500.

---

## Conflictos

Los conflictos de estado utilizan:

```text
HTTP 409
```

Un caso ya existente en el proyecto es una orden con:

```java
Status.PREPARING
```

que no puede eliminarse físicamente.

Ese comportamiento ahora puede representarse mediante:

```text
code = ORDER_ALREADY_PREPARING
status = 409
```

en lugar de devolver una respuesta vacía sin un contrato de error común.

---

## Reglas de negocio

Los errores en los que la petición es válida sintácticamente pero la operación no puede completarse utilizan:

```text
HTTP 422
```

Por ejemplo:

```text
INGREDIENT_NOT_FOUND
PAYMENT_METHOD_REQUIRED
BUSINESS_RULE_VIOLATION
```

Esto diferencia una regla de negocio de un request mal formado.

---

## Autorización

Los errores de autorización se representan mediante:

```text
HTTP 403
code = FORBIDDEN
```

o un código funcional más específico como:

```text
ORDER_FORBIDDEN
```

TC-09 únicamente normaliza la respuesta de estos errores.

No modifica todavía la política global de seguridad de Spring.

---

## Error interno

También se agregó un manejador genérico para errores inesperados:

```java
@ExceptionHandler(Exception.class)
```

que produce:

```text
HTTP 500
code = INTERNAL_ERROR
```

con un mensaje controlado:

```text
An unexpected error occurred.
```

No se devuelve:

```text
exception.getMessage()
stackTrace
cause
nombre de excepción
nombre de driver
```

De esta manera una excepción interna como:

```text
MongoTimeoutException
MongoSocketException
NullPointerException
```

no expone información de implementación al cliente.

---

# `IngredientController.java`

Los endpoints de ingredientes fueron adaptados para utilizar Bean Validation y el manejador global de errores.

## POST

El `IngredientRequest` se valida antes de convertirlo y persistirlo.

El flujo queda:

```text
HTTP Request
     ↓
@Valid IngredientRequest
     ↓
ApiMapper
     ↓
repo.save()
```

Si la validación falla, el repositorio no es ejecutado.

La construcción dinámica de `Location` implementada en TC-03 se mantiene sin cambios funcionales.

---

## PUT

La actualización continúa comprobando la consistencia entre:

```text
ID de la ruta
ID del request
```

pero los errores se integran al nuevo contrato uniforme.

Un ID contradictorio se considera:

```text
HTTP 400
```

mientras que un ingrediente que no existe se representa como:

```text
HTTP 404
```

La escritura sigue formando parte de la cadena reactiva.

---

## GET/DELETE

Las operaciones que no encuentran el ingrediente utilizan ahora la misma representación de error que el resto de la API.

De esta manera un 404 deja de depender de una respuesta específica construida dentro del controlador.

---

# `OrderApiController.java`

El controlador de órdenes fue adaptado para ejecutar Bean Validation y producir excepciones funcionales que posteriormente son traducidas por `ApiExceptionHandler`.

## POST

La creación utiliza:

```java
@Valid
@RequestBody OrderCreateRequest request
```

La validación ocurre antes de:

```java
ApiMapper.toCommand(...)
orderService.createOrder(...)
```

Por lo tanto:

```text
request inválido
      ↓
Bean Validation
      ↓
400
```

y nunca:

```text
request inválido
      ↓
guardar
      ↓
publicar
```

Esto cumple la restricción de validar antes de cualquier efecto externo.

---

## PUT/PATCH

`OrderDeliveryRequest` también es validado mediante `@Valid`.

Los campos no permitidos continúan detectándose mediante la lista blanca existente.

Los escenarios se normalizan de la siguiente manera:

```text
campo no permitido     → 400
orden inexistente      → 404
sin autorización       → 403
datos válidos          → operación normal
```

Todos los errores controlados pueden ser transformados posteriormente a `ApiProblem`.

---

## DELETE

La operación conserva el comportamiento introducido en TC-05.

Los escenarios quedan:

```text
orden inexistente       → 404
sin autorización        → 403
orden PREPARING         → 409
orden eliminable        → 204
```

La diferencia introducida por TC-09 es que los errores utilizan ahora un contrato uniforme en lugar de retornar únicamente estados HTTP sin información estructurada.

# `ApiExceptionHandlerTest.java`

Se agregaron únicamente las tres pruebas mínimas especificadas por TC-09.

## Validación de varios campos

La primera prueba envía una orden que contiene simultáneamente varios campos inválidos.

Por ejemplo:

```json
{
  "deliveryName": "",
  "deliveryStreet": "",
  "deliveryCity": "",
  "deliveryState": "X",
  "deliveryZip": "!",
  "tacos": []
}
```

Se comprueba:

```text
HTTP 400
code = VALIDATION_ERROR
instance = /api/orders
```

y que `violations` contenga todos los campos encontrados.

También se verifica que:

```java
orderService.createOrder(...)
```

no haya sido ejecutado.

Esto demuestra que la validación se realiza antes de persistir o publicar.

---

## Mapeo de excepciones funcionales

La segunda prueba comprueba explícitamente que diferentes errores mantengan su semántica.

Se prueban:

```text
not found       → 404
conflict        → 409
business rule   → 422
```

y se verifica el código funcional correspondiente.

Esto evita una regresión en la que una excepción conocida termine convertida en:

```text
500 Internal Server Error
```

---

## Protección de información interna

La tercera prueba provoca intencionalmente una excepción con información simulada de un driver:

```text
MongoTimeoutException
com.mongodb
```

La respuesta debe contener únicamente:

```text
HTTP 500
code = INTERNAL_ERROR
```

sin incluir:

```text
MongoTimeoutException
com.mongodb
stacktrace
```

Con esto se comprueba que la API no expone información de implementación.

# Política HTTP establecida

Para mantener consistencia en los siguientes retos se definió la siguiente política:

| Estado                      | Uso                                                              |
| --------------------------- | ---------------------------------------------------------------- |
| `400 Bad Request`           | Request mal formado, Bean Validation o campos no permitidos      |
| `403 Forbidden`             | Usuario identificado pero sin permiso para realizar la operación |
| `404 Not Found`             | El recurso solicitado no existe                                  |
| `409 Conflict`              | La operación entra en conflicto con el estado actual del recurso |
| `422 Unprocessable Entity`  | El request es válido, pero incumple una regla de negocio         |
| `500 Internal Server Error` | Error inesperado no controlado                                   |

Además de los estados HTTP, cada error controlado contiene un código funcional estable como:

```text
VALIDATION_ERROR
MALFORMED_JSON
ORDER_NOT_FOUND
INGREDIENT_NOT_FOUND
ORDER_ALREADY_PREPARING
BUSINESS_RULE_VIOLATION
INTERNAL_ERROR
```

Esto permite que la interfaz de usuario dependa de códigos definidos por la aplicación y no de mensajes internos.

# Cambios que no se realizaron

## No se actualizó Spring

No se migró el proyecto a Spring Boot 3 ni Spring Framework 6.

Por esta razón tampoco se utilizó:

```java
ProblemDetail
```

El propio TC-09 establece que debe mantenerse la base Spring 5.3 y crear un DTO propio.

Actualizar todo el framework únicamente para utilizar `ProblemDetail` generaría cambios fuera del alcance del reto.

---

## No se agregó correlation ID

`ApiProblem` no incluye todavía un identificador de correlación.

El enunciado indica agregarlo:

```text
cuando TC-31 esté disponible
```

Por lo tanto, implementarlo en TC-09 adelantaría funcionalidad correspondiente a un reto posterior.

---

## No se modificó la seguridad global

TC-09 traduce errores de autorización a una estructura uniforme, pero no cambia:

```text
SecurityConfig
roles globales
deny-by-default
rutas permitidas
```

La autorización completa corresponde a TC-11.

---

## No se modificó el registro de usuarios

No se cambiaron:

```text
RegistrationController
PasswordEncoder
UserRepository
hash de contraseña
```

Estas modificaciones pertenecen específicamente a TC-10.

---

## No se agregó tokenización de pagos

No se introdujeron:

```text
PaymentToken
PaymentGateway
tokenización
eliminación definitiva de PAN/CVV
```

Esto corresponde a TC-12.

---

## No se incorporó lógica de negocio a los DTO

Las anotaciones Bean Validation comprueban únicamente propiedades propias del contrato:

```text
requerido
tamaño
formato
cantidad
```

No se agregaron decisiones de negocio dentro de:

```text
ApiDtos
ApiMapper
```

Las reglas funcionales continúan representándose mediante servicios o excepciones funcionales.

---

## No se devolvieron mensajes originales de excepciones inesperadas

Para los errores internos no se utiliza:

```java
exception.getMessage()
```

porque podría revelar:

```text
drivers
consultas
clases internas
direcciones
credenciales
detalles de infraestructura
```

El cliente recibe únicamente un mensaje genérico controlado.

---

## No se crearon excepciones independientes para cada posible error

Para evitar aumentar innecesariamente la cantidad de archivos, se utiliza una excepción funcional común con:

```text
HttpStatus
code
detail
```

Sólo se mantienen excepciones específicas que ya existían en retos anteriores cuando representan errores concretos del dominio.

Esto reduce la cantidad de clases nuevas sin perder códigos de error estables.

# Resultado

Después de TC-09, el procesamiento de una petición queda conceptualmente:

```text
HTTP Request
      ↓
Bean Validation
      │
      ├── error
      │     ↓
      │ ApiExceptionHandler
      │     ↓
      │ ApiProblem
      │
      ▼
Controller
      ↓
Service / Repository
      │
      ├── error funcional
      │     ↓
      │ ApiExceptionHandler
      │     ↓
      │ ApiProblem
      │
      ▼
HTTP Response
```

TC-09 establece así un contrato uniforme para los errores de la API, mantiene separados los errores de entrada, conflictos y reglas de negocio, evita filtrar información interna y garantiza que la validación ocurra antes de persistir o publicar información.

La solución permanece limitada al objetivo del reto y deja para TC posteriores el registro seguro de usuarios, la autorización completa, la tokenización de pagos y la correlación distribuida.
