# TC-04 — PATCH de órdenes con lista blanca y sin ZIP mutante

## Requisitos del proyecto

### Trabajo solicitado

* Corregir la asignación de `deliveryZip`.
* Crear un DTO específico para PATCH con únicamente los campos permitidos.
* Evitar que PATCH modifique ID, usuario, fecha, total, estado, pago o tacos.
* Devolver `404` cuando la orden no exista.
* Devolver `400` cuando el PATCH contenga campos no permitidos o la orden resultante no sea válida.
* Comprobar que la orden pertenezca al usuario autenticado o que el usuario sea administrador.
* Guardar la orden una sola vez después de realizar todas las validaciones.

### Criterios de aceptación

* [x] Cambiar ZIP no modifica `deliveryState`.
* [x] Los campos no permitidos generan `400 Bad Request`.
* [x] Una orden inexistente genera `404 Not Found`.
* [x] Un usuario no puede modificar una orden ajena.
* [x] Una orden inválida no se persiste.

### Pruebas mínimas

* [x] Prueba de regresión del ZIP.
* [x] Prueba de campo prohibido.
* [x] Prueba de ownership y `404`.

### Pregunta para defender la solución

**¿PATCH es “copiar todo lo no nulo” o ejecutar una operación de negocio controlada?**

PATCH debe tratarse como una operación controlada. El cliente solamente debe poder modificar los campos definidos por el contrato del endpoint. Recibir directamente una entidad completa permitiría intentar modificar propiedades que no pertenecen a la operación, como ID, usuario, pago o tacos.

Por esta razón se utiliza un DTO específico que define una lista blanca de campos permitidos.

## Modificaciones y su cumplimiento de los retos

### `OrderDeliveryRequest.java`

Se creó `OrderDeliveryRequest` para reemplazar el uso de `TacoOrder` como cuerpo del PATCH.

```java
@Data
public class OrderDeliveryRequest {

  private String deliveryName;
  private String deliveryStreet;
  private String deliveryCity;
  private String deliveryState;
  private String deliveryZip;

  private final Map<String, Object> unsupportedFields =
      new HashMap<>();

  @JsonAnySetter
  public void addUnsupportedField(
      String name,
      Object value) {

    unsupportedFields.put(name, value);
  }

  public boolean hasUnsupportedFields() {
    return !unsupportedFields.isEmpty();
  }
}
```

El DTO únicamente permite modificar:

```text
deliveryName
deliveryStreet
deliveryCity
deliveryState
deliveryZip
```

Cualquier otra propiedad recibida es almacenada mediante `@JsonAnySetter` y posteriormente provoca una respuesta `400 Bad Request`.

Esto evita que PATCH pueda modificar campos como ID, usuario, datos de pago o tacos.

---

## `OrderApiController.java`

El endpoint ahora recibe:

```java
@RequestBody OrderDeliveryRequest patch
```

en lugar de:

```java
@RequestBody TacoOrder patch
```

Antes de realizar cualquier modificación se comprueba que no existan campos no permitidos:

```java
if (patch.hasUnsupportedFields()) {
  return Mono.just(
      ResponseEntity.badRequest().build());
}
```

Después se busca la orden:

```java
return repo.findById(orderId)
```

Si la orden no existe:

```java
.defaultIfEmpty(
    ResponseEntity.notFound().build());
```

produce:

```text
404 Not Found
```

### Verificación de ownership

Antes de aplicar el PATCH se comprueba si el usuario puede modificar la orden:

```java
if (!canModify(order, authentication)) {
  return Mono.just(
      ResponseEntity
          .status(HttpStatus.FORBIDDEN)
          .<TacoOrder>build());
}
```

El método `canModify()` permite la operación cuando el usuario autenticado es propietario de la orden o posee `ROLE_ADMIN`.

En caso contrario se devuelve:

```text
403 Forbidden
```

---

## Corrección de ZIP

El código original realizaba:

```java
order.setDeliveryZip(
    patch.getDeliveryState());
```

por lo que el ZIP podía tomar el valor del estado.

Se corrigió a:

```java
if (patch.getDeliveryZip() != null) {
  order.setDeliveryZip(
      patch.getDeliveryZip());
}
```

De esta forma `deliveryZip` y `deliveryState` se modifican de manera independiente.

---

## Validación antes de persistir

Después de aplicar los campos permitidos se valida la orden resultante mediante Bean Validation:

```java
Set<ConstraintViolation<TacoOrder>> violations =
    validator.validate(order);

if (!violations.isEmpty()) {
  return Mono.just(
      ResponseEntity
          .badRequest()
          .<TacoOrder>build());
}
```

Si existe alguna violación:

```text
400 Bad Request
```

y `repo.save()` no se ejecuta.

Solamente cuando todas las comprobaciones son correctas se guarda la orden:

```java
return repo.save(order)
    .map(ResponseEntity::ok);
```

Por lo tanto, la persistencia se realiza una sola vez y al final de la operación.

# Pruebas realizadas

## Prueba de regresión del ZIP

Se crea una orden con:

```text
deliveryState = "AGS"
deliveryZip   = "20000"
```

y se modifica únicamente:

```text
deliveryZip = "20230"
```

La prueba comprueba:

```java
assertEquals(
    "20230",
    response.getBody().getDeliveryZip());

assertEquals(
    "AGS",
    response.getBody().getDeliveryState());
```

Esto demuestra que cambiar el ZIP no modifica el estado.

---

## Prueba de campo prohibido

Se intenta agregar un campo fuera de la lista blanca:

```java
patch.addUnsupportedField(
    "ccNumber",
    "4111111111111111");
```

La prueba espera:

```text
400 Bad Request
```

y verifica que no se consulte ni se guarde ninguna orden:

```java
verify(repo, never())
    .findById(anyString());

verify(repo, never())
    .save(any(TacoOrder.class));
```

---

## Prueba de ownership y 404

Se prueban dos casos.

Cuando el usuario autenticado no es propietario de la orden:

```text
403 Forbidden
```

Cuando:

```java
repo.findById("ORDER-MISSING")
```

devuelve:

```java
Mono.empty()
```

la respuesta es:

```text
404 Not Found
```

En ninguno de los dos casos se ejecuta:

```java
repo.save(...)
```

# Cumplimiento del reto

Con los cambios realizados:

* Se corrigió el defecto ZIP/estado.
* PATCH utiliza un DTO específico.
* Sólo se aceptan campos de entrega.
* Los campos prohibidos generan `400`.
* Se valida la orden antes de persistir.
* Una orden inexistente genera `404`.
* Se comprueba ownership o rol administrativo.
* La orden se guarda una sola vez.
* Se implementaron las tres pruebas mínimas solicitadas.
