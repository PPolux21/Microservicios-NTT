# TC-14 — Calcular precios y cantidades del lado servidor

## Descripción del TC

### Resultado funcional

`POST /api/orders` recibe líneas con un taco y una cantidad. El servidor consulta cada ingrediente por ID, suma sus precios actuales, multiplica por la cantidad y persiste `unitPriceAtPurchase`, subtotal, total y moneda. Los importes enviados por el cliente no forman parte del DTO de entrada y no controlan el valor guardado ni la respuesta.

La política elegida es:

```text
precio del taco = suma de unitPrice de sus ingredientes
subtotal = unitPriceAtPurchase × quantity
total = suma de subtotales
```

La moneda es `MXN`, la escala monetaria es 2 y el redondeo es `RoundingMode.HALF_UP`.

### Trabajo solicitado

- Introducir líneas de pedido con taco, cantidad, precio unitario de compra y subtotal.
- Cambiar el contrato de creación a `items:[{taco:{name,ingredientIds},quantity}]`.
- Resolver los ingredientes y sus precios desde el catálogo del servidor.
- Calcular precio del taco, subtotales y total con `BigDecimal`.
- Definir una moneda, escala y modo de redondeo.
- Persistir el precio aplicado como snapshot histórico.
- Limitar la cantidad entre 1 y un máximo configurable.
- Adaptar el carrito para conservar y enviar cantidades sin enviar importes confiables.

### Restricciones técnicas obligatorias

- `unitPriceAtPurchase`, subtotal y total son propiedad del servidor.
- Se usa `BigDecimal`, escala 2 y `RoundingMode.HALF_UP`.
- La moneda persistida es `MXN`.
- El máximo de cantidad se configura mediante `tacocloud.orders.max-quantity` y tiene valor predeterminado 10.
- Los precios se consultan mediante `IngredientRepository`; no se aceptan nombre, tipo o precio de ingrediente aportados por el cliente.
- El flujo compone `Flux` y `Mono` sin `block()` ni `subscribe()` dentro del servicio.
- TC-14 no reserva, descuenta ni libera stock.
- No se implementan cupones, descuentos, impuestos, promociones o reglas de TC-15 y posteriores.

### Criterios de aceptación

- [x] La orden persiste líneas con taco, cantidad, `unitPriceAtPurchase` y subtotal.
- [x] `quantity` debe ser al menos 1.
- [x] Existe un máximo configurable para `quantity`.
- [x] Los precios se resuelven desde el catálogo actual.
- [x] El precio del taco es la suma de los precios de sus ingredientes.
- [x] El subtotal es `unitPriceAtPurchase × quantity`.
- [x] El total es la suma de los subtotales.
- [x] Los cálculos usan `BigDecimal`, escala 2 y `RoundingMode.HALF_UP`.
- [x] La orden conserva la moneda `MXN`.
- [x] Precio de compra, subtotal y total son server-owned.
- [x] Una modificación posterior del catálogo no cambia el snapshot histórico.
- [x] La UI conserva y envía cantidades mayores que uno.
- [x] La UI no envía precio unitario, subtotal ni total.
- [x] No se adelantaron reservas ni concurrencia de inventario de TC-16.

### Pruebas mínimas

- `shouldCalculateDecimalPricesAndQuantityOnServer` usa precios sintéticos `0.10` y `0.235`. TC-13 normaliza el segundo a `0.24`; TC-14 obtiene precio unitario `0.34` y subtotal/total `0.68` para cantidad 2. El JSON intenta enviar `0.01` y `0.02`, pero la orden y la respuesta conservan los importes del servidor.
- `shouldKeepHistoricalPriceSnapshotAfterCatalogChange` crea la orden con precio `1.25`, cambia después el ingrediente a `9.99` y comprueba que el snapshot sigue en `1.25` y el subtotal en `2.50`.
- `shouldRejectZeroNegativeAndExcessiveQuantities` comprueba 0, -1 y un valor superior al máximo configurado, todos como 422 mediante el formato funcional de TC-09.
- `shouldIgnoreServerOwnedFields` verifica en el límite DTO que `total`, `unitPriceAtPurchase` y subtotal no pasan al comando ni a la entidad.
- `should preserve and send a cart quantity greater than one` comprueba en Angular que el carrito conserva cantidad 2, envía IDs de ingredientes y no envía importes.

## Cambios de código

### `TacoOrder.java`

Se añadió `OrderItem` como clase pequeña anidada para evitar otro archivo de dominio. La línea contiene el taco resuelto, cantidad, precio unitario aplicado y subtotal. La orden persiste además total y moneda. `tacos` se conserva para compatibilidad con los flujos previos de correo y cocina, mientras que `items` es la fuente del cálculo monetario en las nuevas órdenes API.

```java
private List<OrderItem> items = new ArrayList<>();
private BigDecimal total = BigDecimal.ZERO.setScale(2);
private String currency = "MXN";

@Data
@NoArgsConstructor
@AllArgsConstructor
public static class OrderItem implements Serializable {
  private Taco taco;

  @Min(1)
  private int quantity;

  private BigDecimal unitPriceAtPurchase;
  private BigDecimal subtotal;
}
```

### `ApiDtos.java`

El request ahora representa exactamente `items`, y el taco sólo permite nombre e IDs de ingredientes. Los DTO de entrada no declaran campos monetarios, de modo que Jackson ignora esos intentos según la estrategia establecida en TC-08. La respuesta incorpora líneas calculadas, total y moneda.

```java
public static class OrderItemRequest {
  @Valid
  @NotNull(message="taco is required")
  private OrderTacoRequest taco;

  @NotNull(message="quantity is required")
  @Min(value=1,message="quantity must be at least 1")
  private Integer quantity;
}

public static class OrderItemResponse {
  private OrderTacoResponse taco;
  private int quantity;
  private BigDecimal unitPriceAtPurchase;
  private BigDecimal subtotal;
}
```

### `OrderService.java`

El servicio reutiliza `IngredientRepository` y compone la resolución de ingredientes con `concatMap`. Valida la cantidad contra el máximo configurable, exige catálogo disponible con precio válido y realiza todos los cálculos monetarios. No lee stock ni lo modifica.

```java
private static final int MONEY_SCALE = 2;
private static final RoundingMode MONEY_ROUNDING = RoundingMode.HALF_UP;
private static final String ORDER_CURRENCY = "MXN";

@Value("${tacocloud.orders.max-quantity:10}")
void configureMaxQuantity(int maxQuantity) {
  this.maxQuantity = maxQuantity;
}
```

```java
BigDecimal unitPrice = ingredients.stream()
    .map(Ingredient::getUnitPrice)
    .reduce(BigDecimal.ZERO,BigDecimal::add)
    .setScale(MONEY_SCALE,MONEY_ROUNDING);

BigDecimal subtotal = unitPrice
    .multiply(BigDecimal.valueOf(quantity))
    .setScale(MONEY_SCALE,MONEY_ROUNDING);
```

El total se obtiene únicamente de las líneas calculadas:

```java
BigDecimal total = BigDecimal.ZERO.setScale(MONEY_SCALE);
for (OrderItem item : items) {
  order.addItem(item);
  total = total.add(item.getSubtotal());
}
order.setTotal(total.setScale(MONEY_SCALE,MONEY_ROUNDING));
```

## Resultado

TC-14 queda implementado con cantidades reales y precios calculados exclusivamente en servidor. Las líneas persisten el snapshot de precio, la respuesta expone subtotales y total en MXN, y la UI envía sólo los datos permitidos. Las pruebas focalizadas backend y Angular pasan, al igual que la compilación completa del reactor. La selección amplia de pruebas API conserva seis fallos preexistentes en fixtures aislados de `ApiExceptionHandlerTest` e `IngredientControllerTest`, donde errores esperados 400/404 se convierten en 500 por no registrar correctamente el advice. La ejecución Maven completa con dependencias también se detiene antes de la API por dos errores preexistentes de `RegistrationControllerTest` y `SecurityConfigTest`. Las pruebas nuevas de TC-14 y las regresiones directamente afectadas finalizan correctamente.
