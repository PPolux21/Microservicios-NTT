# TC-03 Construir Location sin localhost ni rutas rotas

## Requisitos del proyecto

### Trabajo solicitado

* Eliminar la URI hardcodeada `http://localhost:8080/ingredients/...`.
* Construir `Location` a partir de la petición actual y la ruta real `/api/ingredients/{id}`.
* Devolver `201 Created` con la entidad creada y el header `Location`.
* Validar el cuerpo antes de persistir.

### Restricciones técnicas obligatorias

* La URI debe respetar host, puerto, esquema y context path de la petición.
* No concatenar strings para formar el URL completo.
* El identificador usado debe ser el asignado por persistencia.

### Criterios de aceptación

* [x] La respuesta contiene `Location` resoluble mediante GET.
* [ ] La prueba funciona con puerto aleatorio.
* [x] No queda ninguna referencia a `localhost:8080` en el controlador.
* [x] Un body inválido no se guarda.

### Pruebas mínimas

* [x] Prueba con `WebTestClient` que inspeccione `Location`.
* [x] Prueba que siga `Location` y obtenga `200`.
* [x] Prueba de validación `400`.

### Pregunta para defender la solución

**¿Por qué una URL absoluta hardcodeada funciona en la laptop y falla en un ingress o reverse proxy?**

Una URL absoluta hardcodeada queda asociada directamente al entorno en el que fue escrita. Por ejemplo, `http://localhost:8080` solamente representa correctamente una aplicación ejecutándose localmente en el puerto 8080.

Cuando la aplicación se despliega en otro entorno, puede utilizar otro host, puerto, esquema o context path. Por ejemplo, una aplicación podría ejecutarse internamente en HTTP y ser accedida externamente mediante HTTPS a través de un reverse proxy.

Por esta razón, la URI utilizada en el header `Location` debe construirse a partir de la petición recibida, en lugar de depender de valores escritos manualmente en el controlador.

## Modificaciones y su cumplimiento de los retos

Para completar TC-03 se modificó el método `postIngredient()` de [`IngredientController.java`](../../tacocloud-api/src/main/java/tacos/web/api/IngredientController.java) y se agregaron las pruebas correspondientes en [`IngredientControllerTest.java`](../../tacocloud/tacocloud-api/src/test/java/tacos/web/api/IngredientControllerTest.java).

## `IngredientController.java`

### Antes de la modificación

Originalmente, el endpoint de creación guardaba correctamente el ingrediente mediante el repositorio reactivo, pero construía manualmente el header `Location` utilizando una dirección fija:

```java
@PostMapping
public Mono<ResponseEntity<Ingredient>> postIngredient(@Valid @RequestBody Ingredient ingredient, HttpServletRequest request) {

  return repo.save(ingredient)
    .map(savedIngredient -> {
      URI location = ServletUriComponentsBuilder
        .fromRequestUri(request)
        .pathSegment(savedIngredient.getId())
        .build()
        .toUri();
      return ResponseEntity
        .created(location)
        .body(savedIngredient);
    });
}
```

El principal problema se encontraba en:

```java
URI.create(
    "http://localhost:8080/ingredients/"
    + i.getId())
```

Esta URI estaba asociada directamente al entorno local y además utilizaba `/ingredients/{id}` en lugar de la ruta real de la API:

```text
/api/ingredients/{id}
```

### Después de la modificación

El método fue reemplazado por:

```java
@PostMapping
public Mono<ResponseEntity<Ingredient>> postIngredient(
    @Valid @RequestBody Ingredient ingredient,
    HttpServletRequest request) {

  return repo.save(ingredient)
      .map(savedIngredient -> {

        URI location = ServletUriComponentsBuilder
            .fromRequestUri(request)
            .pathSegment(savedIngredient.getId())
            .build()
            .toUri();

        return ResponseEntity
            .created(location)
            .body(savedIngredient);
      });
}
```

### Cambios realizados

El primer cambio consiste en eliminar completamente:

```java
"http://localhost:8080/ingredients/"
```

y utilizar como base la petición HTTP recibida:

```java
ServletUriComponentsBuilder
    .fromRequestUri(request)
```

De esta manera, el controlador ya no contiene un host, puerto o esquema escritos manualmente.

Posteriormente se agrega únicamente el identificador del ingrediente:

```java
.pathSegment(savedIngredient.getId())
```

Si la petición se realiza a:

```text
/api/ingredients
```

la URI resultante tendrá la forma:

```text
/api/ingredients/{id}
```

También se utiliza:

```java
savedIngredient.getId()
```

en lugar de obtener directamente el identificador del objeto recibido.

Esto es importante porque `savedIngredient` representa el objeto emitido por:

```java
repo.save(ingredient)
```

por lo que la construcción de `Location` utiliza el resultado de la operación de persistencia.

Finalmente:

```java
ResponseEntity
    .created(location)
    .body(savedIngredient);
```

crea una respuesta:

```text
201 Created
```

incluyendo automáticamente:

```text
Location: URI_GENERADA
```

y utilizando como cuerpo la entidad guardada.

La operación continúa formando parte de la misma cadena reactiva:

```java
repo.save(ingredient)
    .map(...)
```

sin utilizar llamadas manuales a:

```java
subscribe()
```

o:

```java
block()
```

# Pruebas de `IngredientController`

Las pruebas correspondientes a TC-03 fueron agregadas dentro de `IngredientControllerTest.java`.

Las dos primeras pruebas utilizan:

```java
MockMvcWebTestClient.bindToController(...)
```

debido a que el controlador recibe:

```java
HttpServletRequest
```

como argumento.

`MockMvcWebTestClient` mantiene la interfaz de `WebTestClient`, pero ejecuta las peticiones utilizando la infraestructura MVC necesaria para proporcionar correctamente un `HttpServletRequest` al controlador.

---

## Prueba 1 — Inspeccionar el header Location

La primera prueba comprueba que la creación de un ingrediente produzca una respuesta `201 Created` y que el header `Location` apunte a la ruta correspondiente al ingrediente creado.

```java
@Test
public void shouldReturnLocationWhenCreatingIngredient() {
  IngredientRepository ingredientRepo = Mockito.mock(IngredientRepository.class);
  Ingredient testIngredient = new Ingredient("FLTO", "Flour Tortilla", Type.WRAP);

  when(ingredientRepo.save(any(Ingredient.class))).thenReturn(Mono.just(testIngredient));

  WebTestClient testClient = MockMvcWebTestClient.bindToController(
    new IngredientController(ingredientRepo)).build();

  testClient.post()
    .uri("/api/ingredients")
    .contentType(MediaType.APPLICATION_JSON)
    .bodyValue(testIngredient)
    .exchange()
    .expectStatus().isCreated()
    .expectHeader().value(
      "Location",
      location -> assertTrue(
        location.endsWith(
          "/api/ingredients/FLTO")));

  Mockito.verify(
    ingredientRepo,
    Mockito.times(1))
    .save(any(Ingredient.class));
}
```

La verificación:

```java
.expectStatus().isCreated()
```

demuestra que el contrato HTTP devuelve:

```text
201 Created
```

mientras que:

```java
.expectHeader().value(
    "Location",
    location -> assertTrue(
        location.endsWith(
            "/api/ingredients/FLTO")))
```

comprueba que la URI producida termina en:

```text
/api/ingredients/FLTO
```

Por lo tanto, ya no se depende de:

```text
http://localhost:8080
```

ni de una ruta fija incorrecta.

Finalmente:

```java
Mockito.verify(
    ingredientRepo,
    Mockito.times(1))
    .save(any(Ingredient.class));
```

comprueba que la creación ejecutó exactamente una operación de persistencia.

## Prueba 2 — Seguir Location y obtener 200

La segunda prueba comprueba que el valor generado en `Location` no solamente tenga la forma correcta, sino que pueda utilizarse posteriormente para consultar el ingrediente mediante `GET`.

```java
@Test
public void shouldFollowLocationAndReturnCreatedIngredient() {
  IngredientRepository ingredientRepo = Mockito.mock(IngredientRepository.class);
  Ingredient testIngredient = new Ingredient("FLTO", "Flour Tortilla", Type.WRAP);

  when(ingredientRepo.save(any(Ingredient.class))).thenReturn(Mono.just(testIngredient));
  when(ingredientRepo.findById("FLTO")).thenReturn(Mono.just(testIngredient));

  WebTestClient testClient = MockMvcWebTestClient.bindToController(
          new IngredientController(ingredientRepo)).build();

  EntityExchangeResult<Ingredient> postResult =
    testClient.post()
      .uri("/api/ingredients")
      .contentType(MediaType.APPLICATION_JSON)
      .bodyValue(testIngredient)
      .exchange()
      .expectStatus().isCreated()
      .expectHeader().exists("Location")
      .expectBody(Ingredient.class)
      .returnResult();

  URI location = postResult.getResponseHeaders().getLocation();

  assertNotNull(location);

  testClient.get()
    .uri(location.getPath())
    .exchange()
    .expectStatus().isOk()
    .expectBody(Ingredient.class)
    .value(ingredient -> {
      assertEquals(
        "FLTO",
        ingredient.getId());

      assertEquals(
        "Flour Tortilla",
        ingredient.getName());
    });

  Mockito.verify(ingredientRepo).save(any(Ingredient.class));
  Mockito.verify(ingredientRepo).findById("FLTO");
}
```

En primer lugar se realiza:

```text
POST /api/ingredients
```

y se recupera el header generado por el controlador:

```java
URI location =
    postResult.getResponseHeaders().getLocation();
```

Posteriormente se obtiene la ruta de esa URI:

```java
location.getPath()
```

y se utiliza directamente para realizar:

```java
testClient.get()
    .uri(location.getPath())
```

El resultado esperado es:

```text
200 OK
```

Esto demuestra el siguiente flujo:

```text
POST /api/ingredients
        │
        ▼
201 Created
        │
        ▼
Location: .../api/ingredients/FLTO
        │
        ▼
GET /api/ingredients/FLTO
        │
        ▼
200 OK
```

Por lo tanto, `Location` representa un recurso que puede ser consultado posteriormente mediante el endpoint correspondiente.

Las verificaciones:

```java
Mockito.verify(ingredientRepo)
    .save(any(Ingredient.class));

Mockito.verify(ingredientRepo)
    .findById("FLTO");
```

también comprueban que durante el flujo se ejecutó tanto la creación como la consulta posterior.

## Prueba 3 — Validación 400

Finalmente se agregó una prueba para comprobar el comportamiento ante un cuerpo HTTP inválido.

```java
@Test
public void shouldReturnBadRequestWhenIngredientBodyIsInvalid() {
  IngredientRepository ingredientRepo = Mockito.mock(IngredientRepository.class);
  
  WebTestClient testClient = WebTestClient.bindToController(new IngredientController(ingredientRepo)).build();

  String invalidIngredient =
    "{"
    + "\"id\":\"BAD\","
    + "\"name\":\"Invalid Ingredient\","
    + "\"type\":\"INVALID_TYPE\""
    + "}";

  testClient.post()
    .uri("/api/ingredients")
    .contentType(MediaType.APPLICATION_JSON)
    .bodyValue(invalidIngredient)
    .exchange()
    .expectStatus().isBadRequest();

  Mockito.verify(ingredientRepo,Mockito.never()).save(any(Ingredient.class));
}
```

En este caso se utiliza:

```json
{
  "id": "BAD",
  "name": "Invalid Ingredient",
  "type": "INVALID_TYPE"
}
```

El valor:

```text
INVALID_TYPE
```

no corresponde con ninguno de los valores permitidos por el enum `Ingredient.Type`.

Por ello, Spring no puede construir correctamente el objeto `Ingredient` y la petición es rechazada con:

```text
400 Bad Request
```

La verificación:

```java
Mockito.verify(
    ingredientRepo,
    Mockito.never())
    .save(any(Ingredient.class));
```

demuestra además que una petición inválida es rechazada antes de producir una operación de persistencia.

# Cumplimiento del reto

Con los cambios realizados se consiguió:

* Eliminar la URI absoluta `http://localhost:8080/ingredients/...` del controlador.
* Construir `Location` a partir de la petición HTTP recibida.
* Utilizar la ruta real `/api/ingredients/{id}`.
* Utilizar el identificador contenido en el objeto emitido por `repo.save()`.
* Responder con `201 Created`.
* Incluir automáticamente el header `Location`.
* Mantener la escritura dentro de la cadena reactiva retornada.
* Comprobar mediante `WebTestClient` el contenido de `Location`.
* Comprobar que `Location` permite realizar posteriormente un `GET` con respuesta `200 OK`.
* Comprobar que un cuerpo HTTP inválido produce `400 Bad Request`.
* Comprobar que una petición inválida no ejecuta `repo.save()`.

El criterio de prueba con puerto aleatorio no fue implementado, ya que las pruebas realizadas utilizan un entorno MVC simulado mediante `MockMvcWebTestClient.bindToController(...)` en lugar de iniciar la aplicación mediante `@SpringBootTest(webEnvironment = RANDOM_PORT)`.
