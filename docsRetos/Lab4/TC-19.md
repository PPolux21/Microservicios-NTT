# TC-19 — Buscar, filtrar, ordenar y paginar tacos

## Descripción del TC

### Resultado funcional

`GET /api/tacos` devuelve ahora una página de tacos y admite filtros opcionales por nombre, ingrediente, clasificación dietaria, alérgeno excluido y nivel exacto de picante. MongoDB realiza el filtrado, el ordenamiento, el offset y el límite; la API devuelve metadata de navegación y la UI consume este nuevo contrato.

### Trabajo solicitado

- Incorporar filtros opcionales y combinables en `GET /api/tacos`.
- Ejecutar filtros, sort y paginación dentro de MongoDB.
- Limitar y escapar la búsqueda textual.
- Validar page, size y una lista blanca de sort.
- Devolver `items`, `page`, `size`, `totalElements` y `totalPages`.
- Mantener un orden secundario estable por identificador.
- Consumir la metadata dietaria de TC-17 sin aceptar clasificación del cliente.
- Corregir la UI para utilizar `/api/tacos` y el response paginado.
- Crear y comprobar índices relacionados únicamente con el catálogo.

### Restricciones técnicas obligatorias

- No se usa `findAll()` seguido de filtros, `skip` o `take` en Java.
- Todos los criterios independientes se combinan con AND.
- La regex se construye con `Pattern.quote` y el nombre se limita a 50 caracteres.
- El máximo de página proviene de `tacocloud.search.max-page-size`.
- Los únicos campos de sort aceptados son `createdAt`, `name` e `id`.
- Cuando el campo principal no es `id`, se añade `id ASC` como desempate.
- No se añadieron `block()` ni `subscribe()` en servicios o repositorios.
- Los índices se crean de forma reactiva una sola vez y sólo sobre la colección `taco`.
- No se implementó cursor paging ni funcionalidad de TC-20 o posteriores.

La clasificación sigue usando la metadata de los ingredientes persistidos dentro del diseño. La consulta Mongo traduce exactamente las políticas de TC-17: una etiqueta dietaria exige que ningún ingrediente carezca de ella, los alérgenos se excluyen si cualquiera los contiene y el picante exacto requiere ese nivel sin que exista otro superior. La respuesta se construye mediante `TacoClassificationService.classifyIngredients`, por lo que la representación pública mantiene una única implementación de clasificación.

## Cambios de código

### `TacoSearchRepository.java`

Define el fragmento custom, el query interno ya normalizado y el resultado de página. Mantiene el contrato de datos junto, evitando archivos para cada criterio.

```java
Mono<TacoSearchPage> search(TacoSearchQuery query);
```

### `TacoSearchRepositoryImpl.java`

Construye una lista pequeña de `Criteria`, la combina mediante `andOperator`, aplica sort seguro, desempate, `skip` y `limit`, y obtiene el total con `count()`.

```java
pageQuery.with(Sort.by(direction, search.getSortField()));
if (!"id".equals(search.getSortField())) {
  pageQuery.with(Sort.by(Sort.Direction.ASC, "id"));
}
pageQuery.skip((long) search.getPage() * search.getSize())
    .limit(search.getSize());
```

La búsqueda textual no interpreta patrones del cliente:

```java
Pattern safeName = Pattern.compile(
    Pattern.quote(search.getName()),
    Pattern.CASE_INSENSITIVE | Pattern.UNICODE_CASE);
```

Los índices se inicializan mediante un `Mono<Void>` cacheado que forma parte del primer flujo de búsqueda. No se usan suscripciones manuales y no se propagan índices a `TacoOrder` aunque `Taco` esté embebido allí.

### `TacoRepository.java`

Extiende `TacoSearchRepository` además de `ReactiveCrudRepository`; no se creó un segundo repositorio de tacos.

### `TacoController.java`

Reemplaza el handler especial `params="recent"` por un GET paginado general. Normaliza filtros, convierte los enums de TC-17, valida el máximo configurable y protege el sort con una lista blanca.

```java
private static final Set<String> SORT_FIELDS =
    new LinkedHashSet<>(Arrays.asList("createdAt", "name", "id"));
```

Los errores funcionales usan los códigos `PAGE_SIZE_EXCEEDED`, `INVALID_SORT`, `INVALID_DIET`, `INVALID_ALLERGEN` e `INVALID_SPICE`, compatibles con el manejo de TC-09.

### `ApiDtos.java`

Añade `TacoSearchQuery` para binding y validación de parámetros, y `TacoSearchResponse` para la página. Los valores predeterminados son page 0, size 20 y `createdAt,desc`.

### `ApiMapper.java`

Convierte sólo los elementos de la página y reutiliza `TacoClassificationService` para generar la clasificación pública y el disclaimer de TC-17.

### `application.yml`

Externaliza el máximo permitido:

```yaml
tacocloud:
  search:
    max-page-size: 50
```

### `RecentTacosService.ts`

Construye parámetros URL codificados, consulta `/api/tacos` y transforma la respuesta HTTP a la página JSON.

```typescript
getRecentTacos() {
  return this.search({page: 0, size: 12, sort: 'createdAt,desc'});
}
```

### `recents.component.ts`

El componente deja de realizar una llamada HTTP paralela y consume el único servicio, asignando `page.items` a la vista existente.

### `TacoSearchMongoIntegrationTest.java`

Inserta cinco tacos sintéticos, ejecuta el repositorio custom contra Mongo y comprueba resultados exactos, metadata e índices.

### `TacoControllerTest.java` y `app.component.spec.ts`

Prueban el contrato de entrada/salida, las validaciones de seguridad del sort/paginación y la ruta usada por la UI.

## Cambios que no se realizaron

- TC-20: no se implementó taco del día, recomendación, `Clock` ni cache diaria.
- TC-21: no se implementaron favoritos.
- TC-22: no se implementaron calificaciones, ranking ni agregaciones.
- No se implementó cursor paging, fuzzy search, text index, Elasticsearch ni un framework genérico de filtros.
- No se modificaron las reglas de validación de diseños de TC-18.
- No se cambió la autorización de endpoints de escritura.

Offset paging con `page/size` es suficiente para el alcance académico de TC-19 y simplifica la navegación de la UI. Su limitación es que, si se insertan documentos entre dos solicitudes, los offsets pueden desplazarse y causar duplicados u omisiones. Un cursor basado en `createdAt + id` sería más estable para un catálogo con cambios frecuentes. Este TC conserva un solo modelo, offset, pero garantiza un orden determinista sobre el dataset observado mediante el campo principal y `id` como desempate.

| Requisito | Implementación |
| --- | --- |
| Búsqueda por nombre | Regex escapada y limitada en `TacoSearchRepositoryImpl` |
| Filtro ingredientId | `Criteria` sobre `ingredients.id` |
| Filtro diet | Política de todos los ingredientes de TC-17 traducida a Mongo |
| Excluir allergen | Ausencia de `elemMatch` con el alérgeno solicitado |
| Filtro spice | Nivel exacto y ausencia de niveles superiores |
| Filtros combinados | `Criteria.andOperator(...)` |
| Page/size | `TacoSearchQuery` + `skip/limit` |
| Tamaño máximo | `tacocloud.search.max-page-size` + `PAGE_SIZE_EXCEEDED` |
| Sort seguro | Whitelist en `TacoController` |
| Paginación estable | Sort principal + `id ASC` |
| Metadata de página | `TacoSearchResponse` |
| Regex segura | `Pattern.quote` + `@Size(max=50)` |
| No filtrar en memoria | `ReactiveMongoTemplate.find/count` |
| Índices | Inicialización reactiva cacheada sobre seis campos de `taco` |
| Ruta correcta UI | `RecentTacosService` usa `/api/tacos` |
| Integración real | `TacoSearchMongoIntegrationTest` con Mongo embebido |

## Resultado

TC-19 queda implementado con filtros opcionales y combinables ejecutados completamente en MongoDB, paginación offset validada, sort restringido y orden estable. La clasificación expuesta conserva las reglas de TC-17, la UI consume el contrato paginado y las pruebas reales demuestran consultas, metadata e índices sin cargar el catálogo completo en memoria.
