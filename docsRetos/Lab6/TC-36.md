# TC-36 — Suite de integración que detenga regresiones reales

## Descripción del TC

### Resultado funcional

La red de seguridad combina pruebas unitarias rápidas, integración real con
MongoDB/RabbitMQ y contratos HTTP/JSON/OpenAPI. El runtime principal se prueba
en puerto aleatorio mediante `WebTestClient`; Testcontainers suministra un
Mongo replica set y RabbitMQ sin depender de servicios instalados.

### Archivos modificados o creados

  smoke test convertido en regresión HTTP de runtime real.
- `tacocloud/tacocloud/src/test/java/tacos/DesignTacoControllerWebTest.java`:

  espera determinista con Reactor y condición observable del broker.

### Trabajo solicitado

Se auditó `src/test`, los POM, perfiles, dependencias y pruebas existentes. Se
reutilizaron las suites de TC-01 a TC-35 y sólo se amplió el test del ensamblado
final para cubrir los huecos HTTP reales. La integración Rabbit existente se
hizo determinista sin `Thread.sleep`.

Se revisaron las secciones §8, §9, §11 y §12 del manual y la documentación de
TC-01, TC-02, TC-04, TC-06, TC-07, TC-10, TC-11, TC-12, TC-29, TC-30 y TC-34;
como dependencias concretas también TC-08, TC-09, TC-16, TC-25, TC-27, TC-28,
TC-31 y TC-35.

### Restricciones técnicas obligatorias

- JUnit 5, Spring Test, Reactor Test y Testcontainers ya gestionados por Maven.
- `@SpringBootTest(webEnvironment = RANDOM_PORT)` con cliente HTTP real.
- MongoDB `mongo:6.0.14` en replica set mediante `getReplicaSetUrl`.
- RabbitMQ `rabbitmq:3.12-alpine`, el broker ya elegido en TC-30.
- Datos sintéticos, limpieza antes de cada escenario y propiedades dinámicas.
- Ningún Mongo o broker instalado localmente y ningún `subscribe()` manual para
  disparar efectos.

### Criterios de aceptación

Cada regresión obligatoria tiene al menos una prueba que falla si desaparece su
garantía. Los escenarios críticos usan infraestructura real donde importa:
persistencia, transacciones, índices, HTTP, seguridad, redelivery y DLQ. Maven
es la única entrada para local y CI.

### Pruebas mínimas

- Unitarias: pricing, workflow, hashing, mappers y validadores existentes.
- Runtime HTTP: ingrediente PUT/DELETE, PATCH de orden, registro, seguridad e
  idempotencia secuencial/concurrente.
- Mongo: outbox transaccional/rollback/recovery e idempotencia con índice único.
- RabbitMQ: entrega duplicada, retry, rollback, DLQ y replay.
- Contratos: `OrderEvent`, DTOs seguros, `ApiProblem` y OpenAPI v1.

## Cambios de código

`TacoCloudApplicationTests` conserva el nombre del smoke test existente, pero
ahora levanta la aplicación real con `RANDOM_PORT`, conecta un `WebTestClient`
al servidor y usa Mongo Testcontainers. Prueba efectos persistidos mediante
HTTP y autentica usuarios sintéticos a través de la cadena de seguridad real.

`RabbitOrderConsumerIntegrationTest` reemplaza sleeps/polling bloqueante por un
polling reactivo acotado con `StepVerifier`, ejecutado en `boundedElastic` para
las consultas bloqueantes del cliente de prueba. Antes del replay verifica la
profundidad de la DLQ, haciendo observable la precondición sin temporizadores
arbitrarios.

Las pruebas del ensamblado detectaron cinco defectos de producción que impedían
el runtime real: binding de fechas ISO dependiente del locale, constructor
ambiguo de `OutboxPublisher`, reconstrucción Mongo ambigua de `PaymentMethod` y
falta de un log seguro para errores inesperados, además de una llamada obsoleta
del módulo web al repositorio de órdenes. Se corrigieron en el punto mínimo, sin
cambiar contratos funcionales.

El workflow de GitHub Actions usa Java 11, ejecuta `mvn --batch-mode clean
verify` con Docker disponible y publica reportes Surefire/Failsafe incluso ante
fallos.

## Cambios que no se realizaron

No se buscó 100 % de coverage.

No se agregaron tests triviales para getters/setters.

No se probaron los tres brokers end-to-end; sólo RabbitMQ, seleccionado en
TC-30.

No se instaló Mongo o broker localmente.

No se añadió infraestructura de reporting/coverage innecesaria.

No se creó un framework de testing personalizado, módulo de pruebas, DSL,
fixtures globales, Allure, Sonar, JaCoCo, Awaitility, Cucumber ni pruebas de
carga.

¿Qué prueba habría detectado cada defecto original antes de la demo?

| Defecto | Prueba que lo detecta |
| --- | --- |
| `repo.save()` descartado | PUT HTTP + GET con Mongo real |
| `deleteById()` descartado | DELETE HTTP + GET 404 con Mongo real |
| PATCH cruza ZIP/state o permite campos internos | PATCH real y contratos negativos |
| Publisher frío o doble suscripción de email | `EmailOrderServiceTest` con `StepVerifier` |
| Password en claro | registro HTTP + `PasswordEncoder.matches` |
| `permitAll` accidental | accesos anónimo/USER rechazados en runtime real |
| PAN/CVV/password expuestos | contratos JSON y respuesta HTTP negativa |
| Order guardada sin intención de envío | transacción Order + Outbox y rollback real |
| Redelivery duplica efecto | mismo `eventId` dos veces en RabbitMQ real |
| Doble `Idempotency-Key` crea dos órdenes | dos requests HTTP concurrentes + conteos Mongo |
| OpenAPI diverge del runtime | `OpenApiContractTest` |

Una prueba unitaria verifica una regla aislada y da diagnóstico rápido; una de
integración comprueba colaboración real con Spring, Mongo o broker; una de
contrato fija la forma/semántica observable de HTTP, JSON, eventos u OpenAPI.
Cada test se conserva cuando protege un riesgo distinto, usa la fidelidad de
infraestructura necesaria y produce un fallo que señala la garantía rota.

## Resultado

El comando completo es:

```shell
cd tacocloud
mvn clean verify
```

Subconjuntos útiles:

```shell
mvn -pl tacocloud -am -Dtest=TacoCloudApplicationTests -Dsurefire.failIfNoSpecifiedTests=false test
mvn -pl tacocloud-api -am -Dtest=OutboxMongoIntegrationTest,OrderIdempotencyMongoIntegrationTest -Dsurefire.failIfNoSpecifiedTests=false test
mvn -pl tacocloud-kitchen -am -Dtest=RabbitOrderConsumerIntegrationTest -Dsurefire.failIfNoSpecifiedTests=false test
mvn -pl tacocloud-messaging-contract,tacocloud-api -am -Dtest=OrderEventContractTest,DtoContractTest,OpenApiContractTest -Dsurefire.failIfNoSpecifiedTests=false test
```

Los reportes se generan en `*/target/surefire-reports/`; CI también conserva
`*/target/failsafe-reports/` si aparecen. Los contenedores y propiedades se
crean desde las pruebas, por lo que el build no depende de `localhost`, `.env`,
datos previos, IDE ni servicios manuales.

La ejecución final produjo 49 reportes con 388 tests, 0 fallos, 0 errores y 0
omitidos. Los 17 módulos finalizaron en `BUILD SUCCESS`.

Tests existentes reutilizados: suites unitarias, Mongo, seguridad, contratos y
RabbitMQ de TC-01 a TC-35.

Tests nuevos realmente necesarios: ninguno como clase adicional; se amplió el
smoke test del ensamblado final con cinco escenarios críticos.

Fixtures reutilizados: repositorios, DTOs, `WebTestClient`, usuarios y builders
locales existentes.

Fixtures nuevos: helpers privados mínimos dentro del smoke test, sin fixture
global.

Containers reutilizados: Mongo replica set y RabbitMQ con las mismas imágenes
de TC-29/TC-30.

Containers nuevos: ninguno distinto.

Dependencias nuevas: sólo `junit-jupiter` y `mongodb` de Testcontainers en el
módulo ensamblador, ya versionadas por el BOM padre.

Infraestructura que se decidió NO añadir: framework/DSL de pruebas, módulo de
testing, Awaitility, cobertura, reporting externo o un segundo broker E2E.

Código productivo modificado: únicamente las cinco correcciones reales de
arranque/persistencia/diagnóstico indicadas arriba.

Retos posteriores no implementados: ninguno; TC-36 cierra el bloque actual.
