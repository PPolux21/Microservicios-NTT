# TC-10 — Registro reactivo con contraseñas protegidas

## Requisitos del proyecto

### Trabajo solicitado

El reto solicita corregir el proceso de registro de usuarios para garantizar que la contraseña nunca sea almacenada en texto plano y que la persistencia reactiva forme parte realmente del flujo ejecutado.

También requiere controlar la unicidad de `username` y `email` tanto mediante una comprobación previa como mediante restricciones de persistencia capaces de proteger frente a condiciones de carrera.

Los objetivos principales son:

- Reemplazar `NoOpPasswordEncoder` por `PasswordEncoderFactories.createDelegatingPasswordEncoder()`.
- Componer el `userRepo.save(...)` dentro del flujo reactivo del registro.
- Validar la unicidad de `username` y `email`.
- Proteger esa unicidad mediante índices únicos de MongoDB.
- No devolver ni registrar la contraseña o su hash.
- Generar la redirección del registro únicamente después de que la persistencia termine correctamente.
- Convertir intentos de registro duplicados en HTTP `409 Conflict`.

### Restricciones técnicas obligatorias

El hash almacenado debe incluir un identificador de algoritmo, por ejemplo:

```text id="37akbj"
{bcrypt}$2a$...
```

La contraseña en texto plano sólo existe durante la recepción y transformación de la solicitud.

La protección frente a duplicados no puede depender únicamente de:

```text id="o7mt7d"
buscar → si no existe → guardar
```

porque dos solicitudes concurrentes podrían superar simultáneamente la comprobación.

La base de datos debe actuar como última garantía mediante índices únicos.

No deben utilizarse:

```java id="7ba4s4"
subscribe()
block()
```

dentro del flujo de registro.

### Criterios de aceptación

- [x] La contraseña persistida es diferente de la contraseña ingresada.
- [x] `PasswordEncoder.matches(...)` reconoce correctamente la contraseña original.
- [x] El hash incluye el identificador del algoritmo delegado.
- [x] El usuario guardado queda disponible para el mecanismo de autenticación existente.
- [x] Username o email duplicados producen conflicto.
- [x] La condición de carrera queda protegida por índices únicos.
- [x] `userRepo.save(...)` forma parte del publisher retornado.
- [x] No existe un publisher de persistencia descartado.
- [x] La redirección ocurre solamente después de completar `save()`.

### Pruebas mínimas

Se implementaron las tres categorías requeridas:

1. Prueba del encoder y del hash.
2. Prueba de persistencia/reactividad.
3. Prueba de duplicado y `DuplicateKeyException` traducida a conflicto.

> **Pregunta para defender la solución**
>
> ¿Por qué “cifrar” contraseñas no es la meta y sí lo es aplicar hash adaptativo con salt?
>
> Una contraseña no necesita ser recuperada después de almacenarse. Por ello no conviene utilizar cifrado reversible, ya que quien obtuviera la clave podría recuperar todas las contraseñas.
>
> Para autenticación solamente se necesita comprobar que una contraseña ingresada corresponde al valor almacenado. Un algoritmo de hash adaptativo como bcrypt incorpora salt y un costo computacional configurable, dificultando ataques de diccionario y fuerza bruta.
>
> Spring Security realiza la comprobación mediante:
>
> ```java id="de5lkr"
> passwordEncoder.matches(
>     rawPassword,
>     storedHash);
> ```
>
> sin recuperar nunca la contraseña original.

# `SecurityConfig.java`

## Sustitución de `NoOpPasswordEncoder`

El proyecto original utilizaba:

```java id="9b16en"
NoOpPasswordEncoder
```

lo cual provocaba que la contraseña pudiera almacenarse sin protección.

TC-10 reemplaza ese encoder por:

```java id="3wl3lc"
PasswordEncoderFactories
    .createDelegatingPasswordEncoder();
```

El nuevo encoder almacena hashes con un identificador de algoritmo.

Por ejemplo:

```text id="8dmgr7"
{bcrypt}$2a$10$...
```

Esto permite que Spring Security pueda determinar qué algoritmo debe utilizar al verificar una contraseña.

El flujo pasa de:

```text id="ar0i02"
password
   ↓
NoOpPasswordEncoder
   ↓
"secretPassword"
```

a:

```text id="43nsuf"
password
   ↓
DelegatingPasswordEncoder
   ↓
{bcrypt}$2a$...
```

### Compatibilidad con autenticación

El mismo `PasswordEncoder` configurado en Spring Security puede utilizar:

```java id="0nkye5"
passwordEncoder.matches(
    rawPassword,
    storedPassword);
```

por lo que el usuario registrado continúa siendo compatible con el mecanismo de autenticación.

### Cambio que no se realizó

Las reglas globales de autorización de `SecurityConfig` no se modificaron.

En particular, TC-10 no implementa todavía la política:

```text id="7owdvu"
deny-by-default
```

porque ese comportamiento corresponde explícitamente a TC-11.

# `RegistrationForm.java`

El formulario de registro continúa teniendo la responsabilidad de transportar los datos introducidos por el usuario y construir la entidad `User`.

La diferencia principal es que la contraseña se transforma mediante el nuevo `PasswordEncoder` antes de crear el objeto que llegará al repositorio.

Conceptualmente:

```text id="r4uzxq"
RegistrationForm
      │
      │ password en texto plano
      ▼
PasswordEncoder.encode()
      │
      ▼
User
      │
      │ password = {bcrypt}...
      ▼
MongoDB
```

El objeto persistido nunca recibe directamente la contraseña original.

## Protección frente a logs

También se protege el campo de contraseña frente a representaciones automáticas como `toString()`.

De esta manera se evita que operaciones como:

```java id="8qzxba"
log.info("{}", registrationForm);
```

puedan incluir accidentalmente la contraseña proporcionada por el usuario.

La misma consideración aplica al hash almacenado en la entidad `User`.

# `RegistrationController.java`

Este archivo contiene el cambio funcional principal de TC-10.

## Problema anterior

El registro ejecutaba conceptualmente:

```java id="v43dmi"
userRepo.save(user);

return "redirect:/login";
```

Sin embargo, `UserRepository` es reactivo.

Por lo tanto:

```java id="en805o"
userRepo.save(user)
```

no representa una escritura inmediata, sino un publisher que debe ser suscrito.

Al descartar el `Mono`, la operación podía no ejecutarse.

## Nuevo flujo reactivo

El registro se reorganizó para construir una única cadena:

```text id="la2l8e"
verificar username
        ↓
verificar email
        ↓
codificar contraseña
        ↓
crear User
        ↓
userRepo.save()
        ↓
MongoDB confirma
        ↓
redirect:/login
```

La operación de guardado forma parte del publisher retornado por el controlador.

No se utiliza:

```java id="5t3ulm"
userRepo.save(...).subscribe();
```

porque Spring es quien realiza la suscripción al publisher retornado por el endpoint.

## Redirección después de persistir

La redirección se genera mediante un operador posterior al guardado.

Conceptualmente:

```java id="fw6d9q"
userRepo.save(user)
    .thenReturn(
        "redirect:/login");
```

Por tanto, si MongoDB devuelve un error:

```text id="2qv5cb"
save()
  X
  │
  └── no redirect
```

El registro sólo se considera terminado cuando la persistencia se completa correctamente.

# Validación de username y email

Antes de crear el usuario se comprueba que no exista otro registro con el mismo:

```text id="3iy59x"
username
email
```

La primera comprobación permite devolver un error funcional comprensible sin intentar innecesariamente la escritura.

El flujo es:

```text id="az27aq"
findByUsername(username)
        │
        ├── existe → 409
        │
        ▼
findByEmail(email)
        │
        ├── existe → 409
        │
        ▼
save()
```

Sin embargo, esta comprobación por sí sola no garantiza unicidad frente a concurrencia.

---

# Protección frente a condición de carrera

Dos solicitudes pueden ejecutarse simultáneamente:

```text id="1p3ydg"
Petición A                  Petición B

find username → vacío      find username → vacío
find email    → vacío      find email    → vacío

        save()             save()
```

Por esta razón TC-10 no depende exclusivamente de las consultas previas.

MongoDB mantiene una segunda protección mediante índices únicos.

Si dos solicitudes alcanzan `save()` al mismo tiempo, solamente una puede completar la escritura.

La otra recibe:

```java id="yyojnd"
DuplicateKeyException
```

que posteriormente se convierte en un conflicto HTTP.

Esto satisface la restricción del reto de proteger también las carreras.

---

# `User.java`

La entidad `User` se modificó para que los campos utilizados como identidad lógica tengan restricciones únicas en MongoDB.

Los campos protegidos son:

```text id="q486ds"
username
email
```

mediante índices equivalentes a:

```java id="y17yfg"
@Indexed(unique=true)
```

Esto proporciona una garantía de persistencia independiente de la comprobación previa realizada por el controlador.

Por tanto, existen dos niveles:

```text id="npqw7o"
Nivel aplicación
findByUsername / findByEmail
          +
Nivel MongoDB
@Indexed(unique=true)
```

La consulta previa mejora la experiencia normal.

El índice único garantiza la integridad.

## Protección del password

El campo correspondiente a la contraseña también se excluye de representaciones automáticas.

Aunque MongoDB necesita almacenar el hash para permitir autenticación, dicho valor no debe tratarse como información pública ni aparecer innecesariamente en logs.

# `ApiExceptionHandler.java`

TC-09 introdujo una estructura uniforme para los errores HTTP.

TC-10 reutiliza esa infraestructura para representar los conflictos de registro sin introducir un segundo formato de errores.

Se agregó manejo para la excepción utilizada por el módulo de seguridad para representar conflictos HTTP.

El resultado esperado ante un usuario duplicado conserva el contrato:

```json id="7q0sc8"

  "detail": "Username or email already exists.",
```

El registro pertenece al módulo:



No se agregó una dependencia desde security hacia API únicamente para lanzar una excepción propia de dicha capa.

Esto evita introducir un acoplamiento innecesario entre módulos.

La primera prueba comprueba la protección de la contraseña.

Se genera un hash utilizando el encoder configurado en `SecurityConfig`.

Después se verifica:

```text id="tjkvgs"
rawPassword != encodedPassword
```

```java id="tgd69z"

    rawPassword,
    encodedPassword)
```

debe devolver:

```text id="5jqgcn"
true
```

También se comprueba que el hash tenga el identificador del algoritmo delegado, por ejemplo:

```text id="3d3ayh"
{bcrypt}
```

Esta prueba cubre directamente el primer criterio de aceptación del reto.

# Prueba de persistencia reactiva

La segunda prueba comprueba que el registro no ejecute la persistencia antes de que exista una suscripción.

Conceptualmente:

```java id="ovjbf4"
Mono<String> result =
    controller.processRegistration(form);
```

por sí solo no debe ejecutar el guardado.

Después:

```java id="c36fp1"
StepVerifier.create(result)
```

suscribe el flujo y provoca la ejecución de:

```text id="mxn1x1"
find username
find email
save user
redirect
```

También se captura el usuario enviado al repositorio y se verifica que su contraseña:

```text id="ryvvzt"
NO sea el texto original
```

pero que:

```java id="mxmtwj"
encoder.matches(
    rawPassword,
    savedUser.getPassword())
```

sea verdadero.

Con esto se comprueba tanto la reactividad como la protección de la contraseña.

# Prueba de duplicados

La tercera prueba agrupa los escenarios relacionados con unicidad.

Se comprueban tres situaciones.

### Username existente

Si:

```text id="fl9c3f"
findByUsername(username)
```

devuelve un usuario, el flujo termina con:

```text id="dr5ty7"
409 Conflict
```

y `save()` no debe ejecutarse.

### Email existente

Si username está disponible pero:

```text id="r8cqrf"
findByEmail(email)
```

encuentra un usuario, se obtiene igualmente:

```text id="rvxwrv"
409 Conflict
```

sin guardar una nueva entidad.

### Carrera detectada por MongoDB

El tercer escenario simula:

```text id="z1c24r"
find username → vacío
find email    → vacío
save          → DuplicateKeyException
```

Esto representa una condición de carrera en la que otro registro fue insertado después de las consultas previas.

`DuplicateKeyException` se transforma en el mismo conflicto controlado:

```text id="cyhgmf"
HTTP 409
```

sin devolver al cliente mensajes internos de MongoDB como:

```text id="pny4tw"
duplicate key
E11000
nombre del índice
nombre de colección
```

# Resultado

Con TC-10 el registro deja de presentar los dos problemas principales detectados originalmente en el proyecto:

```text id="pyv8hm"
NoOpPasswordEncoder
publisher de save descartado
```

La contraseña se transforma mediante un `DelegatingPasswordEncoder` antes de llegar al repositorio, el hash conserva el identificador de algoritmo y puede verificarse mediante `matches()`.

La persistencia forma parte de la cadena reactiva retornada por el controlador, por lo que la redirección sólo se produce después de que MongoDB confirme el guardado.

La unicidad de `username` y `email` se protege mediante dos mecanismos complementarios:

```text id="fygtjp"
comprobación reactiva previa
          +
índice único en MongoDB
```

y tanto los duplicados detectados previamente como las carreras detectadas durante `save()` producen un conflicto HTTP `409` integrado con el contrato de errores de TC-09.

La implementación permanece limitada a TC-10 y no adelanta las reglas de autorización global que corresponden a TC-11.
