# TC-25 — Flujo de estados de una orden

## Descripción del TC

### Resultado funcional

Las órdenes dejan de tener un estado modificable sin reglas y avanzan mediante un workflow central. El servidor controla el estado inicial, valida la combinación estado actual/objetivo/rol, conserva cada transición en una auditoría segura y usa optimistic locking para rechazar escrituras obsoletas. La cancelación del propietario conserva la orden como `CANCELLED` y libera la reserva de TC-16.

### Trabajo solicitado

Se añadieron los siete estados, una matriz central de transiciones y roles, los endpoints `PATCH /api/orders/{id}/status` y `POST /api/orders/{id}/cancel`, cancelación con ownership, cutoff antes de preparación, historial embebido, versión optimista y errores uniformes. La creación normal, por correo y mediante reorder continúa iniciando en `CREATED` sin aceptar estado desde el cliente.

### Restricciones técnicas obligatorias

- `status`, actor, origen, timestamp y versión son server-owned.
- `OrderCreateRequest` no contiene `status`.
- La matriz vive únicamente en `OrderWorkflowService`.
- No se utiliza `synchronized`, locks en memoria, `block()` ni `subscribe()` en servicios.
- Una transición repetida autorizada es idempotente y no agrega otra auditoría.
- La auditoría sólo contiene estado origen/destino, fecha, actor, origen controlado y razón limitada a 200 caracteres.
- `@Version` protege el agregado persistido y un conflicto se traduce a `ORDER_VERSION_CONFLICT`/409.
- Cancelar no reimplementa inventario: delega en `InventoryService.release`.

## Cambios de código

### `TacoOrder.java`

El agregado contiene la única representación de estados y la versión optimista:

```java
@Version
private Long version;

public enum Status {
  CREATED, ACCEPTED, PREPARING, READY,
  OUT_FOR_DELIVERY, DELIVERED, CANCELLED
}
```

El historial es una lista embebida porque el número de cambios es acotado y siempre se consulta junto con la orden:

```java
private List<OrderStatusHistoryEntry> statusHistory = new ArrayList<>();

public static class OrderStatusHistoryEntry {
  private Status fromStatus;
  private Status toStatus;
  private Date changedAt;
  private String changedBy;
  private ChangeOrigin origin;
  private String reason;
}
```

`ChangeOrigin` sólo admite `USER_API`, `KITCHEN_API`, `ADMIN_API` y `SYSTEM`; no acepta texto arbitrario del request.

### `OrderWorkflowService.java`

Es la única fuente de verdad de transición y autorización:

```java
allow(matrix, CREATED, ACCEPTED, KITCHEN, ADMIN);
allow(matrix, ACCEPTED, PREPARING, KITCHEN, ADMIN);
allow(matrix, PREPARING, READY, KITCHEN, ADMIN);
allow(matrix, READY, OUT_FOR_DELIVERY, ADMIN);
allow(matrix, OUT_FOR_DELIVERY, DELIVERED, ADMIN);
allow(matrix, CREATED, CANCELLED, USER, ADMIN);
allow(matrix, ACCEPTED, CANCELLED, USER, ADMIN);
```

`transition` carga por ID para actores operativos y valida rol más grafo. `cancel` resuelve el usuario autenticado y consulta por `orderId + userId`; una orden ajena e inexistente producen el mismo 404 de TC-23.

Una transición exitosa cambia estado, agrega una sola entrada y guarda el agregado. Los fallos de versión se convierten en:

```java
ApiException.conflict(
    "ORDER_VERSION_CONFLICT",
    "The order was updated concurrently. Reload and retry.")
```

La cancelación persiste primero `CANCELLED` y después compone `InventoryService.release`. En un retry, el estado no se vuelve a guardar ni auditar y la liberación idempotente puede completar un intento anterior sin duplicar stock.

### `OrderApiController.java`

El controlador sólo adapta HTTP y delega:

```java
@PatchMapping("/{orderId}/status")
workflowService.transition(orderId, request.getStatus(),
    request.getReason(), authentication);

@PostMapping("/{orderId}/cancel")
workflowService.cancel(orderId, "Cancelled by owner", authentication);
```

El `DELETE` legado también delega en el mismo workflow y ya no borra físicamente el documento, evitando una segunda regla de cancelación.

### `OrderService.java`

La creación normal y reorder establecen explícitamente `CREATED` y registran el evento inicial con el usuario autenticado. La creación por correo registra origen `SYSTEM`. Ningún comando de creación transporta el estado.

```java
order.setStatus(TacoOrder.Status.CREATED);
order.addStatusHistory(new OrderStatusHistoryEntry(
    null, TacoOrder.Status.CREATED, placedAt,
    user.getUsername(), origin, "Order created"));
```

### `ApiDtos.java` y `ApiMapper.java`

`OrderStatusChangeRequest` sólo permite estado objetivo y una razón de hasta 200 caracteres. No incluye `userId`, owner, actor, origin, timestamp o version. `OrderResponse` expone la versión y el historial seguro mediante DTOs; nunca serializa `User` ni datos de pago.

### `SecurityConfig.java`

La seguridad de borde aplica la matriz gruesa antes del servicio:

```java
PATCH /api/orders/*/status -> KITCHEN o ADMIN
POST  /api/orders/*/cancel -> USER o ADMIN
```

El workflow vuelve a validar el rol concreto para cada transición y el ownership de cancelación. Esto conserva deny-by-default sin confiar sólo en la ruta.

### `OrderWorkflowServiceTest.java`

La prueba parametrizada recorre todas las combinaciones de estado actual, estado objetivo y rol. Los casos adicionales comprueban versión/auditoría en el camino feliz, `CREATED → DELIVERED`, cancelación propia/ajena, cutoff, repetición, conservación de `userId`, JSON seguro y mapeo de optimistic locking.

### `OrderWorkflowMongoIntegrationTest.java`

Persiste una orden con `@Version`, obtiene dos copias, guarda la transición de la primera y demuestra que Mongo rechaza el `save` de la segunda copia obsoleta. Finalmente verifica que sólo la primera transición y su historial quedaron persistidos.

### Pruebas existentes modificadas

`DtoContractTest` intenta enviar `status: DELIVERED` durante creación y comprueba que la entidad continúa en `CREATED`. `OrderServiceTest` comprueba la auditoría inicial. `OrderApiControllerTest` verifica delegación al workflow y adapta el DELETE legado. `SecurityConfigTest` comprueba la matriz HTTP. `ApiExceptionHandlerTest` sólo recibe la nueva dependencia del constructor.

## Cambios que no se realizaron

- **TC-26:** no se implementaron cola de cocina, claim atómico, `claimedBy`, estaciones ni ETA.
- **TC-27:** no se definió el contrato único/versionado de eventos de cambio de estado.
- **TC-29:** no se implementó outbox ni recuperación de publicación.
- No se añadió Spring State Machine ni una clase por estado.
- No se modificaron listeners para reclamar o avanzar órdenes; cuando esa función exista deberá llamar al mismo `OrderWorkflowService`.

Para siete estados con reglas simples, `enum + matriz explícita + servicio central` constituye una máquina de estados suficientemente clara. Un State Pattern completo o una librería se justificarían con acciones complejas de entrada/salida, muchas condiciones, numerosos estados o cambios frecuentes del grafo; esas condiciones todavía no existen en TC-25.

## Resultado

TC-25 queda completo: el estado es propiedad del servidor, las transiciones y roles tienen una única fuente de verdad, la cancelación aplica ownership y cutoff, y cada cambio queda auditado sin información sensible. `@Version` evita que dos actores sobrescriban silenciosamente una orden y la prueba con Mongo real demuestra el conflicto. La solución permanece pequeña y reutilizable para TC-26 sin implementar aún cola, claim ni ETA.
