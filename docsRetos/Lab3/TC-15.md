# TC-15 — Motor de cupones con reglas y fecha de expiración

## Descripción del TC

### Resultado funcional

El runtime principal acepta un único `couponCode` al crear o cotizar una orden. El servidor vuelve a calcular el subtotal con el catálogo de TC-13/TC-14, evalúa reglas externas de tipo `PERCENTAGE` o `FIXED` y obtiene `discountAmount` y total sin confiar en importes enviados por el cliente.

Los códigos se normalizan con `trim()` y mayúsculas usando `Locale.ROOT`. La vigencia usa un `Clock` inyectado y límites inclusivos. Una orden aplicada conserva como snapshot únicamente el código normalizado y el descuento. `POST /api/orders/quote` devuelve los importes de la cotización sin guardar una orden, publicar eventos ni modificar inventario.

### Trabajo solicitado

- Incorporar al runtime principal cupones porcentuales y fijos configurables.
- Aplicar vigencia, compra mínima y máximo de descuento cuando corresponda.
- Normalizar códigos de manera case-insensitive y aceptar como máximo uno por orden.
- Calcular descuento y total exclusivamente en servidor con `BigDecimal`.
- Persistir el código aplicado y el descuento como snapshot histórico.
- Exponer una cotización que no cree órdenes ni produzca otros efectos.
- Evitar la enumeración de promociones y no publicar un catálogo de cupones.

### Restricciones técnicas obligatorias

- Los cálculos usan escala 2 y `RoundingMode.HALF_UP`, igual que TC-14.
- La fecha se obtiene desde un `Clock` inyectado; el motor no llama a `LocalDate.now()`.
- Desconocido, no vigente, expirado y compra mínima no alcanzada comparten la política pública `COUPON_NOT_APPLICABLE` al crear una orden.
- La cotización no revela el código ni la regla y expresa el mismo caso únicamente con `valid=false`.
- `discount`, `discountAmount`, `discountedTotal` y `total` no forman parte del contrato confiable de entrada.
- La configuración comercial reside en `application.yml` bajo `tacocloud.coupons.rules` y puede sobrescribirse con propiedades o variables de entorno de Spring.
- No se usan `block()` ni `subscribe()` en los servicios.
- No se reserva, decrementa ni libera inventario.

### Criterios de aceptación

- [x] El motor soporta `PERCENTAGE` y `FIXED`.
- [x] Una regla admite tipo, valor, vigencia, compra mínima y máximo de descuento.
- [x] Los códigos se normalizan con espacios recortados y sin distinguir mayúsculas.
- [x] La vigencia incluye `validFrom` y `validUntil` y usa `Clock`.
- [x] La compra mínima se compara con `BigDecimal`.
- [x] El descuento porcentual respeta `maxDiscount`.
- [x] El descuento fijo nunca produce un total negativo.
- [x] La API acepta cero o un `couponCode`, no una colección acumulable.
- [x] Los importes finales son propiedad del servidor.
- [x] La orden persiste `appliedCouponCode` y `discountAmount` como snapshot.
- [x] Cambiar después la configuración no altera la orden creada.
- [x] `POST /api/orders/quote` no guarda, publica ni modifica stock.
- [x] La respuesta de quote no enumera códigos ni expone reglas.
- [x] No existe endpoint para listar cupones.
- [x] La configuración está fuera del servicio Java.
- [x] No se adelantó TC-16.

### Pruebas mínimas

- `CouponServiceTest` ejecuta 15 casos: ambos tipos, cuatro límites de vigencia con `Clock.fixed`, tres casos de mínimo de compra, máximo porcentual, total cero, tres variantes de capitalización y resultado genérico para código desconocido.
- `shouldPersistCouponSnapshotCalculatedByServer` comprueba subtotal, código normalizado, descuento y total persistidos; luego cambia la regla y verifica que el snapshot ya creado no se recalcula.
- `shouldUseSameGenericErrorForUnknownAndExpiredCoupons` demuestra que ambos casos producen `COUPON_NOT_APPLICABLE` y que no se guarda ni publica la orden.
- `shouldQuoteWithoutPersistencePublicationOrInventoryMutation` comprueba cálculo de quote y ausencia de llamadas a repositorio de órdenes, mensajería, pagos y usuarios.
- `shouldIgnoreServerOwnedFields` intenta enviar descuento, total y dos códigos; sólo el único `couponCode` permitido llega al comando y ningún importe llega a la entidad.
- `shouldReturnSafeQuoteWithoutCouponEnumeration` comprueba que la respuesta sólo contiene estado e importes y no expone códigos, reglas ni colecciones de promociones.

## Cambios de código

### `CouponProperties.java`

Define la configuración mínima del motor y los dos tipos admitidos. El mapa usa el código como clave y evita crear una entidad o repositorio innecesarios.

```java
@ConfigurationProperties(prefix="tacocloud.coupons")
public class CouponProperties {
  private Map<String,CouponRule> rules = new LinkedHashMap<>();

  public enum CouponType { PERCENTAGE, FIXED }
}
```

### `CouponService.java`

Centraliza normalización, vigencia, mínimo y cálculo. Recibe `Clock`, mantiene el redondeo de TC-14 y limita el descuento al subtotal.

```java
LocalDate today = LocalDate.ofInstant(clock.instant(),clock.getZone());

BigDecimal percentageDiscount = subtotal
    .multiply(rule.getValue())
    .divide(new BigDecimal("100"),2,RoundingMode.HALF_UP);

BigDecimal discount = calculateDiscount(rule,subtotal)
    .min(subtotal)
    .max(BigDecimal.ZERO);
```

### `TacoOrder.java`

Conserva el subtotal previo al cupón y el resultado aplicado, sin copiar la configuración comercial completa.

### `ApiDtos.java`

### `ApiMapper.java`

Reutiliza el mapeo de líneas de TC-14 para creación y quote. La respuesta de orden incorpora el snapshot; la respuesta de quote no incorpora códigos ni reglas.

```java
return new OrderQuoteCommand(
```

### `OrderService.java`

Extrae el pricing reactivo común en `priceItems`. La creación exige un cupón aplicable y persiste el resultado; la cotización usa exactamente el mismo subtotal confiable sin tocar repositorios de órdenes ni mensajería.

```java
CouponApplication coupon = couponService.evaluate(
    command.getCouponCode(),subtotal);

order.setSubtotal(coupon.getSubtotal());
order.setAppliedCouponCode(
    coupon.isApplied() ? coupon.getNormalizedCode() : null);
order.setDiscountAmount(coupon.getDiscount());
order.setTotal(coupon.getTotal());
```

```java
public Mono<OrderQuote> quote(OrderQuoteCommand command) {
  return priceItems(command.getItems())
      .map(this::subtotal)
      .map(value -> couponService.evaluate(command.getCouponCode(),value))
      .map(coupon -> new OrderQuote(
          coupon.isApplicable(),coupon.getSubtotal(),coupon.getDiscount(),
          coupon.getTotal(),ORDER_CURRENCY));
}
```

### `OrderApiController.java`

Expone un único endpoint de evaluación, reutilizando DTO, mapper y servicio.

```java
@PostMapping(path="/quote",consumes="application/json")
public Mono<OrderQuoteResponse> quote(
    @Valid @RequestBody OrderQuoteRequest request) {
  return orderService.quote(ApiMapper.toCommand(request))
      .map(ApiMapper::toResponse);
}
```

## Cambios que no se realizaron

- No se creó un módulo Maven ni un repositorio de cupones.
- No se expuso un endpoint de listado, administración o descubrimiento de códigos.
- No se implementaron cupones acumulables ni `couponCodes[]`.
- No se añadieron tarifas, impuestos, promociones automáticas ni reglas distintas de porcentaje/fijo.
- No se modificó la UI: el contrato admite opcionalmente un código, pero TC-15 no exige una pantalla nueva.
- No se reserva, decrementa o libera stock; no existen compensaciones ni control de concurrencia de TC-16.

## Resultado

TC-15 queda implementado en el runtime principal con cálculo monetario confiable, configuración externa, fechas deterministas, snapshot histórico y cotización sin efectos secundarios. Las 32 pruebas focalizadas de TC-15 y de las regresiones de DTO/TC-14 pasan sin fallos. La compilación y empaquetado de los nueve módulos necesarios para el runtime, incluida la UI, también pasan.

Las suites amplias conservan fallos preexistentes ya observados antes de TC-15: `ApiExceptionHandlerTest` falla tres casos por usar `HttpServletRequest` en un fixture WebFlux, `IngredientControllerTest` falla tres casos 400/404 por no registrar el advice en el fixture, y varios métodos antiguos de `OrderApiControllerTest` esperan valores distintos de las excepciones actuales. Ninguno de esos fallos toca el motor, el pricing, la persistencia del descuento o el endpoint nuevo.
