# TC-30 — Consumidor idempotente, retry limitado y DLQ

## Descripción del TC

TC-29 entrega eventos al menos una vez, por lo que cocina debe tolerar redeliveries. TC-30 introduce una marca persistente por `eventId`, coordina esa marca con el efecto durable, limita el retry de fallos transitorios y dirige mensajes permanentes o agotados a una DLQ visible.

### Resultado funcional

RabbitMQ es el broker demostrado de extremo a extremo. El listener entrega el `OrderEvent` a un servicio portable; éste valida el contrato, evita repetir eventos ya confirmados y ejecuta el workflow de TC-25 junto con `ProcessedEvent` en una transacción Mongo. Rabbit sólo confirma el mensaje cuando el `Mono` termina después del commit o cuando la publicación controlada en DLQ termina correctamente.

### Archivos modificados o creados

- `tacocloud-data-mongodb/.../consumer/ProcessedEvent.java` y `ProcessedEventRepository.java`: marca durable e índice único por `eventId`.
- `tacocloud-kitchen/pom.xml`: dependencias API/datos, Actuator y Testcontainers Mongo/Rabbit.
- `tacocloud-kitchen/src/main/resources/application.yml`: Mongo replica set, retry, concurrencia y destinos DLQ externalizados.
- `tacocloud-kitchen/.../consumer/*`: servicio idempotente, handler de workflow, clasificación de errores y métricas.
- `RabbitKitchenMessagingConfig.java`: cola, DLX, DLQ y container factory con ACK manual/asíncrono.
- `rabbit/listener/OrderListener.java`: listener delgado, retry filtrado y envío a DLQ.
- `RabbitOrderDlqPublisher.java` y `RabbitOrderDlqReplayService.java`: headers seguros y replay controlado.
- `RabbitOrderMessagingService.java`: conserva `eventId` y `correlationId` en headers operativos.
- `RabbitOrderConsumerIntegrationTest.java`: pruebas con Mongo replica set y RabbitMQ reales.

### Trabajo solicitado

- Persistir cada `eventId` procesado una sola vez.
- Aplicar el cambio de estado y la marca dentro de una unidad transaccional local.
- Confirmar duplicados sin repetir el workflow.
- Reintentar sólo fallos transitorios, con intentos totales y backoff configurables.
- Enviar errores permanentes y transitorios agotados a la DLQ específica.
- Mantener `correlationId` y una causa acotada sin datos sensibles.
- Exponer métricas pequeñas y un replay que preserve el evento original.

### Restricciones técnicas obligatorias

- La llave idempotente es `eventId`; `orderId` sólo identifica la orden.
- El contrato continúa siendo `OrderEvent` v1 de TC-27.
- `OrderEventConsumerService`, `ProcessedEvent` y el workflow no importan clases Rabbit.
- `maxAttempts` cuenta la entrega inicial: valor `3` significa una ejecución inicial y hasta dos retries.
- Sólo `TransientOrderEventException`, errores Spring Data transitorios y errores Mongo etiquetados como transacción transitoria son reintentables.
- Versiones, estados y transiciones inválidas son permanentes.
- Las métricas no usan `eventId`, `orderId` ni `correlationId` como tags.

### Criterios de aceptación

- Dos entregas de E1 producen un efecto y un `ProcessedEvent`.
- Dos eventos con distinto `eventId` para la misma orden pueden procesarse.
- El índice Mongo único resuelve la carrera final de inserción.
- Efecto, outbox derivado y marca se confirman o revierten juntos.
- El ACK Rabbit ocurre después de la terminación exitosa del procesamiento asíncrono.
- Retry agotado y error permanente llegan a `tacocloud.messaging.rabbit.dead-letter-queue`.
- La versión no soportada genera `UNSUPPORTED_EVENT_VERSION`.
- El replay conserva `eventId`; una marca existente evita repetir el efecto.

### Pruebas mínimas

La suite integrada cubre doble entrega, entrega concurrente, dos eventos de la misma orden, retry que termina con éxito, retry agotado, DLQ y headers, versión no soportada, tipo contractual desconocido, rollback después del efecto, replay idempotente, índice único y métricas `processed`, `duplicate`, `retry` y `dlq`. El backoff de integración es `10ms` para mantener la prueba rápida.

## Cambios de código

`ProcessedEvent` guarda únicamente `eventId`, tipo, fecha, resultado y correlación. No duplica el payload ni datos de usuario/pago. `ProcessedEventRepository` ofrece la búsqueda previa y Mongo impone el índice único ante consumidores concurrentes.

`OrderEventConsumerService` valida v1, consulta por `eventId`, invoca el handler sólo para eventos nuevos y guarda la marca dentro del `TransactionalOperator` reutilizado de TC-29. Si dos transacciones compiten y Mongo devuelve E11000, la transacción perdedora queda abortada y se confirma como duplicado al comprobar la marca ganadora.

`WorkflowOrderEventBusinessHandler` traduce `ORDER_CREATED` a `CREATED -> ACCEPTED` y delega `STATUS_CHANGED` en `OrderWorkflowService`; no contiene una segunda matriz de estados. `CANCELLED` se registra como evento conocido sin intentar una transición reservada al propietario.

`KitchenConsumerConfiguration` incorpora repositorios reactivos y reutiliza `ReactiveMongoTransactionManager`, `OrderOutboxService`, `InventoryService` y `OrderWorkflowService`. No crea otra tecnología transaccional.

`RabbitKitchenMessagingConfig` declara la cola original y su DLQ específica con valores externos. El container usa ACK manual compatible con el resultado `Mono`: success/duplicate o publicación DLQ completada permiten ACK; un fallo previo conserva la entrega como fallida.

`OrderListener` aplica retry fijo únicamente a errores transitorios. Un error permanente pasa directamente al publicador DLQ; al agotarse un error transitorio usa `TRANSIENT_RETRIES_EXHAUSTED`. No contiene lógica de estados ni acceso a Mongo.

`RabbitOrderDlqPublisher` añade sólo código de causa, correlación, evento y destino original. `RabbitOrderDlqReplayService` es una operación explícita: extrae un mensaje de la DLQ y republica el mismo cuerpo al destino original. No cambia `eventId` ni elimina `ProcessedEvent`.

`OrderEventConsumerMetrics` registra `tacocloud.kitchen.order.events` con tags acotados `result` y `eventType`. No implementa dashboards ni un catálogo operacional.

¿Qué ocurre si se guarda `ProcessedEvent` antes del cambio de estado y el proceso muere entre ambos? El evento queda marcado aunque su efecto nunca ocurrió; la redelivery lo consideraría duplicado y confirmaría una pérdida permanente. Por eso la implementación confirma el cambio de orden/outbox y `ProcessedEvent` dentro de la misma transacción Mongo: commit conserva ambos y rollback ninguno.

## Cambios que no se realizaron

TC-31:
propagación completa de correlation ID HTTP/event/logs.

TC-32:
observabilidad operacional completa.

TC-36:
suite global de integración.

No se duplicaron retry/DLQ end-to-end en JMS y Kafka, no se añadió edición de mensajes venenosos, no se borra `ProcessedEvent` durante replay y no se promete exactly-once.

## Relación entre requisitos e implementación

| Requisito | Implementación |
| --- | --- |
| Idempotencia | `ProcessedEvent` |
| Key correcta | `eventId` |
| Índice único | Mongo `processed_event_id_unique` |
| Efecto + marca | `TransactionalOperator` |
| Duplicado | resultado `DUPLICATE` sin handler |
| ORDER_CREATED | handler + `OrderWorkflowService` |
| STATUS_CHANGED | handler + workflow TC-25 |
| Retry transitorio | filtro del listener Rabbit |
| Backoff | `tacocloud.kitchen.consumer.backoff` |
| Error permanente | excepción tipada sin retry |
| DLQ/DLT | DLX/cola específica Rabbit |
| Causa/correlación | headers seguros `x-tacocloud-*` |
| Versión no soportada | `UNSUPPORTED_EVENT_VERSION` |
| Broker E2E | RabbitMQ Testcontainer |
| Replay | `RabbitOrderDlqReplayService` |
| Replay idempotente | cuerpo y `eventId` originales |
| Métrica | `tacocloud.kitchen.order.events` |
| Ack correcto | finalización del `Mono` tras commit/DLQ |

## Resultado

La cocina dispone de un consumidor RabbitMQ idempotente y probado contra infraestructura real. La garantía conjunta es at-least-once en transporte más efecto idempotente por evento: puede existir redelivery después del commit, pero no un segundo efecto para el mismo `eventId`. Los otros transportes conservan el contrato portable de TC-27 sin recibir infraestructura duplicada de TC-30.
