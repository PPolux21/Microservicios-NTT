# TC-02 Eliminar de verdad y responder con semántica HTTP

## Requisitos del proyecto

### Trabajo solicitado

- Reemplazar el método `void` por una cadena reactiva retornada.
- Devolver 204 cuando se elimina y 404 cuando el recurso no existe.
- Hacer que una segunda eliminación del mismo ID responda de forma definida y documentada.
- No capturar excepciones que un repositorio reactivo no lanzará de manera síncrona.

### Restricciones técnicas obligatorias

- La verificación de existencia y el delete deben estar encadenados.
- No responder con cuerpo en 204.
- No usar `try/catch` alrededor de un publisher sin suscripción.

### Criterios de aceptación

+ [x] Después de 204, GET ya no devuelve el ingrediente.
+ [x] ID ausente produce 404.
+ [x] La eliminación se ejecuta exactamente una vez.
+ [x] No hay `subscribe()` manual.

### Pruebas mínimas

- Prueba 204 y verificación de `delete`.
- Prueba 404 sin invocar delete.
- *Prueba de integración con Mongo para confirmar desaparición (Pendiente).*

## Modificaciones y su cumplimiento de los retos

Se modificaron los archivos [`IngredientController.java`](../../tacocloud/tacocloud-api/src/main/java/tacos/web/api/IngredientController.java) y el archivo de pruebas [`IngredientControllerTest.java`](../../tacocloud/tacocloud-api/src/test/java/tacos/web/api/IngredientControllerTest.java) para poder completar con éxito este reto.

### `IngredientController.java`

Se implementó el método de la API `deleteIngredient()` asegurando una arquitectura puramente reactiva, tal y como se muestra a continuación:

```java
  // Antes de la modificación
  @DeleteMapping("/{id}")
  public void deleteIngredient(@PathVariable String id) {
    repo.deleteById(id);
  }

  // Después de la modificación
  @DeleteMapping("/{id}")
  public Mono<ResponseEntity<Void>> deleteIngredient(@PathVariable String id) {
    return repo.findById(id)
      .flatMap(repoFound -> {
        return repo.deleteById(id)
          .thenReturn(ResponseEntity.noContent().<Void>build()); // 204 No Content
      })
      .defaultIfEmpty(ResponseEntity.notFound().<Void>build()); // 404 Not Found
  }
```

De esta forma se cumple con lo solicitado:

- **Encadenamiento reactivo:** Se utiliza `.flatMap()` para garantizar que la operación `deleteById()` solo se ejecute si `findById()` emite un resultado, acatando la restricción de verificar existencia antes de eliminar.
- **Manejo de códigos HTTP sin cuerpo:** Se utiliza el Type Witness `<Void>` en la construcción de los `ResponseEntity` para garantizar estáticamente que la respuesta 204 no contenga ningún cuerpo, y se devuelve el 404 mediante `.defaultIfEmpty()` si el ID no existe.
- **Ausencia de bloqueos:** No existen bloques `try/catch` síncronos ni llamadas a `.subscribe()`, dejando que el framework gestione el ciclo de vida de la suscripción.
- **Segunda eliminación controlada:** Por diseño, si se envía una segunda petición de eliminación para el mismo ID, la búsqueda inicial devolverá vacío y se retornará un 404 limpio y documentado.

### `IngredientControllerTest.java`
Continuando con el archivo de pruebas [IngredientControllerTest.java](../../tacocloud/tacocloud-api/src/test/java/tacos/web/api/IngredientControllerTest.java), se implementaron los métodos de prueba unitaria usando `WebTestClient` para validar los escenarios del método `deleteIngredient()`. A continuación se muestra el código implementado:

```Java
  // TC-02: Pruebas con WebTestClient para el método deleteIngredient
  // 404 Not Found test
  @Test
  public void shouldReturnNotFoundWhenDeletingNonExistentIngredient() {
    IngredientRepository ingredientRepo = Mockito.mock(IngredientRepository.class);

    when(ingredientRepo.findById(any(String.class))).thenReturn(Mono.empty());

    WebTestClient testClient = WebTestClient.bindToController(
        new IngredientController(ingredientRepo)).build();

    testClient.delete()
        .uri("/api/ingredients/1234")
      .exchange()
      .expectStatus().isNotFound();

    Mockito.verify(ingredientRepo, Mockito.never())
      .deleteById(any(String.class));
  }

  // 204 No Content test
  @Test
  public void shouldReturnNoContentWhenDeletingExistingIngredient() {
    IngredientRepository ingredientRepo = Mockito.mock(IngredientRepository.class);
    Ingredient testIngredient = new Ingredient("FLTO", "Flour Tortilla", Type.WRAP);

    when(ingredientRepo.findById(any(String.class))).thenReturn(Mono.just(testIngredient));
    when(ingredientRepo.deleteById(any(String.class))).thenReturn(Mono.empty());

    WebTestClient testClient = WebTestClient.bindToController(
        new IngredientController(ingredientRepo)).build();

    testClient.delete()
        .uri("/api/ingredients/FLTO")
      .exchange()
      .expectStatus().isNoContent()
      .expectBody().isEmpty();

      Mockito.verify(ingredientRepo, Mockito.times(1))
        .deleteById("FLTO");
  }
```

De esta forma se cumple con lo solicitado en los criterios de aceptación y pruebas mínimas:

- **Prueba 404 (ID ausente):** Se simula exitosamente el comportamiento de la base de datos devolviendo `Mono.empty()`, lo que activa la rama de `.defaultIfEmpty()` del controlador y verifica que el estado de respuesta sea `isNotFound()`.
- **Prueba 204 (Camino feliz):** Se verifica que, al encontrar un ingrediente, el cliente web recibe el estado `isNoContent()`, procesando adecuadamente el `Mono.empty()` que retorna la operación de borrado simulada.
