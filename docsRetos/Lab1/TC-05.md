# TC-05 PUT y DELETE de órdenes con identidad consistente

## Requisitos del proyecto

### Trabajo solicitado

* Agregar `@PathVariable orderId` al endpoint PUT y garantizar que la modificación corresponda a la orden indicada por la ruta.
* Evitar que el body pueda modificar ID, usuario, fecha de creación o información de pago.
* Corregir DELETE para retornar y componer el publisher del repositorio.
* Permitir modificación y eliminación únicamente al propietario de la orden o a un usuario con rol `ADMIN`.
* Evitar la eliminación física de órdenes que ya se encuentran en preparación.
* Responder con `200`, `204`, `403`, `404` o `409` según corresponda.

### Restricciones técnicas obligatorias

* PUT no debe crear una nueva orden cuando el ID indicado no existe.
* DELETE debe componer búsqueda, autorización y eliminación dentro de la misma cadena reactiva.
* No utilizar directamente `TacoOrder` como request sin protección.

### Criterios de aceptación

* [x] El ID enviado en el body no puede redirigir la escritura.
* [x] Una orden perteneciente a otro usuario no puede modificarse ni eliminarse.
* [x] Una orden en estado `PREPARING` no puede eliminarse físicamente.
* [x] La respuesta `204 No Content` se produce después de finalizar la eliminación.

### Pruebas mínimas

* [x] PUT con ID contradictorio.
* [x] DELETE de orden existente, ausente y perteneciente a otro usuario.
* [x] DELETE de una orden en estado no eliminable.

> **Pregunta para defender la solución**
>
> ¿Cuándo conviene eliminación física y cuándo una transición a `CANCELLED`?
>
> La eliminación física es adecuada cuando la orden todavía no ha comenzado su procesamiento y puede eliminarse sin afectar otros procesos. Una vez que la orden entra en preparación, ya representa un proceso de negocio iniciado y no debe desaparecer físicamente. En TC-05 se rechaza esa eliminación con `409 Conflict`; una transición formal a `CANCELLED` corresponde al flujo de estados que se desarrollará posteriormente.

Los criterios anteriores corresponden directamente a lo solicitado por TC-05.

### `OrderDeliveryRequest.java`

El DTO utilizado anteriormente exclusivamente para PATCH fue generalizado como `OrderDeliveryRequest`.

El request únicamente permite trabajar con los datos de entrega autorizados y mantiene la detección de propiedades no soportadas mediante `@JsonAnySetter`.

De esta manera campos controlados por el servidor como:

```text
id
user
placedAt
status
ccNumber
ccExpiration
ccCVV
```

no forman parte del contrato permitido.

Esto permite que tanto PATCH como PUT utilicen un request protegido sin recibir directamente una instancia completa de `TacoOrder`.

### `OrderApiController.java`

Se modificaron los endpoints PUT y DELETE.

#### PUT

Anteriormente PUT ignoraba el `orderId` incluido en la ruta y guardaba directamente la orden recibida.

El nuevo flujo utiliza:

```java
repo.findById(orderId)
```

para localizar primero la orden que corresponde al ID de la URL.

Posteriormente se comprueba:

```java
canModify(existingOrder, authentication)
```

para verificar que el usuario sea propietario o administrador.

Los campos permitidos se copian desde `OrderDeliveryRequest` sobre la orden ya recuperada y finalmente se ejecuta:

```java
repo.save(existingOrder)
```

Por lo tanto:

* El ID de la ruta determina qué orden se modifica.
* El cliente no puede sustituir el ID mediante el body.
* Una orden inexistente devuelve `404`.
* Una orden ajena devuelve `403`.
* Una modificación correcta devuelve `200`.
* PUT no crea silenciosamente una orden nueva.

#### DELETE

El método DELETE anterior era `void` y descartaba el publisher retornado por:

```java
repo.deleteById(orderId);
```

El método fue reemplazado por:

```java
Mono<ResponseEntity<Void>>
```

y ahora realiza el flujo:

```text
buscar orden
     ↓
comprobar propietario/ADMIN
     ↓
comprobar estado
     ↓
ejecutar delete
     ↓
204 No Content
```

Una orden inexistente produce:

```text
404 Not Found
```

Una orden perteneciente a otro usuario produce:

```text
403 Forbidden
```

Una orden que ya se encuentra en preparación produce:

```text
409 Conflict
```

y no se ejecuta `deleteById()`.

La eliminación válida utiliza la composición:

```java
repo.deleteById(orderId)
    .thenReturn(
        ResponseEntity
            .noContent()
            .<Void>build());
```

Esto garantiza que `204 No Content` sólo se emita después de completar el publisher de eliminación. El manual identifica precisamente como defecto original que el DELETE descartaba el publisher reactivo.

### `TacoOrder.java`

Se agregó el estado mínimo necesario para distinguir una orden que todavía puede eliminarse de una que ya comenzó su preparación:

```java
public enum Status {
  CREATED,
  PREPARING
}
```

y el estado inicial:

```java
private Status status = Status.CREATED;
```

Para TC-05 únicamente se necesitan estos estados:

```text
CREATED
→ eliminación permitida

PREPARING
→ eliminación física rechazada con 409
```

No se implementaron transiciones adicionales, ya que el flujo completo de estados corresponde a retos posteriores.

### `OrderApiControllerTest.java`

Se agregaron tres pruebas correspondientes a las pruebas mínimas de TC-05.

#### PUT con ID contradictorio

Se agrega un ID no permitido al request y se comprueba:

```text
400 Bad Request
```

Además se verifica que:

```java
repo.findById(...)
repo.save(...)
```

no sean ejecutados.

Con esto se demuestra que el ID incluido en el body no puede redirigir la escritura.

#### DELETE existente, ausente y ajeno

La misma prueba cubre los tres escenarios solicitados:

```text
Orden existente y propia
→ 204 No Content
→ deleteById() ejecutado

Orden inexistente
→ 404 Not Found
→ deleteById() no ejecutado

Orden de otro usuario
→ 403 Forbidden
→ deleteById() no ejecutado
```

Esto comprueba tanto la semántica HTTP como el control de ownership.

#### DELETE de orden en preparación

Se crea una orden con:

```java
TacoOrder.Status.PREPARING
```

y se intenta eliminar.

La respuesta esperada es:

```text
409 Conflict
```

y se comprueba mediante Mockito que:

```java
repo.deleteById(...)
```

nunca sea ejecutado.

Con esto se satisface el criterio de que una orden que ya se encuentra en preparación no pueda eliminarse físicamente. Esta prueba también está expresamente solicitada por TC-05 como prueba de estado no cancelable.
