# TC-33 — Reemplazar Notes por anuncios operativos seguros

## Descripción del TC

### Resultado funcional

El endpoint volátil `/actuator/notes` se reemplaza por `/api/admin/announcements`. Los anuncios operativos se guardan en Mongo con ID estable, autor server-side, severidad acotada, expiración y visibilidad activa. Sólo `ROLE_ADMIN` puede leer, crear o borrar.

### Archivos modificados o creados

- `tacocloud-domain-mongodb/.../OpsAnnouncement.java`: documento Mongo y enum de severidad.
- `tacocloud-data-mongodb/.../OpsAnnouncementRepository.java`: consulta de anuncios activos/no expirados y conteo para el límite.
- `tacocloud-api/.../AnnouncementService.java`: validación, creación, lectura y borrado por ID.
- `tacocloud-api/.../AnnouncementController.java`: contrato REST administrativo y DTOs mínimos.
- `tacocloud-security/.../SecurityConfig.java`: regla ADMIN explícita para announcements.
- `tacocloud/src/main/resources/application.yml`: elimina `notes` de la exposición Actuator.
- `NotesEndpoint.java`: eliminado junto con el `ArrayList` y el índice posicional.
- `ApiExceptionHandlerTest`: usa el puente MVC correcto para verificar sin cambiar el contrato de errores TC-09.
- Pruebas de servicio, contrato, Mongo y seguridad.

### Trabajo solicitado

Persistir anuncios operativos con identidad estable, datos acotados, expiración y acceso administrativo, eliminando el estado en memoria de `NotesEndpoint`.

### Restricciones técnicas obligatorias

- El contrato único es `/api/admin/announcements`; no se creó un segundo endpoint Actuator.
- Sólo se implementaron listar activos, crear y borrar por ID.
- El request contiene únicamente `text`, `severity` y `expiresAt`.
- `createdAt`, `createdBy`, `active` e ID se controlan en servidor.
- No hay lista estática, índice posicional, `block()`, `subscribe()` ni `Thread.sleep()`.
- La respuesta no expone `createdBy` ni objetos `User`.

### Criterios de aceptación

- Mongo conserva anuncios entre instancias del servicio.
- Dos escrituras concurrentes reciben IDs distintos y no sobrescriben contenido.
- El borrado usa el ID Mongo y no altera otros anuncios.
- La consulta excluye `active=false` y `expiresAt <= Clock.instant()`.
- `ROLE_ADMIN` es obligatorio para lectura y escritura.
- Texto, severidad, expiración y máximo activo se validan con errores controlados.

### Pruebas mínimas

- `OpsAnnouncementMongoIntegrationTest`: persistencia, concurrencia, ID estable, borrado, expiración, límite e índice TTL.
- `AnnouncementServiceTest`: vacío, espacios, controles, longitud 500/501, severidad, fecha y máximo activo.
- `AnnouncementControllerTest`: autor autenticado, DTO sin autor, enum desconocido y validación del límite textual.
- `SecurityConfigTest`: ADMIN permitido; USER, KITCHEN y anonymous rechazados.

## Cambios de código

- `OpsAnnouncement`: contiene exclusivamente `id`, `text`, `severity`, `createdAt`, `expiresAt`, `createdBy` y `active`. `@Id` deja que Mongo genere una identidad estable y `expiresAt` posee un índice TTL.
- `OpsAnnouncementRepository`: expresa en Mongo `active=true AND expiresAt>now`, evitando `findAll().filter(...)`, y deshabilita su exportación Data REST para conservar un único contrato HTTP.
- `AnnouncementService`: reutiliza el `Clock` existente, genera metadata server-side, valida el texto y limita a 20 anuncios activos. El conteo y guardado no se presentan como un lock distribuido: una carrera extrema justo en el umbral podría superar temporalmente el máximo, pero cada documento permanece íntegro e independiente.
- `AnnouncementController`: implementa `GET`, `POST` y `DELETE /{announcementId}`. Dos DTOs internos evitan exponer la entidad y omiten `createdBy`.
- `SecurityConfig`: conserva deny-by-default y agrega la ruta a la matriz ADMIN existente; no abre Actuator.
- `application.yml`: conserva `health,info,metrics` de TC-32 y retira el endpoint `notes` eliminado.
- `NotesEndpoint`: se elimina; no se intenta reparar su `ArrayList`.
- `ApiExceptionHandlerTest`: sustituye el montaje WebFlux aislado por `MockMvcWebTestClient`, coherente con el advice Servlet/MVC existente; producción no cambia.

Se eligió `/api/admin/announcements` porque el CRUD reactivo, Bean Validation, `ApiExceptionHandler` y la autorización `/api/admin/**` pertenecen naturalmente a la API. Actuator queda reservado a diagnóstico y operación técnica, sin convertirse en una API general de contenido.

La longitud máxima de 500 caracteres y el máximo de 20 anuncios activos son decisiones de implementación centralizadas en `AnnouncementService`, no valores impuestos por el enunciado. Se rechazan todos los caracteres ISO de control, incluidos CR, LF y tabulador.

Mongo elimina físicamente documentos cuando vence `expiresAt` mediante el índice TTL `ops_announcement_expiry_ttl`. Como el monitor TTL no es instantáneo, la consulta excluye expirados usando el `Clock` antes de que ocurra la limpieza física.

¿Un endpoint Actuator debe contener funcionalidad de negocio o sólo operación? Actuator debe limitarse a administración, diagnóstico y operación de la aplicación. Un mensaje estrictamente técnico podría exponerse allí, pero cuando existe CRUD persistente y un contrato administrativo resulta más clara una API normal. Si los anuncios evolucionaran a contenido comercial, interacción o workflow, pertenecerían todavía más claramente a la API de producto, nunca a Actuator.

## Relación entre requisitos e implementación

| Requisito | Implementación |
| --- | --- |
| ID estable | Mongo `@Id` |
| Persistencia | `OpsAnnouncementRepository` reactivo |
| Texto | Bean Validation y validación defensiva del servicio |
| Severidad | `INFO`, `WARNING`, `CRITICAL` |
| createdAt | `Clock` server-side |
| expiresAt | validación, consulta Mongo e índice TTL |
| createdBy | `Authentication.getName()` |
| active | `true` al crear y condición de consulta |
| Longitud | máximo centralizado de 500 |
| Control chars | rechazo de caracteres ISO de control |
| Máximo activo | máximo centralizado de 20 y error 409 |
| Expirados ocultos | query `active=true AND expiresAt>now` |
| Cleanup | índice TTL Mongo |
| Concurrencia | documentos Mongo independientes e IDs distintos |
| Delete correcto | `findById` y `delete(entity)` |
| Escritura ADMIN | `SecurityConfig` |
| Lectura | sólo ADMIN |
| Autor no público | `AnnouncementResponse` sin `createdBy` |
| Contrato único | repositorio no exportado por Data REST |
| Sin ArrayList | `NotesEndpoint` eliminado |

## Resultado

TC-33 reemplaza por completo las notas volátiles con un flujo administrativo pequeño, reactivo y persistente. Los anuncios tienen ID estable, validación, expiración determinista y seguridad ADMIN sin revertir TC-11 o TC-32.

Clases existentes reutilizadas:
`Clock`, `SecurityConfig`, `ApiExceptionHandler`, Mongo reactivo y configuración de índices.

Clases nuevas realmente necesarias:
cuatro clases productivas: modelo, repositorio, servicio y controlador. Los DTOs y el enum viven dentro de esas clases para evitar archivos adicionales.

Abstracciones que se decidió NO crear:
cleanup service, scheduler, manager, factory, workflow, auditoría, notificaciones, chat o endpoint Actuator paralelo.

Dependencias nuevas:
ninguna.

Retos posteriores no implementados:
TC-34, TC-35 y TC-36.
