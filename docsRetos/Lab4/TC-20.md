# TC-20 — Taco del día determinista y comprobable

## Descripción del TC

### Resultado funcional

`GET /api/tacos/today` devuelve una recomendación calculada para la fecha de la zona configurada. El servicio sólo considera tacos que continúan siendo válidos con los ingredientes actuales, ordena los candidatos por identificador y selecciona uno mediante un índice reproducible. La consulta no guarda tacos ni recomendaciones.

### Trabajo solicitado

- Seleccionar entre tacos disponibles y válidos para una fecha y zona configuradas.
- Obtener la fecha desde un `Clock` inyectado.
- Producir el mismo ID para las mismas entradas.
- Ignorar el orden físico de Mongo mediante un orden estable por ID.
- Exponer taco, fecha y una explicación breve en `GET /api/tacos/today`.
- Definir el comportamiento sin candidatos.
- Evitar persistencia, aleatoriedad y estado innecesario.

### Restricciones técnicas obligatorias

- El algoritmo no utiliza `Random`, UUID, `Instant.now()` ni `LocalDate.now()` sin `Clock`.
- La zona se declara una sola vez mediante `tacocloud.recommendation.zone`.
- Los candidatos se revalidan mediante `TacoDesignValidator`; no se copian reglas de TC-17 o TC-18.
- La disponibilidad procede del ingrediente actual del catálogo, no de la copia embebida histórica del taco.
- La composición permanece reactiva y no contiene `block()` ni `subscribe()`.
- El endpoint no crea documentos de recomendación ni llama a `save()`.
- No se añadió caché: el cálculo es barato y volver a consultar evita invalidación obsoleta.

### Criterios de aceptación

- [x] Dos llamadas con la misma fecha y catálogo retornan el mismo ID.
- [x] Dos fechas producen exactamente el resultado indicado por el algoritmo.
- [x] Dos órdenes físicos de candidatos producen el mismo resultado.
- [x] La selección se calcula después de ordenar por identificador estable.
- [x] La fecha procede de un `Clock` inyectado.
- [x] La zona `America/Mexico_City` es configurable.
- [x] Sólo se consideran diseños válidos con ingredientes actuales disponibles.
- [x] Un ingrediente que deja de estar disponible elimina al taco de los candidatos.
- [x] Una referencia de ingrediente que ya no existe elimina al taco de los candidatos.
- [x] Sin candidatos se responde 404 con `NO_TACO_AVAILABLE`.
- [x] La respuesta contiene `taco`, `date` y `reason`.
- [x] Consultar la recomendación no persiste ningún taco.
- [x] No se implementó funcionalidad de TC-21 o TC-22.

### Pruebas mínimas

`DailyTacoServiceTest` demuestra con `Clock.fixed(...)`:

- dos evaluaciones del mismo día con el mismo ID;
- dos fechas consecutivas contra el índice esperado;
- independencia frente al orden físico de la lista;
- fecha lógica determinada por `America/Mexico_City` cerca del límite UTC;
- error estable sin candidatos;
- exclusión de tacos con ingredientes no disponibles o inexistentes;
- ausencia de llamadas a `TacoRepository.save(...)`.

`TacoControllerTest` comprueba el contrato HTTP 200 con `taco`, fecha ISO y razón, además del 404 uniforme `NO_TACO_AVAILABLE` y la ausencia de persistencia.

La regresión conjunta de `DailyTacoServiceTest`, `TacoControllerTest`, `TacoClassificationServiceTest`, `TacoDesignValidatorTest` y `TacoSearchMongoIntegrationTest` ejecutó 33 pruebas sin fallos. El empaquetado completo de los nueve módulos también terminó correctamente. La ejecución sin filtro de todo el reactor continúa detenida por fallos heredados de `tacocloud-security`, anteriores y ajenos a los archivos de TC-20.

## Cambios de código

### `DailyTacoService.java`

Centraliza la obtención, revalidación y selección. Cada diseño usa el validador de TC-18, que a su vez resuelve la metadata vigente de ingredientes:

```java
return tacoRepo.findAllByOrderByIdAsc()
    .concatMap(taco -> designValidator.validate(
        taco.getName(), ingredientIds(taco))
        .filter(TacoDesignValidator.ValidationResult::isValid));
```

Antes de seleccionar vuelve a ordenar por ID, por lo que el resultado no depende del orden proporcionado por el repositorio:

```java
ordered.sort(Comparator.comparing(
    candidate -> candidate.getTaco().getId()));
int index = Math.floorMod(date.toEpochDay(), ordered.size());
```

La fecha se obtiene únicamente mediante:

```java
LocalDate date = LocalDate.now(clock);
```

Si no queda ningún candidato, el servicio emite `NO_TACO_AVAILABLE`. No guarda ninguna entidad.

### `TacoRepository.java`

Añade una consulta derivada y reactiva que solicita a Mongo los tacos ordenados por ID:

```java
Flux<Taco> findAllByOrderByIdAsc();
```

El servicio conserva además su propio ordenamiento antes del módulo como defensa frente a cualquier fuente que entregue un orden físico distinto.

### `TacoController.java`

El controlador delega toda la selección al servicio y sólo adapta el resultado HTTP:

```java
@GetMapping("/today")
public Mono<DailyTacoResponse> tacoOfTheDay() {
  return dailyTacoService.recommend().map(ApiMapper::toResponse);
}
```

### `ApiDtos.java`

Incorpora `DailyTacoResponse` en el archivo de DTOs existente para evitar otro archivo pequeño:

```java
public static class DailyTacoResponse {
  private TacoCatalogResponse taco;
  private String date;
  private String reason;
}
```

La fecha se expone como ISO `yyyy-MM-dd` y el taco reutiliza el contrato seguro y clasificado del catálogo.

### `ApiMapper.java`

Convierte la recomendación interna a `DailyTacoResponse` reutilizando el mapper de `ClassifiedTaco`; no vuelve a implementar clasificación ni serialización del catálogo.

### `TacoCloudApplication.java`

El único bean `Clock` de la aplicación usa una zona externa:

```java
Clock applicationClock(
    @Value("${tacocloud.recommendation.zone:America/Mexico_City}")
    String zone) {
  return Clock.system(ZoneId.of(zone));
}
```

Esto evita depender de la zona del servidor o contenedor y mantiene la inyección ya usada por cupones.

### `application.yml`

Declara la zona lógica de forma centralizada:

```yaml
tacocloud:
  recommendation:
    zone: America/Mexico_City
```

### `DailyTacoServiceTest.java`

Prueba directamente el algoritmo, el reloj, el orden estable y la revalidación de disponibilidad. Los resultados se verifican por ID, no sólo por nombre.

### `TacoControllerTest.java`

Añade pruebas HTTP para respuesta exitosa y ausencia de candidatos. También verifica con Mockito que el GET no invoque `save()`.

## Cambios que no se realizaron

- TC-21: no se implementaron favoritos ni endpoints del usuario.
- TC-22: no se implementaron calificaciones, promedios ni ranking.
- No se agregó personalización por usuario, dieta, popularidad o historial.
- No se creó un documento `DailyTaco`, historial de recomendaciones ni escritura adicional.
- No se agregó caché porque es opcional, el cálculo es barato y omitirla evita estado e invalidación innecesarios cuando cambia el catálogo.
- No se agregó Redis, Caffeine ni ninguna dependencia.

Determinismo no significa necesariamente obtener un taco diferente todos los días. Significa que las mismas entradas —fecha, zona y catálogo ordenado de candidatos— producen siempre el mismo resultado. Con un único candidato, por ejemplo, todos los días deben devolver ese mismo taco; el comportamiento sigue siendo predecible y reproducible.

## Resultado

TC-20 queda resuelto mediante una selección pequeña, reactiva y reproducible. La recomendación depende únicamente de la fecha obtenida del `Clock`, la zona configurada y el conjunto actual de diseños válidos ordenados por ID. El endpoint reutiliza clasificación, validación, DTOs y manejo uniforme de errores existentes, no persiste estado y queda fuera del alcance de favoritos y ratings.
