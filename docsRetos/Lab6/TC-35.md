# TC-35 — Versionar la API y publicar contrato OpenAPI

## Descripción del TC

TC-35 publica los contratos HTTP mantenidos bajo `/api/v1`, conserva `/api` como
alias temporal y deja `docs/openapi.yaml` como fuente revisable del contrato.

### Resultado funcional

Los mismos controladores atienden las rutas v1 y legacy sin duplicar casos de
uso. Los clientes Angular y cocina usan v1. Una ruta legacy versionada conserva
su funcionamiento y recibe `Deprecation: true` y un `Link` al path sucesor.

### Archivos modificados o creados

- Los controladores de ingredientes, tacos, ratings, favoritos, órdenes,
  historial, cocina y anuncios incorporan un segundo mapping `/api/v1`.
- `SecurityConfig` aplica la misma matriz a ambas bases y permite/exhibe los
  headers transversales en CORS.
- `CorrelationIdWebFilter` añade la metadata de deprecación del alias legacy.
- Angular y `KitchenUI` consumen v1; la creación UI envía `Idempotency-Key`.
- `tacocloud-api/pom.xml` incorpora Swagger Parser sólo para tests.
- `docs/openapi.yaml` y `OpenApiContractTest` publican y verifican el contrato.
- `README.md` explica la base recomendada, la ubicación del spec y la transición.

### Trabajo solicitado

- Introducir `/api/v1` sin eliminar `/api`.
- Documentar los contratos reales de ingredientes, tacos, órdenes, favoritos,
  ratings, cocina, administración y errores.
- Documentar seguridad HTTP Basic, `Idempotency-Key`, `X-Correlation-Id`,
  requests/responses separados, estados y ejemplos.
- Validar el documento y contrastar `POST /api/v1/orders` y `ApiProblem` con
  respuestas reales del controlador.

### Restricciones técnicas obligatorias

- El YAML describe DTOs HTTP y no se genera desde entidades Mongo.
- No se duplican controladores, servicios o modelos con sufijo V1.
- El spec vive en Git, no en `target`.
- Swagger Parser 2.0.32 es test-only; no se añadió Swagger UI ni generación
  runtime y no se actualizó Spring Boot 2.5.3.
- La tokenización sigue en `/api/payment-methods/tokenize` como borde legacy no
  público: documentar su request expondría datos de tarjeta que TC-35 prohíbe en
  schemas públicos. Su respuesta segura continúa entregando `paymentMethodId`.

### Criterios de aceptación

- `openapi.yaml` valida sin mensajes de error y todos sus `$ref` se resuelven.
- Sus 27 paths contienen las 35 operaciones versionadas que existen en los ocho
  controladores incluidos en el contrato público v1.
- Requests, responses y `ApiProblem` usan schemas diferentes y explícitos.
- Una prueba falla ante un campo requerido ausente y comprueba que 202 no está
  documentado para crear una orden.
- UI y cocina usan v1; el alias legacy permanece probado y documentado.
- Los schemas no contienen campos de credenciales, tarjeta, roles internos ni
  token completo, y tampoco incluyen `TacoOrder`, `User` o `PaymentMethod`.

### Pruebas mínimas

- Swagger Parser sobre `docs/openapi.yaml`.
- Respuesta real 201 y replay 200 de `POST /api/v1/orders` contra `OrderResponse`.
- Error 400 real con `application/problem+json` contra `ApiProblem`.
- Alias `/api/orders` operativo y filtro con `Deprecation`/`Link`.
- Inspección negativa de nombres sensibles en todos los schemas.
- Regresiones focalizadas de controladores, seguridad, UI y cocina.

## Cambios de código

- `docs/openapi.yaml`: define OpenAPI 3.0.3, seguridad Basic, paths v1, headers,
  estados, ejemplos y schemas DTO independientes de Mongo.
- Controladores API: mappings dobles que delegan a los mismos métodos. El
  `Location` de orden se construye desde la URI solicitada y conserva `/api/v1`.
- `CorrelationIdWebFilter`: reutiliza el borde transversal existente para
  metadata legacy; no marca rutas v1 ni tokenización.
- `SecurityConfig`: replica las reglas por rol para v1 sin alterar `denyAll`, y
  añade headers de idempotencia/correlación/deprecación a CORS.
- `OpenApiContractTest`: valida spec/referencias, paths, seguridad, órdenes,
  problemas, status, incompatibilidad y campos prohibidos.
- UI y cocina: sólo cambian sus paths mantenidos a v1; no se reescribieron los
  clientes ni su arquitectura.

¿Versionar por URL resuelve automáticamente la compatibilidad? No. `/api/v1`
identifica una versión HTTP, pero la compatibilidad también depende de campos
requeridos, tipos, estados, headers, seguridad, reglas y significado. Mantener la
ruta y cambiar la semántica de `total` seguiría siendo incompatible. Además,
`OrderEvent.version` pertenece al contrato de mensajería de TC-27 y no cambia al
versionar HTTP. Se necesitan URL, schema, semántica y pruebas contractuales.

## Cambios que no se realizaron

TC-36:
suite global de integración, Testcontainers completos y pipeline general.

No se agregó Swagger UI ni un generador runtime porque `openapi.yaml` versionado
y validado satisface el contrato requerido.

No se duplicaron controllers o DTOs para v1 cuando el contrato era el mismo.

No se actualizó Spring Boot, Java, eventos, persistencia ni reglas de negocio.

## Relación entre requisitos e implementación

| Requisito | Implementación |
| --- | --- |
| API v1 | `/api/v1/**` en los controladores existentes |
| API legacy | mappings `/api/**` compartidos |
| Deprecación | `CorrelationIdWebFilter`: `Deprecation` + `Link` |
| Contrato | `docs/openapi.yaml` |
| Ingredientes | paths y schemas request/response específicos |
| Tacos | búsqueda, detalle, creación, validación y clasificación |
| Órdenes | creación, quote, reorder, workflow, cancelación e historial |
| Favoritos | rutas `/users/me`, paginación y ownership autenticado |
| Ratings | score 1–5 y top agregado |
| Cocina | queue, claim y status seguro |
| Request/response separados | DTOs TC-08 y schemas distintos |
| Errores | `ApiProblem` + `application/problem+json` |
| Idempotency | `Idempotency-Key` requerido en creación/reorder |
| Correlation | request/response `X-Correlation-Id` |
| Seguridad | `basicAuth`, roles descritos y matriz real de `SecurityConfig` |
| Ejemplos | creación de orden, respuesta y problema |
| Validation | Swagger Parser 2.0.32 en test |
| Contract test | `POST /api/v1/orders` 201/200/400 |
| Legacy test | `/api/orders` + metadata del filtro |
| Datos sensibles | inspección de propiedades de schemas |
| UI/cliente | Angular y cocina usan `/api/v1` |

## Resultado

El contrato HTTP recomendado queda identificado por URL, descrito en un único
YAML y comprobado durante tests. La transición no rompe `/api`, la seguridad se
mantiene simétrica y los clientes activos se migraron sin duplicar lógica.

Clases existentes reutilizadas:
controladores actuales, `ApiProblem`, `SecurityConfig` y
`CorrelationIdWebFilter`.

DTOs reutilizados:
los contratos de `ApiDtos`, `OrderDeliveryRequest`, `EmailOrder` y anuncios.

Controllers reutilizados:
ocho controladores versionados mediante mappings dobles; tokenización permanece
como borde legacy deliberadamente fuera del spec público.

Archivos nuevos realmente necesarios:
`docs/openapi.yaml`, `OpenApiContractTest.java` y este documento.

Dependencias nuevas:
Swagger Parser 2.0.32, exclusivamente test scope.

Abstracciones que se decidió NO crear:
facade v1, version manager, registry, gateway, generador runtime y DTOs V1
duplicados.

Contrato fuente:
`openapi.yaml`.

Reto posterior no adelantado:
TC-36.
