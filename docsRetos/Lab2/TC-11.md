# TC-11 — Autorización deny-by-default y roles útiles

## Requisitos del proyecto

### Resultado funcional

La aplicación deja de terminar su configuración de seguridad con una regla global `permitAll` y pasa a utilizar una matriz explícita de autorización.

Se incorporan tres roles:

```text
USER
ADMIN
KITCHEN
```

Cada rol tiene responsabilidades distintas y las rutas no declaradas quedan denegadas por defecto.

Además, el acceso a órdenes no depende únicamente de la URL protegida, sino que también se comprueba el ownership dentro de la lógica de servicio.

### Trabajo solicitado

- Definir los roles `USER`, `ADMIN` y `KITCHEN`.
- Permitir lectura pública del catálogo.
- Exigir autenticación para creación y gestión de órdenes.
- Restringir administración de ingredientes a `ADMIN`.
- Reservar operaciones de cocina para `KITCHEN`.
- Eliminar cualquier regla global `permitAll`.
- Aplicar ownership de órdenes dentro del servicio.
- Proteger `/data-api/**`.
- Proteger Actuator y decidir explícitamente qué parte de health es pública.
- Configurar CORS sin utilizar `*`.
- Revisar CSRF según el mecanismo de autenticación utilizado.
- Incluir pruebas positivas y negativas de autorización.

### Restricciones técnicas obligatorias

- Deben existir pruebas `401 Unauthorized`.
- Deben existir pruebas `403 Forbidden`.
- La identidad del usuario debe obtenerse desde `Authentication` o el contexto de seguridad.
- No se debe confiar en un `userId` enviado por el cliente.
- CORS debe utilizar orígenes explícitos.
- Una ruta nueva debe quedar protegida automáticamente.
- Ownership no puede depender únicamente de que una URL esté protegida.

### Criterios de aceptación

- [x] Un usuario anónimo puede consultar el catálogo.
- [x] Un usuario anónimo no puede crear una orden.
- [x] `USER` puede crear órdenes.
- [x] `USER` sólo puede consultar/modificar sus propias órdenes.
- [x] `ADMIN` puede administrar ingredientes.
- [x] `ADMIN` puede consultar órdenes de todos los usuarios.
- [x] `KITCHEN` puede acceder al namespace reservado para operaciones de cocina.
- [x] `KITCHEN` no obtiene permisos administrativos.
- [x] `/data-api/**` queda restringido.
- [x] Actuator queda protegido salvo el health básico decidido como público.
- [x] Una ruta no declarada queda denegada por defecto.
- [x] CORS queda centralizado y no utiliza comodines.

### Pruebas mínimas

- [x] Pruebas `401 / 403 / 200` según rol.
- [x] Prueba de usuario A intentando acceder a una orden de B.
- [x] Prueba de endpoint no listado denegado.
- [x] Prueba de protección de Actuator.
- [x] Prueba de protección de Spring Data REST.

> **Pregunta para defender la solución**
>
> ¿Qué falla más seguido: una regla equivocada o una ruta nueva que nadie agregó a la matriz?
>
> Ambos casos son posibles, pero una política permisiva por defecto agrega un riesgo adicional: una ruta nueva puede quedar pública sin que nadie lo note.
>
> Por ello TC-11 utiliza:
>
> ```java
> .anyRequest().denyAll()
> ```
>
> Una ruta nueva nace cerrada y debe ser agregada explícitamente a la matriz de seguridad.
>
> Esto reduce el riesgo de exposición accidental y obliga a que cada nuevo endpoint tenga una decisión consciente de autorización.

# Matriz de autorización implementada

La política de seguridad queda definida explícitamente.

| Recurso | Anónimo | USER | ADMIN | KITCHEN |
| --- | --- | --- | --- | --- |
| `GET /api/tacos/**` | Permitido | Permitido | Permitido | Permitido |
| `GET /api/ingredients/**` | Permitido | Permitido | Permitido | Permitido |
| `POST /api/tacos/**` | 401 | Permitido | Permitido | Denegado |
| Escritura `/api/ingredients/**` | 401 | 403 | Permitido | 403 |
| `/api/orders/**` | 401 | Propias | Todas | 403 |
| `POST /api/orders/fromEmail` | 401 | 403 | Permitido | 403 |
| `/api/kitchen/**` | 401 | 403 | 403 | Permitido |
| `/data-api/**` | 401 | 403 | Permitido | 403 |
| `/actuator/health` | Público | Público | Público | Público |
| Otros `/actuator/**` | 401 | 403 | Permitido | 403 |
| Ruta no listada | Denegada | Denegada | Denegada | Denegada |

Esta matriz permite separar autorización HTTP general de reglas adicionales de ownership.

# `SecurityConfig.java`

Este archivo contiene el cambio principal de TC-11.

## Eliminación del `permitAll` global

La configuración anterior terminaba conceptualmente con una regla equivalente a:

```java
.antMatchers("/**")
.permitAll()
```

Esto hacía que Spring Security estuviera presente, pero no proporcionara una política efectiva de protección.

La nueva configuración termina con:

```java
.anyRequest()
.denyAll()
```

De esta forma solamente las rutas incluidas explícitamente dentro de la matriz pueden ser utilizadas.

El flujo pasa de:

```text
ruta conocida   → permitida
ruta nueva      → permitida accidentalmente
```

a:

```text
ruta conocida   → regla explícita
ruta nueva      → DENY
```

Esto incluye:

```text

```

De esta manera un usuario estándar puede consultar ingredientes pero no:


## Órdenes

Todas las operaciones normales de:

```text
/api/orders/**
```

requieren un usuario autenticado con:

```text
ROLE_USER
ROLE_ADMIN
```

La autorización HTTP actúa como primera barrera.

Posteriormente `OrderService` vuelve a verificar ownership.

---

## Órdenes provenientes de correo

El endpoint:

```text
POST /api/orders/fromEmail
```

se restringe a `ADMIN`.

La razón es que ese flujo construye una orden utilizando un correo recibido como entrada.

Permitirlo directamente a un `USER` introduciría la posibilidad de solicitar la creación de una orden asociada al correo de otro usuario.

No se modificó la lógica funcional de TC-06/TC-07; únicamente se restringió quién puede iniciar ese flujo desde HTTP.

---

## Namespace de cocina

Se reserva:

```text
/api/kitchen/**
```

para:

```text
ROLE_KITCHEN
```

TC-11 define la frontera de autorización, pero no crea todavía la lógica funcional completa de cocina.

Esto permite que futuros endpoints de cocina nazcan dentro de un namespace ya protegido.

---

# CSRF

TC-11 revisa explícitamente CSRF según el modelo de autenticación existente.

La aplicación todavía utiliza mecanismos basados en navegador como:

```text
formLogin
```

Por ese motivo no se deshabilita CSRF globalmente.

Las pruebas de operaciones mutables utilizan un token CSRF válido mediante:

```java
.with(csrf())
```

Esto diferencia:

```text
autenticación
```

de:

```text
protección frente a solicitudes cross-site
```

y evita resolver el problema desactivando la protección completa.

# `OrderApiController.java`

El controlador de órdenes fue adaptado para delegar decisiones de ownership hacia `OrderService`.

## Consulta de órdenes

Antes, el controlador podía utilizar directamente:

```java
repo.findAll()
```

lo que permitía obtener todas las órdenes.

Ahora delega en:

```java
orderService.findOrdersFor(authentication)
```

El resultado depende del usuario autenticado.

Para un `USER`:

```text
Authentication
      ↓
username
      ↓
UserRepository
      ↓
órdenes del usuario
```

Para un `ADMIN`:

```text
Authentication
      ↓
ROLE_ADMIN
      ↓
repo.findAll()
```

---

## Creación de una orden

La creación de órdenes también recibe la identidad autenticada.

Conceptualmente:

```text
OrderCreateRequest
       +
Authentication
       ↓
OrderService
       ↓
User autenticado
       ↓
TacoOrder.user
```

El cliente no decide quién es el propietario de la orden.

La propiedad se obtiene desde:

```java
authentication.getName()
```

y posteriormente se resuelve el `User` almacenado.

Esto evita confiar en valores como:

```text
userId
username
owner
```

proporcionados por el cliente.

---

## PUT / PATCH / DELETE

Las operaciones que modifican una orden dejaron de depender de una función privada de autorización dentro del controlador.

Ahora utilizan:

```java
orderService.canAccessOrder(...)
```

De esta manera la regla de ownership se concentra en el servicio y puede reutilizarse independientemente del endpoint.

# `OrderService.java`

Este archivo incorpora la segunda capa importante de seguridad.

## Ownership en servicio

Se agregó lógica para determinar si un usuario puede operar sobre una orden.

Conceptualmente:

```text
ADMIN
  ↓
puede acceder

USER
  ↓
order.user.username
        ==
authentication.name
```

Un usuario común solamente puede acceder cuando:

```text
dueño de la orden == usuario autenticado
```

---

## Consulta de órdenes por usuario

Para usuarios normales se utiliza el usuario autenticado como criterio de búsqueda.

No se utiliza un identificador recibido desde el cliente.

El flujo queda:

```text
authentication.getName()
       ↓
findByUsername(...)
       ↓
User persistido
       ↓
findByUserOrderByPlacedAtDesc(...)
```

Esto garantiza que un usuario A no pueda solicitar las órdenes de B manipulando parámetros del request.

---

## Auditoría para ADMIN

Cuando la autenticación posee:

```text
ROLE_ADMIN
```

el servicio permite consultar todas las órdenes mediante:

```java
repo.findAll()
```

Esto cumple el requisito de que ADMIN pueda auditar órdenes.

---

## Creación asociada al usuario autenticado

Al crear una orden, `OrderService` obtiene el usuario desde el repositorio y asigna:

```java
order.setUser(user);
```

El owner no procede del DTO.

Con esto se mantiene la protección contra mass assignment establecida anteriormente y se agrega la garantía de ownership requerida por TC-11.

# Política 401 frente a 403

La implementación diferencia correctamente ambos estados.

## 401 Unauthorized

Se utiliza cuando el usuario no está autenticado.

Ejemplo:

```text
anónimo

```

```text

```

## 403 Forbidden

Se utiliza cuando el usuario sí está autenticado, pero no posee permiso suficiente.

Ejemplo:

```text

POST /api/ingredients
```

Resultado:

```text

```

Esta diferencia permite que el cliente sepa si necesita autenticarse o si sus credenciales actuales simplemente no poseen el rol necesario.

# Flujo final de autorización

La política completa puede resumirse como:

```text
                 Request
                    ↓
             SecurityConfig
                    ↓
        ┌───────────┴───────────┐
        │                       │
      permit                  deny
        │                       │
        ▼                       ▼
    Controller             401 / 403
        │
        ▼
     Service
        │
        ▼
ownership / regla funcional
        │
        ▼
    Repository
```

Una ruta nueva que no forme parte de la matriz termina en:

```text
denyAll
```

y no queda disponible accidentalmente.

# Resultado

TC-11 transforma la configuración de seguridad de TacoCloud desde una política permisiva hacia una estrategia explícita y deny-by-default.

La seguridad ya no termina en:

```java
permitAll()
```

sino en:

```java
denyAll()
```

y cada grupo de endpoints tiene una decisión clara.

El catálogo permanece público para lectura, mientras que las operaciones sensibles se separan por rol:

```text
USER    → uso normal y órdenes propias
ADMIN   → administración y auditoría
KITCHEN → operaciones de cocina
```

El ownership de órdenes se valida dentro de `OrderService`, utilizando la identidad obtenida desde `Authentication` en lugar de aceptar un propietario proporcionado por el cliente.

Spring Data REST y Actuator dejan de estar expuestos libremente, CORS queda centralizado con orígenes explícitos y las pruebas comprueban tanto accesos permitidos como denegaciones `401` y `403`.

Finalmente, una ruta nueva queda cerrada automáticamente hasta que sea incluida de forma consciente en la matriz de autorización, cumpliendo el objetivo principal de TC-11 sin adelantar las funcionalidades correspondientes a TC-12 o retos posteriores.
