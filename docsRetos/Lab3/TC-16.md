# TC-16 — Reservar y liberar inventario sin vender aire

## Descripción del TC

### Resultado funcional

La creación de una orden API conserva el pricing y los cupones de TC-14/TC-15, genera primero un ID estable y reserva las cantidades físicas antes de guardar la orden. Cada ingrediente se descuenta mediante una actualización atómica condicionada por disponibilidad y stock suficiente. La orden sólo se persiste cuando todos los ingredientes quedaron reservados.

Si un ingrediente falla, se liberan en orden inverso únicamente los descuentos que sí se realizaron. Si falla el guardado de la orden después de reservar, se libera la reserva antes de propagar el error. Una cancelación permitida libera el inventario antes de borrar la orden. Tanto `reserve()` como `release()` son idempotentes mediante un documento persistente cuya clave es el ID de la orden.

### Trabajo solicitado

- Reservar por ingrediente y cantidad antes de confirmar una orden.
- Agrupar ingredientes repetidos y procesarlos en orden estable.
- Evitar overselling con un decremento Mongo atómico y condicionado.
- Compensar reservas parciales sin incrementar ingredientes no reservados.
- Registrar reserva, estado e ítems para idempotencia persistente.
- Liberar exactamente una vez al cancelar o al fallar el guardado.
- Verificar concurrencia, compensación e idempotencia contra Mongo real.

### Restricciones técnicas obligatorias

- El descuento usa `ReactiveMongoTemplate.updateFirst()` con `_id`, `available=true` y `stockOnHand >= requested` en la misma consulta.
- No se usa `findById() + save()` para descontar stock.
- Un `TreeMap` agrega y ordena las cantidades antes de escribir.
- Las operaciones se componen con `Mono`, `Flux` y `concatMap`; no se introducen `block()` ni `subscribe()` en servicios.
- Se usa compensación verificable en lugar de una transacción Mongo multidocumento.
- `INSUFFICIENT_STOCK` se expresa como `ApiException` 409, compatible con TC-09.
- La clave interna de idempotencia es el ID generado de la orden; no se implementa un encabezado HTTP de idempotencia.
- La mensajería posterior al guardado conserva la semántica de TC-07; TC-16 no intenta resolverla con outbox.

### Criterios de aceptación

- [x] Dos reservas concurrentes con stock 1 producen un éxito y un `INSUFFICIENT_STOCK`.
- [x] El stock final del escenario concurrente es 0, nunca -1.
- [x] Un fallo en el tercer ingrediente libera los dos descuentos anteriores.
- [x] La reserva parcial fallida no queda en estado `RESERVED`.
- [x] Un reintento con el mismo ID no vuelve a descontar.
- [x] Una liberación repetida sólo incrementa una vez.
- [x] La cancelación permitida libera y después elimina la orden.
- [x] Un fallo de `OrderRepository.save()` libera antes de propagarse.
- [x] Los ingredientes repetidos se agregan antes de reservar.
- [x] Los ingredientes se procesan lexicográficamente.
- [x] Un ingrediente `available=false` no se reserva aunque tenga stock.
- [x] Las cantidades físicas no dependen del porcentaje del cupón.
- [x] Pricing, snapshots monetarios y total de TC-14/TC-15 se conservan.
- [x] Las pruebas críticas se ejecutan contra un proceso Mongo real.
- [x] No se adelantaron TC-25, TC-26 ni TC-29.

### Pruebas mínimas

- `shouldAllowOnlyOneConcurrentBuyerForStockOne`: lanza dos reservas sobre Mongo con stock 1; comprueba un éxito, un error `INSUFFICIENT_STOCK`, saldo 0 y disponibilidad desactivada.
- `shouldCompensateOnlyReservedIngredientsInStableOrder`: solicita `C, B, A`; el documento queda ordenado `A, B, C`. Al fallar C, A y B regresan a 10, C permanece en 0 y la reserva queda `RELEASED`.
- `shouldAggregateAndReserveSameIdOnlyOnce`: dos líneas requieren el mismo ingrediente en cantidades 2 y 3. Se reserva una sola entrada de 5 y repetir el mismo ID mantiene el stock en 5.
- `shouldReleaseOnlyOnce`: reserva 2, ejecuta dos liberaciones y comprueba stock original 10 y estado `RELEASED`.
- `shouldNotReserveUnavailableIngredientWithStock`: un ingrediente no disponible conserva sus 10 unidades y produce `INSUFFICIENT_STOCK`.
- `shouldReleaseReservationWhenOrderSaveFails`: verifica la secuencia `reserve → save fallido → release` y ausencia de evento.
- `shouldReservePhysicalQuantityIndependentOfCoupon`: un cupón del 50 % modifica el total, pero la reserva sigue recibiendo cantidad 3; también verifica `reserve → save → evento`.
- `shouldReleaseInventoryBeforeDeletingCancelableOrder`: comprueba `release → delete`.

## Cambios de código

### `InventoryReservation.java`

Se añadió el documento mínimo de idempotencia. Su `_id` y `orderId` son el ID de la orden; los únicos estados son `PENDING`, `RESERVED` y `RELEASED`.

```java
@Document(collection="inventoryReservations")
public class InventoryReservation {
  @Id
  private String id;
  private String orderId;
  private Status status;
  private List<ReservationItem> items = new ArrayList<>();

  public enum Status { PENDING, RESERVED, RELEASED }
}
```

La unicidad nativa de `_id` decide qué ejecución crea una reserva. Un reintento encuentra el registro existente y no inicia otro decremento.

### `InventoryService.java`

Agrupa ingredientes repetidos con `TreeMap`; por ello tanto el documento como las escrituras siguen un orden determinista.

```java
Map<String,Integer> required = new TreeMap<>();

for (Ingredient ingredient : ingredients) {
  required.merge(
      ingredient.getId(),line.getQuantity(),Integer::sum);
}
```

El decremento no lee y guarda la entidad. Mongo decide atómicamente si todavía hay unidades y el ingrediente continúa disponible:

```java
Query enoughStock = Query.query(Criteria.where("_id")
    .is(item.getIngredientId())
    .and("available").is(true)
    .and("stockOnHand").gte(item.getQuantity()));

Update decrement = new Update()
    .inc("stockOnHand",-item.getQuantity());

return mongo.updateFirst(enoughStock,decrement,Ingredient.class);
```

Los ítems se recorren con `concatMap`. La lista `reserved` pertenece a una única suscripción y sólo recibe un ítem después de un decremento confirmado. Ante error, se compensa esa lista y se vuelve a emitir el error original.

```java
return Flux.fromIterable(reservation.getItems())
    .concatMap(item -> decrement(item)
        .doOnNext(ignored -> reserved.add(item)))
    .then(markReserved(reservation.getId()))
    .onErrorResume(original -> compensate(reservation.getId(),reserved)
        .then(Mono.error(original)));
```

`release()` reclama atómicamente sólo un documento `RESERVED`. La primera llamada cambia el estado y devuelve sus ítems; las siguientes no encuentran un estado reclamable y terminan sin incrementar.

```java
Query claim = Query.query(Criteria.where("_id").is(reservationId)
    .and("status").is(Status.RESERVED));

return mongo.findAndModify(
        claim,Update.update("status",Status.RELEASED),
        FindAndModifyOptions.options().returnNew(true),
        InventoryReservation.class)
    .flatMap(reservation -> releaseItems(reservation.getItems()))
    .then();
```

### `OrderService.java`

Después del pricing y del cupón se genera el ID estable, se reserva, se guarda y finalmente se publica. Un fallo del guardado compensa; un fallo posterior de mensajería no intenta resolver el problema distribuido.

```java
order.setId(UUID.randomUUID().toString());
```

```java
.flatMap(order -> inventoryService.reserve(order)
    .flatMap(reservation -> repo.save(order)
        .onErrorResume(saveError -> inventoryService
            .release(reservation.getId())
            .then(Mono.error(saveError))))
    .flatMap(savedOrder ->
        Mono.fromRunnable(() -> orderMessages.sendOrder(savedOrder))
            .thenReturn(savedOrder)))
```

La cancelación reutiliza el ID de orden como ID de reserva y libera antes del borrado:

```java
return inventoryService.release(order.getId())
    .then(repo.deleteById(order.getId()));
```

## Cambios que no se realizaron

- No se usó una transacción Mongo multidocumento; el proyecto ejecuta Mongo standalone y se eligió compensación explícita.
- No se implementó una máquina completa de estados de orden.
- No se añadieron cola de cocina, claim, ETA, outbox, DLQ, retry de broker ni transacciones distribuidas.
- No se añadió un contrato HTTP `Idempotency-Key`.
- No se modificaron precios, `unitPriceAtPurchase`, subtotales, descuento ni total.
- No se calcula inventario desde el importe descontado.
- No se creó un módulo Maven, repositorio adicional ni interfaz innecesaria.
- No se cambió el flujo legacy de órdenes por correo, que no utiliza las líneas valoradas de TC-14.

## Resultado

TC-16 evita overselling por ingrediente mediante un `$inc` condicionado y demostrado bajo concurrencia real. La atomicidad de esa operación garantiza que un ingrediente individual nunca se descuente por debajo del stock disponible, incluso si dos compradores compiten al mismo tiempo.

Esa garantía no convierte una orden de diez ingredientes en una operación atómica: cada ingrediente sigue siendo un documento y una escritura distinta, por lo que puede ocurrir `A ✓, B ✓, C ✗`. Para cubrir la garantía que falta a nivel de orden, esta implementación conserva exactamente qué decrementos tuvieron éxito y los compensa dentro de la misma cadena reactiva. Es la alternativa mínima a una transacción Mongo multidocumento compatible con el Mongo standalone actual.

Las cinco pruebas de integración ejecutadas contra `mongod` real pasan, al igual que las 37 pruebas focalizadas de órdenes, cancelación, DTO, pricing y cupones. Las regresiones amplias conservan fallos preexistentes en fixtures de TC-09/TC-13 y seguridad: no registran correctamente el advice WebFlux/MVC o carecen de configuración de prueba. Esos fallos no afectan las consultas atómicas, compensación, idempotencia ni liberación implementadas en TC-16.
