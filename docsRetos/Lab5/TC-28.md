# TC-28 — Elegir broker en runtime, no editando el POM

## Descripción del TC

TC-28 sustituye la selección manual de dependencias Maven por una elección exclusiva de transporte en runtime. El contrato común de TC-27 permanece intacto y el proceso ejecutable contiene los cuatro adaptadores disponibles.

### Resultado funcional

`tacocloud.messaging.transport` acepta `noop`, `jms`, `rabbit` o `kafka`. Cada valor registra una sola implementación de `OrderMessagingService`; un valor desconocido, una selección insegura en producción o una cardinalidad distinta de uno impiden el arranque.

Cambiar de RabbitMQ a Kafka requiere cambiar configuración externa y reiniciar la aplicación. No requiere editar Java, comentar dependencias, modificar el POM ni recompilar con fuentes diferentes.

### Archivos modificados o creados

- Ensamblado: `tacocloud/tacocloud/pom.xml` y `tacocloud/tacocloud-api/pom.xml`.
- Selección y validación: `MessagingSelectionConfiguration.java` y `MessagingSelectionConfigurationTest.java`.
- Noop: `NoopMessagingConfig.java`, `NoOpOrderMessagingService.java` y POM del módulo.
- JMS: `JmsMessagingConfig.java` y `JmsOrderMessagingService.java`.
- RabbitMQ: `RabbitMessagingConfig.java` y `RabbitOrderMessagingService.java`.
- Kafka: `KafkaMessagingConfig.java`, `KafkaOrderMessagingService.java` y POM del módulo.
- Cocina: configuraciones JMS/Rabbit renombradas, listeners y receptores condicionados, y `application.yml` externalizado.
- Configuración desplegable: `tacocloud/tacocloud/src/main/resources/application.yml`.
- Se eliminaron los `application.yml` duplicados de API y adaptadores y las cuatro clases genéricas `MessagingConfig` reemplazadas.

### Trabajo solicitado

- Incluir noop, JMS, RabbitMQ y Kafka en el ensamblado ejecutable.
- Seleccionar uno mediante `tacocloud.messaging.transport`.
- Mantener el único puerto `OrderMessagingService` de TC-27.
- Externalizar destinos, hosts y credenciales de brokers.
- Impedir fallback silencioso ante configuración inválida o productiva incompleta.
- Verificar el ensamblado con `ApplicationContextRunner` sin brokers reales.

### Restricciones técnicas obligatorias

- La API depende del contrato, no de adaptadores concretos.
- El módulo ejecutable es el composition root y depende de los cuatro adaptadores.
- No hay `switch` ni `if` de transporte en servicios o controladores.
- Las condiciones de los cuatro adaptadores son mutuamente exclusivas.
- No se usa `@Primary` para ocultar múltiples implementaciones.
- Los destinos no están codificados en Java.
- Las credenciales versionadas son variables de entorno con defaults exclusivamente locales; no se incluyen secretos reales.
- No se cambió `tacocloud-messaging-contract`.

### Criterios de aceptación

- `noop`, `jms`, `rabbit` y `kafka` producen exactamente un bean del puerto.
- Ausencia de propiedad en ejecución local, `dev` o `test` produce noop.
- `prod` y `production` requieren elección explícita y rechazan noop.
- `integration` también requiere un broker explícito.
- Un valor no admitido muestra `noop, jms, rabbit, kafka` y aborta.
- Un segundo bean accidental aborta el contexto.
- Productor y cocina leen destino/topic desde propiedades.
- Los perfiles de cocina ya no eligen broker; `template` sólo elige el modo alternativo de recepción de TC-26.

### Pruebas mínimas

`MessagingSelectionConfigurationTest` contiene 13 escenarios: los cuatro transportes, cardinalidad real del mapa de beans, default local, perfiles dev/test, prod sin propiedad, noop explícito en prod, broker explícito en prod, valor inválido, dos implementaciones, dos destinos JMS distintos y ausencia de credenciales broker legacy. Los templates JMS/Rabbit/Kafka son mocks, por lo que ninguna prueba abre conexiones.

También se ejecutan las pruebas del contrato TC-27, los módulos de adaptador, cocina y las regresiones del mapper y workflows de orden.

## Cambios de código

### Ensamblado Maven

`tacocloud/tacocloud/pom.xml` incorpora los cuatro adaptadores. Es el único módulo que conoce el conjunto de implementaciones disponibles. `tacocloud-api/pom.xml` conserva sólo `tacocloud-messaging-contract` y elimina tanto la dependencia fija a noop como los bloques comentados para JMS/Rabbit/Kafka. Esto elimina la selección por edición de POM y no crea ciclos: API → contrato; ejecutable → API + adaptadores; adaptadores → contrato.

### Noop

`NoOpOrderMessagingService` deja de ser un `@Service` incondicional. `NoopMessagingConfig` lo registra cuando el transporte es `noop` o falta en un entorno local. No abre conexiones ni modifica el evento. Su POM añade únicamente Spring Boot autoconfigure para evaluar la condición.

### JMS

La antigua `tacos.messaging.MessagingConfig` se reemplaza por `JmsMessagingConfig`, evitando la colisión FQCN con Rabbit. La configuración crea el adaptador y el converter sólo con `transport=jms`. `JmsOrderMessagingService` recibe `tacocloud.messaging.jms.destination` por constructor y sigue publicando `OrderEvent` del contrato común.

### RabbitMQ

La antigua `tacos.messaging.MessagingConfig` se reemplaza por `RabbitMessagingConfig`. Sólo se carga con `transport=rabbit`, configura el converter JSON y construye `RabbitOrderMessagingService` con `tacocloud.messaging.rabbit.destination`. No introduce un puerto alternativo ni tipos de Rabbit en el contrato.

### Kafka

`KafkaMessagingConfig` se crea con condición `transport=kafka`. Construye `KafkaOrderMessagingService` con `tacocloud.messaging.kafka.topic`; el topic deja de estar codificado en Java. El POM incorpora sólo la dependencia de autoconfiguración necesaria para la condición.

### Validación del arranque

`MessagingSelectionConfiguration` valida los cuatro valores permitidos, restringe el default noop a ejecución local/dev/test, exige elección fuera de esos entornos, rechaza noop en producción/integración y cuenta las instancias reales de `OrderMessagingService`. El error ocurre durante el arranque y explica la propiedad o la cardinalidad incorrecta.

### Configuración externa

El `application.yml` del ejecutable centraliza:

- `tacocloud.messaging.jms.destination` / `TACOCLOUD_JMS_DESTINATION`.
- `tacocloud.messaging.rabbit.destination` / `TACOCLOUD_RABBIT_DESTINATION`.
- `tacocloud.messaging.kafka.topic` / `TACOCLOUD_KAFKA_TOPIC`.
- Artemis mediante `ARTEMIS_HOST`, `ARTEMIS_PORT`, `ARTEMIS_USERNAME`, `ARTEMIS_PASSWORD`.
- RabbitMQ mediante `RABBIT_HOST`, `RABBIT_PORT`, `RABBIT_USERNAME`, `RABBIT_PASSWORD`.
- Kafka mediante `KAFKA_BOOTSTRAP_SERVERS`.

Los defaults `localhost` y `guest` son únicamente conveniencias de laboratorio local; un despliegue productivo debe inyectar sus valores externos. Se eliminaron de API/JMS los usuarios, passwords y hosts de ejemplo que antes estaban versionados.

### Cocina

`JmsKitchenMessagingConfig` y `RabbitKitchenMessagingConfig` sustituyen los nombres genéricos y quedan condicionadas por la misma propiedad de transporte. Los listeners JMS, Rabbit y Kafka también se seleccionan por esa propiedad. Los receptores por template conservados de TC-26 se activan sólo con el perfil neutral `template`; ya no existen perfiles de broker combinables. Listeners y receptores leen destination/topic de configuración y siguen consumiendo `OrderEvent`, no entidades Mongo.

### Pruebas

`MessagingSelectionConfigurationTest` usa `ApplicationContextRunner` con `JmsTemplate`, `RabbitTemplate` y `KafkaTemplate` simulados. Además de identificar la clase seleccionada, inspecciona `getBeansOfType(OrderMessagingService.class)` y exige tamaño uno. Una prueba envía un evento fijo a dos contextos JMS con destinos distintos y verifica el valor recibido por el template, demostrando que el destino no está hardcodeado.

## Cambios que no se realizaron

TC-29:
outbox transaccional.

TC-30:
retry, DLQ y consumidor idempotente.

TC-31:
propagación completa de correlation ID.

No se modificaron `OrderEvent`, `OrderEventPayload`, `OrderEventType` ni `OrderMessagingService`; tampoco se añadió conectividad real a brokers en las pruebas de contexto.

## Relación entre requisitos e implementación

| Requisito | Implementación |
| --- | --- |
| Selección runtime | `tacocloud.messaging.transport` |
| noop | `NoopMessagingConfig` condicional |
| JMS | `JmsMessagingConfig` condicional |
| Rabbit | `RabbitMessagingConfig` condicional |
| Kafka | `KafkaMessagingConfig` condicional |
| Puerto único | `OrderMessagingService` de TC-27 |
| Un solo bean | condiciones exclusivas + validador + conteo en tests |
| Invalid transport | fallo de startup con valores permitidos |
| Config collision | configuraciones específicas renombradas |
| Destinos externos | propiedades JMS/Rabbit/Kafka |
| Hosts externos | variables de entorno de Artemis/Rabbit/Kafka |
| Credenciales fuera de Git | variables de entorno y eliminación de secretos broker legacy |
| Noop dev/test | condición `matchIfMissing` + política validada |
| Noop no prod | validador rechaza ausencia y noop |
| Sin editar POM | cuatro adaptadores ensamblados de forma permanente |
| Tests sin broker | `ApplicationContextRunner` con templates mock |

Los perfiles son apropiados para agrupar entornos como dev, test, prod o integration. Usar perfiles independientes por broker permite activar accidentalmente `rabbit + kafka` y registrar implementaciones simultáneas. Una propiedad representa mejor la elección exclusiva porque tiene un único valor validable. Por eso los perfiles describen el entorno o el modo `template`, mientras `tacocloud.messaging.transport` selecciona el adaptador.

## Resultado

TC-28 queda implementado: cambiar de broker es una operación de configuración externa, existe exactamente un puerto activo, la producción no cae silenciosamente en noop, los destinos y conexiones son desplegables y las pruebas de selección no necesitan infraestructura externa.

Las validaciones focalizadas pasan. El reactor completo sigue encontrando el fallo ambiental preexistente de `npm install` en la UI legacy por permisos sobre la caché global; no afecta los módulos Java ni los criterios de TC-28.
