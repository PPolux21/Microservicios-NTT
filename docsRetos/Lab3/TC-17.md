# TC-17 — Etiquetas dietarias, alérgenos y nivel de picante

## Descripción del TC

### Resultado funcional

Los ingredientes almacenan metadata dietaria tipada y TacoCloud deriva la clasificación de un taco a partir de los ingredientes reales del catálogo. El catálogo, el endpoint `GET /api/tacos/{id}/classification` y el quote exponen etiquetas dietarias, alérgenos, nivel de picante y un disclaimer académico.

### Trabajo solicitado

- Incorporar `dietaryTags`, `allergens` y `spiceLevel` al ingrediente.
- Derivar la clasificación del taco en el servidor.
- Aplicar reglas universales para `VEGAN`, `VEGETARIAN` y `GLUTEN_FREE`.
- Unir todos los alérgenos y elegir el máximo nivel de picante.
- Exponer la clasificación en catálogo, endpoint específico y quote.
- Impedir que los campos enviados por el cliente sean la verdad de la clasificación.
- Incluir un disclaimer sobre contaminación cruzada.

### Restricciones técnicas obligatorias

- Los conceptos cerrados se representan mediante enums, no mediante strings libres.
- Una propiedad “sin X” sólo se afirma si todos los ingredientes la cumplen.
- Un único ingrediente con un alérgeno basta para incluirlo en el resultado.
- El picante se obtiene de forma determinista mediante el máximo nivel.
- La clasificación se calcula con ingredientes resueltos desde el catálogo.
- No se agregaron suscripciones ni bloqueos en servicios reactivos.
- La autorización existente mantiene la escritura de metadata bajo rutas protegidas para `ADMIN`.

### Criterios de aceptación

- [x] La metadata dietaria del ingrediente usa enums.
- [x] Un ingrediente no vegano elimina `VEGAN` de la clasificación.
- [x] `VEGETARIAN` y `GLUTEN_FREE` también requieren que todos los ingredientes cumplan.
- [x] Los alérgenos forman la unión exacta, sin duplicados.
- [x] El picante corresponde al máximo y no depende del orden.
- [x] El cliente no puede falsificar la clasificación mediante el POST de tacos.
- [x] El endpoint de clasificación devuelve datos derivados para tacos existentes.
- [x] Un taco inexistente produce `TACO_NOT_FOUND` con estado 404 mediante el manejo de TC-09.
- [x] El catálogo expone clasificación derivada y disclaimer.
- [x] El quote expone clasificación sin alterar pricing, cupones o inventario.
- [x] Los datos de desarrollo contienen metadata coherente para demostrar las reglas.
- [ ] Los filtros de TC-19 consumen la clasificación. Se difiere expresamente hasta implementar TC-19.

### Pruebas mínimas

`TacoClassificationServiceTest` verifica la intersección de las tres etiquetas dietarias, la unión exacta de múltiples alérgenos y el máximo nivel de picante en dos órdenes distintos.

`TacoControllerTest` comprueba catálogo clasificado, endpoint existente, error 404 y mass assignment: aunque el JSON declara un taco vegano, el ingrediente persistido no vegano controla el resultado.

`OrderServiceTest` verifica que quote incluye `dietaryTags`, `allergens`, `spiceLevel` y disclaimer calculados con los ingredientes ya resueltos por pricing.

`IngredientControllerTest` comprueba la persistencia y respuesta de metadata tipada al actualizar un ingrediente.

## Cambios de código

### `Ingredient.java`

Se agregaron los enums y sus campos persistentes con valores seguros por defecto:

```java
private Set<DietaryTag> dietaryTags = EnumSet.noneOf(DietaryTag.class);
private Set<Allergen> allergens = EnumSet.noneOf(Allergen.class);
private SpiceLevel spiceLevel = SpiceLevel.NONE;

public enum DietaryTag { VEGAN, VEGETARIAN, GLUTEN_FREE }
public enum Allergen { GLUTEN, DAIRY, EGG, PEANUT, TREE_NUT, SOY }
public enum SpiceLevel { NONE, MILD, MEDIUM, HOT, EXTREME }
```

Estos datos describen al ingrediente y no dependen de stock, disponibilidad ni de una orden.

### `TacoClassificationService.java`

Centraliza todas las políticas derivadas. Primero resuelve por identificador los ingredientes reales y después calcula la clasificación:

```java
dietaryTags = EnumSet.allOf(DietaryTag.class);
for (Ingredient ingredient : safeIngredients) {
  dietaryTags.retainAll(ingredient.getDietaryTags());
}
```

Los alérgenos se acumulan mediante unión y el picante usa el máximo ordinal:

```java
allergens.addAll(ingredient.getAllergens());
if (ingredientSpice.ordinal() > spiceLevel.ordinal()) {
  spiceLevel = ingredientSpice;
}
```

Datos del ingrediente: qué etiquetas posee, qué alérgenos contiene y su nivel de picante. Políticas derivadas del producto: todas las etiquetas dietarias requieren unanimidad, los alérgenos se unen y el picante es el máximo de la composición completa.

### `ApiDtos.java`

Los DTO públicos de ingrediente incluyen metadata tipada. Se añadieron `TacoClassificationResponse` y `TacoCatalogResponse`, y `OrderQuoteResponse` incluye una lista de clasificaciones porque un quote puede contener varias líneas de tacos. Los DTO de entrada de órdenes continúan sin campos derivados controlados por el cliente.

### `ApiMapper.java`

Mapea metadata de ingredientes mediante copias de `EnumSet`, normaliza documentos legacy sin picante a `NONE` y crea respuestas de catálogo/quote a partir del resultado de `TacoClassificationService`:

```java
return new TacoClassificationResponse(
    taco.getId(), taco.getName(),
    copyDietaryTags(classification.getDietaryTags()),
    copyAllergens(classification.getAllergens()),
    classification.getSpiceLevel(),
    TacoClassificationService.DISCLAIMER);
```

### `IngredientController.java`

El PUT administrativo existente actualiza también `dietaryTags`, `allergens` y `spiceLevel`. No se creó ningún endpoint público adicional de escritura.

### `TacoController.java`

El catálogo y las consultas por identificador retornan DTOs clasificados. El nuevo endpoint reutiliza exactamente la misma función:

```java
@GetMapping("/{id}/classification")
public Mono<TacoClassificationResponse> classification(String id) {
  return findTaco(id)
      .flatMap(classificationService::classify)
      .map(ApiMapper::toClassificationResponse);
}
```

Un identificador inexistente produce `ApiException.notFound("TACO_NOT_FOUND", ...)`.

### `OrderService.java`

Quote reutiliza los ingredientes que `priceItems` ya resolvió. No vuelve a consultar el catálogo ni modifica las reglas monetarias:

```java
classificationService.classifyIngredients(
    item.getTaco().getIngredients())
```

El resultado se incorpora a `OrderQuote`; cantidades, subtotal, cupón, total e inventario conservan los flujos de TC-14, TC-15 y TC-16.

### `DevelopmentConfig.java`

Los ingredientes de desarrollo recibieron metadata académica coherente: tortilla de harina con `GLUTEN`, quesos y crema con `DAIRY`, vegetales con etiquetas vegetales y salsa con picante `MEDIUM`.

### Pruebas modificadas y nuevas

`TacoClassificationServiceTest`, `TacoControllerTest`, `OrderServiceTest` e `IngredientControllerTest` ligan cada aserción a las reglas del reto. `OrderApiControllerTest` sólo adapta la construcción del quote a su nuevo campo seguro, sin modificar su comportamiento previo.

## Cambios que no se realizaron

TC-18: no se implementaron reglas de validación de diseño, límites de ingredientes, prohibiciones por combinación ni `POST /api/tacos/validate`.

TC-19: no se implementaron búsqueda, filtros dietarios, exclusión de alérgenos, ordenamiento, paginación ni repositorios personalizados.

La clasificación queda centralizada y reutilizable para los filtros de TC-19. La integración efectiva de búsqueda y filtrado se realizará al implementar TC-19; por ello su criterio permanece deliberadamente sin marcar como verificado.

Tampoco se mezcló clasificación con `available`, `stockOnHand`, reserva de inventario, pricing o descuentos.

## Resultado

TC-17 incorpora una única fuente de verdad para clasificación dietaria. La metadata persistida pertenece a cada ingrediente; las propiedades del taco son resultados derivados en el servidor. Catálogo, endpoint específico y quote reutilizan el mismo servicio, el cliente no puede convertir una composición con carne en vegana y el disclaimer evita presentar la metadata académica como garantía médica o de contaminación cruzada.
