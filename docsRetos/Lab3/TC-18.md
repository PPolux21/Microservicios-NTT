# TC-18 — Taco Physics: reglas componibles de diseño

## Descripción del TC

### Resultado funcional

Los diseños de tacos se validan ahora con un conjunto componible de reglas antes de guardarse, cotizarse o alcanzar la reserva de inventario. `POST /api/tacos/validate` devuelve todas las violaciones con códigos estables y no produce efectos secundarios. La creación de tacos, la cotización y la creación de órdenes reutilizan el mismo `TacoDesignValidator`.

### Trabajo solicitado

- Definir un contrato pequeño para reglas de diseño.
- Componer reglas mediante un validador central inyectado por Spring.
- Resolver los ingredientes una vez y compartir un contexto común.
- Validar exactamente una base, entre 2 y 12 ingredientes, ausencia de duplicados y disponibilidad.
- Incorporar dos reglas adicionales configurables sin IDs mágicos.
- Acumular todas las violaciones y devolverlas con códigos estables.
- Exponer `POST /api/tacos/validate` sin persistencia, inventario ni eventos.
- Reutilizar la misma validación antes de crear tacos, cotizar y crear órdenes.

### Restricciones técnicas obligatorias

- Las reglas no consultan repositorios ni lanzan excepciones para una violación normal.
- El validador recibe `List<TacoDesignRule>`; no instancia ni enumera reglas concretas.
- La base se reconoce por `Ingredient.Type.WRAP`, nunca por un identificador concreto.
- La disponibilidad usa `Ingredient.available` y no se deduce del stock.
- La clasificación dietaria y el picante se obtienen mediante `TacoClassificationService` de TC-17.
- Se ejecutan todas las reglas y el resultado se ordena por código para hacerlo determinista.
- No se agregaron `block()` ni `subscribe()` a servicios.
- No se implementaron búsquedas, filtros, paginación ni ordenamiento de TC-19.

Por comportamiento, la solución es principalmente una **composición de Specifications**: cada regla evalúa de forma independiente el mismo contexto y devuelve cero o más violaciones. No es una Chain of Responsibility clásica porque ninguna regla decide si se ejecuta la siguiente y no hay cortocircuito; todas se evalúan. Cada regla también actúa como una estrategia intercambiable, pero el comportamiento dominante es la composición y acumulación de especificaciones.

### Criterios de aceptación

- [x] Existe un contrato `TacoDesignRule` con violaciones que separan `code` y `message`.
- [x] El validador central recibe la colección de reglas por inyección.
- [x] Una regla fake se incorpora sin modificar el validador.
- [x] Se exige exactamente una base a partir de metadata de dominio.
- [x] Se aceptan 2 y 12 ingredientes, y se rechazan 1 y 13.
- [x] Los ingredientes repetidos se detectan explícitamente.
- [x] Un ingrediente con `available=false` invalida el diseño aunque tenga stock.
- [x] Existen dos reglas adicionales configurables: picante extremo y modo vegano.
- [x] Se devuelven todas las violaciones y el orden de las reglas no cambia el conjunto final.
- [x] Los ingredientes se resuelven una vez por identificador y las reglas reutilizan el contexto.
- [x] `POST /api/tacos/validate` no guarda tacos ni órdenes y no reserva inventario.
- [x] Crear tacos, cotizar y crear órdenes usan el mismo validador.
- [x] Un diseño inválido no llega a reserva ni persistencia de la orden.
- [x] No hay IDs mágicos en las reglas.
- [x] No se adelantó TC-19.

### Pruebas mínimas

`TacoDesignValidatorTest` contiene nueve pruebas que cubren de forma independiente las seis reglas, los límites 1/2/12/13, un diseño válido, múltiples fallos, invariancia ante el orden de reglas y extensibilidad mediante una regla fake.

`TacoControllerTest` comprueba el endpoint funcional con varias violaciones, ausencia de persistencia y una sola consulta para un ingrediente repetido. También conserva la prueba de mass assignment de TC-17.

`OrderServiceTest` comprueba que creación y quote rechazan el mismo diseño con `TACO_DESIGN_INVALID`, conservan el mismo código de violación y no invocan `InventoryService.reserve()` ni `OrderRepository.save()`. El caso repetido verifica además una consulta por identificador en cada flujo.

Se ejecutaron 57 pruebas seleccionadas sin fallos, incluidas regresiones de DTOs, cupones, clasificación y las cinco pruebas de inventario con Mongo embebido real.

## Cambios de código

### `TacoDesignValidator.java`

Centraliza la resolución del catálogo, construye el contexto compartido, ejecuta todas las reglas inyectadas y ordena las violaciones. `distinct()` evita repetir consultas, pero se conservan los IDs originales para detectar duplicados.

```java
return Flux.fromIterable(ids)
    .distinct()
    .concatMap(id -> ingredientRepo.findById(id))
    .collectMap(Ingredient::getId, ingredient -> ingredient,
        LinkedHashMap::new)
    .map(byId -> ids.stream().map(byId::get)
        .collect(Collectors.toList()))
    .map(ingredients -> validateResolved(name, ids, ingredients));
```

La extensibilidad proviene de la colección inyectada:

```java
public TacoDesignValidator(IngredientRepository ingredientRepo,
    TacoClassificationService classificationService,
    List<TacoDesignRule> rules) {
  this.ingredientRepo = ingredientRepo;
  this.classificationService = classificationService;
  this.rules = new ArrayList<>(rules);
}
```

### `TacoDesignRules.java`

Agrupa seis beans pequeños para no crear una clase por regla. Las reglas obligatorias usan metadata y datos ya resueltos; las adicionales usan clasificación de TC-17 y configuración.

```java
long bases = context.getResolvedIngredients().stream()
    .filter(ingredient -> ingredient.getType() == Type.WRAP)
    .count();
```

```java
return context -> !allowExtremeSpice
    && context.getClassification().getSpiceLevel() == SpiceLevel.EXTREME
        ? one("EXTREME_SPICE_NOT_ALLOWED",
            "Extreme spice designs are disabled by configuration.")
        : Collections.emptyList();
```

### `TacoController.java`

La creación valida antes de guardar y sustituye las referencias recibidas por ingredientes reales del catálogo. El nuevo endpoint sólo transforma el resultado funcional del validador.

```java
@PostMapping(path="/validate", consumes="application/json")
public Mono<TacoDesignValidationResponse> validate(
    @Valid @RequestBody TacoDesignRequest request) {
  return designValidator.validate(request.getName(), request.getIngredientIds())
      .map(ApiMapper::toResponse);
}
```

### `OrderService.java`

El camino común `priceItems` es utilizado tanto por create como por quote. Cada línea resuelve sus ingredientes distintos una sola vez y valida antes del cálculo económico. En create, esto ocurre antes de la reserva de TC-16 y del guardado.

```java
TacoDesignValidator.ValidationResult validation =
    designValidator.validateResolved(
        itemCommand.getTaco().getName(), ingredientIds, ingredients);
if (!validation.isValid()) {
  return Mono.error(designValidator.invalidDesign(validation));
}
```

### `ApiDtos.java`

Añade `TacoDesignRequest`, `TacoDesignValidationResponse` y `TacoDesignViolationResponse` dentro del contenedor existente. La respuesta sólo expone `valid`, `code` y `message`.

```java
public static class TacoDesignViolationResponse {
  private String code;
  private String message;
}
```

### `ApiMapper.java`

Convierte el resultado de dominio del validador al DTO seguro sin duplicar reglas.

### `ApiExceptionHandler.java`

Amplía `ApiException` de TC-09 para transportar opcionalmente violaciones estructuradas. Los constructores existentes conservan una lista vacía, por lo que los contratos previos no cambian.

```java
public static ApiException unprocessable(String code, String detail,
    List<Violation> violations) {
  return new ApiException(
      HttpStatus.UNPROCESSABLE_ENTITY, code, detail, violations);
}
```

## Cambios que no se realizaron

- No se cambió la actualización atómica, compensación ni idempotencia de inventario de TC-16.
- No se duplicó la clasificación dietaria de TC-17.
- No se añadió un motor externo de reglas ni una clase por cada DTO o regla.
- No se implementó TC-19: búsqueda, filtros, paginación y sort.
- No se modificaron precios, cupones, snapshots ni cantidades de TC-14/TC-15.

## Resultado

TC-18 queda implementado con reglas componibles y reutilizadas por validación, creación de tacos, quote y creación de órdenes. Los diseños inválidos se rechazan antes de cualquier reserva o persistencia, las consultas de catálogo no se repiten por regla y la configuración permite activar o desactivar las dos políticas adicionales. Las pruebas enfocadas y las regresiones seleccionadas finalizaron sin fallos.
