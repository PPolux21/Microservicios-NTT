# TC-21 — Favoritos por usuario sin confiar en userId del cliente

## Descripción del TC

### Resultado funcional

Un usuario autenticado puede marcar, desmarcar y consultar sus tacos favoritos mediante rutas `/me`. La relación se persiste en MongoDB y su propietario se obtiene exclusivamente de `Authentication`; ninguna entrada HTTP permite seleccionar un `userId`. El listado reutiliza el DTO de catálogo de TC-19, está paginado y conserva el estado después de recargar la UI.

### Trabajo solicitado

- Implementar `PUT`, `DELETE` y `GET /api/users/me/favorites`.
- Persistir únicamente `userId`, `tacoId` y la fecha necesaria para ordenar.
- Obtener el propietario desde el usuario autenticado.
- Hacer PUT y DELETE idempotentes, incluso ante altas concurrentes.
- Comprobar que el taco existe antes del alta.
- Aislar todas las consultas y eliminaciones por usuario.
- Paginar el listado con los límites de TC-19 y devolver DTOs de catálogo existentes.
- Limpiar favoritos huérfanos cuando se consultan.
- Proteger las rutas y restaurar el estado persistido en la UI.

### Restricciones técnicas obligatorias

- No existe ruta `/api/users/{userId}/favorites`, parámetro `userId` ni DTO de entrada con propietario.
- `Favorite` no almacena objetos `User` o `Taco` completos.
- MongoDB impone un índice compuesto único sobre `(userId, tacoId)`.
- La duplicación concurrente se traduce a éxito idempotente; no se filtra el error Mongo.
- DELETE usa siempre `userId + tacoId` y responde `204` aunque la relación ya no exista.
- El flujo de servicio es reactivo y no incorpora `block()` ni `subscribe()`.
- Se conserva el deny-by-default de TC-11.
- No se agregaron calificaciones, historial ni reordenamiento.

### Criterios de aceptación

- [x] La identidad procede de `Authentication.getName()` y `UserRepository`.

### Pruebas mínimas

`FavoriteServiceMongoIntegrationTest` usa Mongo embebido real y comprueba:

## Cambios de código

### `Favorite.java`

Representa únicamente la relación y declara la garantía final de concurrencia en MongoDB:

```java
@Document("favorites")
@CompoundIndex(
    name="favorite_user_taco_unique",
    def="{'userId': 1, 'tacoId': 1}",
    unique=true)
public class Favorite {
  private String id;
  private final String userId;
  private final String tacoId;
  private final Date createdAt;
}
```

El constructor anotado con `@PersistenceConstructor` permite reconstruir el documento sin agregar setters de ownership.

### `FavoriteRepository.java`

Expone sólo las consultas necesarias y todas las operaciones funcionales quedan acotadas por usuario:

```java
Flux<Favorite> findByUserId(String userId,Pageable pageable);
Mono<Long> countByUserId(String userId);
Mono<Long> deleteByUserIdAndTacoId(String userId,String tacoId);
```

No existe un método administrativo para listar favoritos de todos los usuarios.

### `FavoriteService.java`

Resuelve primero al usuario autenticado, valida el taco y deja que el índice resuelva la carrera de inserción. Una clave duplicada significa que el estado solicitado por PUT ya existe:

```java
return currentUser(authentication)
    .flatMap(user -> tacoRepo.existsById(tacoId)
        .flatMap(exists -> exists
            ? favoriteRepo.save(new Favorite(user.getId(),tacoId)).then()
            : Mono.error(ApiException.notFound(
                "TACO_NOT_FOUND","Taco does not exist."))))
    .onErrorResume(DuplicateKeyException.class,error -> Mono.empty());
```

La identidad nunca llega como argumento externo distinto de `Authentication`:

```java
return userRepo.findByUsername(authentication.getName())
    .switchIfEmpty(Mono.error(ApiException.notFound(
        "USER_NOT_FOUND","Authenticated user does not exist.")));
```

DELETE usa la clave del propietario y GET pagina por ella. Durante GET, un taco ausente provoca la eliminación reactiva del favorito y éste no aparece en la respuesta.

### `FavoriteController.java`

Publica exactamente las rutas solicitadas y conserva la responsabilidad HTTP en el controlador:

```java
@RequestMapping("/api/users/me/favorites")
@PutMapping("/{tacoId}")
@DeleteMapping("/{tacoId}")
@GetMapping
```

PUT y DELETE responden `204 No Content`. GET valida `page >= 0`, `size >= 1` y el límite `tacocloud.search.max-page-size`, reutilizado de TC-19.

### `ApiDtos.java` y `ApiMapper.java`

`FavoriteQuery` sólo contiene `page` y `size`. `FavoritePageResponse` reutiliza el DTO público de catálogo:

```java
private List<TacoCatalogResponse> items;
private int page;
private int size;
private long totalElements;
private int totalPages;
```

`ApiMapper` convierte las clasificaciones con el mapper ya existente; no introduce un segundo `TacoResponse` ni expone campos internos del favorito.

### `User.java`

Se hizo explícito el constructor que Spring Data usa al reconstruir usuarios autenticados desde Mongo:

```java
@PersistenceConstructor
public User(String username,String password,String fullname, /* ... */) {
  this.username = username;
  // asignación de los campos persistentes finales
}
```

Este ajuste mínimo conserva el contrato de TC-10 y permite que favoritos resuelva de forma fiable `authentication.getName()` a `User.id`.

### `SecurityConfig.java`

La matriz de TC-11 incorpora únicamente la nueva familia de rutas antes del `denyAll()`:

```java
.antMatchers("/api/users/me/favorites/**")
.hasAnyRole("USER","ADMIN")
```

No se añadió un rol específico ni se abrió ninguna ruta por ID de usuario.

### `FavoriteControllerTest.java`, `FavoriteServiceMongoIntegrationTest.java` y `SecurityConfigTest.java`

Las pruebas separan contrato, persistencia concurrente y autorización. La prueba de concurrencia ejecuta ambas altas sobre Mongo real:

```java
.then(Flux.merge(
    service.addFavorite("TACO-1",alice),
    service.addFavorite("TACO-1",alice)).then())
.then(favoriteRepo.countByUserId("U-A"));
```

Después comprueba tanto el recuento `1` como `IndexInfo.isUnique()`.

### `ApiService.ts` y `RecentTacosService.ts`

La UI incorporó PUT/DELETE y construye sólo contratos `/me`:

```typescript
addFavorite(tacoId: string) {
  return this.apiService.put(
      '/api/users/me/favorites/' + encodeURIComponent(tacoId), {});
}
```

El servicio no envía cuerpo con identidad ni guarda favoritos en memoria como fuente definitiva.

### `recents.component.ts` y `recents.component.html`

El componente carga favoritos desde backend al inicializarse, mantiene un mapa sólo para presentación y vuelve a consultar después de cada cambio:

```typescript
ngOnInit() {
  this.recentTacosService.getRecentTacos()
      .subscribe(page => this.recentTacos = page.items);
  this.reloadFavorites();
}
```

La plantilla presenta `♡`/`♥`, permite alternar el estado y muestra el listado persistente sin crear otro catálogo.

### `app.component.spec.ts`

Comprueba que GET, PUT y DELETE usan `/api/users/me/favorites`, que ninguna solicitud contiene `userId` y que una nueva inicialización restaura `favoriteIds` a partir del GET del backend.

Tampoco se creó un endpoint administrativo de favoritos, un evento de cascada, un scheduler de limpieza, un mapper específico ni un estado en `localStorage`. La disponibilidad y el stock no condicionan una preferencia; sólo se exige que el taco exista al marcarlo.

### ¿Qué diferencia práctica hay entre POST y PUT para “marcar favorito”?

`PUT /api/users/me/favorites/{tacoId}` expresa “este taco debe estar en mis favoritos”. La pareja `userId + tacoId` identifica naturalmente la relación, por lo que repetir PUT mantiene el mismo estado final. `POST` suele crear un recurso subordinado cuya identidad asigna el servidor y varias llamadas podrían representar varias creaciones si no se añadiera deduplicación. PUT refleja directamente la semántica idempotente exigida aquí.

## Resultado

TC-21 queda implementado con ownership derivado de autenticación, persistencia mínima, unicidad concurrente garantizada por MongoDB, operaciones PUT/DELETE idempotentes, listado paginado aislado y UI respaldada por el backend. Las 6 pruebas nuevas de API, las 4 de seguridad, las 5 de regresión de catálogo TC-19 y las 6 de Angular finalizaron correctamente.

La regresión heredada `RegistrationControllerTest.shouldReturnConflictForDuplicates` continúa fallando con un `NullPointerException` que ya existía antes de TC-21 y no afecta el flujo de favoritos. No se modificó ese comportamiento ajeno al reto.
