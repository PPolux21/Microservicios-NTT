# TC-31 — Correlation ID de HTTP a evento y logs

## Descripción del TC

TC-31 incorpora un identificador de correlación seguro que acompaña una operación desde HTTP hasta los eventos de orden, el outbox, la DLQ y los logs relevantes, sin introducir un framework de tracing.

### Resultado funcional

`X-Correlation-Id` se conserva cuando contiene de 1 a 64 caracteres ASCII permitidos (`A-Z`, `a-z`, `0-9`, `.`, `_`, `-`). Si falta o no es válido se reemplaza por un UUID. El valor se devuelve en la respuesta, viaja en Reactor Context y se usa al construir `OrderEvent`.

### Archivos modificados o creados

- `tacocloud-api/.../CorrelationIdWebFilter.java`: resolución, validación, response header, Reactor Context y logs HTTP.
- `tacocloud-api/.../OrderService.java`: usa la correlación reactiva para `ORDER_CREATED`.
- `tacocloud-api/.../OrderWorkflowService.java`: usa la correlación reactiva para cambios de estado y cancelación.
- `tacocloud-kitchen/.../rabbit/listener/OrderListener.java`: logs de consumo con MDC acotado y limpieza.
- `tacocloud/src/main/resources/application.yml` y `tacocloud-kitchen/src/main/resources/application.yml`: patrón con `correlationId`.
- Pruebas del filtro, servicios, outbox y listener: validan propagación y ausencia de contaminación.

### Trabajo solicitado

Propagar el ID de correlación de HTTP a eventos y logs reutilizando el contrato TC-27, el outbox TC-29 y la DLQ TC-30.

### Restricciones técnicas obligatorias

- Header exacto `X-Correlation-Id`.
- Reactor Context como fuente de propagación dentro de la cadena.
- MDC sólo alrededor de logs concretos y con restauración en `finally`.
- Sin derivar el ID desde `orderId` o `eventId`.
- Sin registrar bodies, payloads completos ni datos sensibles.

### Criterios de aceptación

- Header válido preservado; ausente o inválido reemplazado por UUID.
- El response header está presente también cuando la cadena termina en error.
- El mismo valor llega a `OrderEvent`, al evento persistido en outbox y a DLQ.
- Los logs HTTP y Rabbit contienen el valor correcto sin contaminar la siguiente operación.

### Pruebas mínimas

- Generación UUID, preservación, CR/LF, longitud máxima y respuesta de error.
- Visibilidad dentro de Reactor Context y limpieza entre dos peticiones.
- Propagación a eventos creados y de cambio de estado.
- Persistencia del mismo valor en outbox.
- Conservación en el header de DLQ.
- Logs y limpieza MDC en el consumidor.

## Cambios de código

- `CorrelationIdWebFilter`: único componente nuevo de producción; valida/genera el ID, escribe la respuesta, añade Reactor Context y emite logs seguros.
- `OrderService` y `OrderWorkflowService`: sustituyen UUIDs locales de correlación por el valor del contexto; mantienen un UUID server-side para flujos no HTTP.
- `OrderListener`: obtiene la correlación del `OrderEvent`, la usa sólo durante cada log y limpia/restaura MDC.
- Configuración YAML: incorpora `%X{correlationId}` al patrón sin reemplazar la configuración de logging existente.
- Outbox y DLQ: no requieren cambios de modelo; ya transportan el evento y su correlación originales.

¿Por qué MDC puede mentir en una cadena reactiva si se asume afinidad de hilo? MDC normalmente se basa en `ThreadLocal`, mientras Reactor puede cambiar de thread o reutilizar uno entre cadenas. Un valor dejado en el thread puede faltar en otro operador o aparecer en logs de otra petición. Reactor Context acompaña la suscripción, no el thread; por eso es la fuente de propagación y MDC sólo se abre de manera controlada al escribir cada log.

## Cambios que no se realizaron

TC-32:
métricas, health y observabilidad operacional.

TC-35:
OpenAPI/versionado de API.

No se añadió:
OpenTelemetry, tracing distribuido, nuevos módulos o persistencia de correlation IDs,
porque TC-31 no los requiere.

Tampoco se duplicó `correlationId` en `OutboxEvent`, no se añadieron tags métricos de alta cardinalidad y no se registraron bodies ni payloads completos.

## Relación entre requisitos e implementación

| Requisito | Implementación |
| --- | --- |
| Header de entrada | `CorrelationIdWebFilter` |
| Sin header | `UUID.randomUUID()` |
| Header válido | preservación exacta |
| Header malicioso | regex y máximo de 64; reemplazo por UUID |
| Response | `X-Correlation-Id` antes de continuar la cadena |
| Propagación reactiva | Reactor Context |
| Evento | `OrderEvent.correlationId` existente |
| Outbox | evento completo de TC-29 |
| DLQ | correlationId original de TC-30 |
| Logs | MDC controlado en filtro y listener Rabbit |
| Limpieza | restauración/eliminación en `finally` |
| Sin orderId | `eventId`, `orderId` y `correlationId` separados |
| Sin tags altos | no se añadieron métricas por ID |
| Sin bodies sensibles | logs limitados a método/ruta/status o evento/tipo |

## Resultado

La aplicación resuelve una correlación HTTP segura, la propaga mediante Reactor Context y conserva el mismo valor en eventos, outbox, DLQ y logs. Sólo se añadió una clase de producción y no se incorporaron dependencias ni abstracciones de tracing.
