# TC-26 — Cola de cocina, claim atómico y tiempo estimado

## Descripción del TC

### Resultado funcional

La cocina consulta una cola persistida de órdenes `CREATED`, ordenada FIFO, y reclama la siguiente mediante una única operación Mongo `findAndModify`. El claim cambia la orden a `ACCEPTED`, asigna estación y cocinero derivados del servidor, incrementa la versión y agrega la auditoría de TC-25 sin una ventana `find -> save`. La respuesta incluye un ETA determinista y sólo datos necesarios para preparar tacos.

### Trabajo solicitado

Se implementaron `GET /api/kitchen/queue` y `POST /api/kitchen/orders/claim`. La cola se filtra en Mongo por `CREATED`; el claim selecciona el primer documento por `placedAt ASC, _id ASC` y lo actualiza atómicamente. La aplicación de cocina consume esos endpoints y reutiliza el `PATCH /api/orders/{id}/status` de TC-25 para avanzar a `PREPARING` y `READY`.

### Restricciones técnicas obligatorias

- El claim utiliza `ReactiveMongoTemplate.findAndModify`; no usa repositorio `find` seguido de `save`.
- El query de claim contiene `status = CREATED` y orden FIFO estable.
- `cookId` procede de `Authentication.getName()` y `stationId` de `tacocloud.kitchen.station-id`.
- Sólo `ROLE_KITCHEN` accede a `/api/kitchen/**`.
- La transición `CREATED -> ACCEPTED` se valida mediante la matriz central de `OrderWorkflowService`.
- Estado, asignación, auditoría y versión se actualizan juntos.
- El DTO de cocina no contiene usuario, dirección, pago ni importes ajenos a preparación.
- ETA es determinista, configurable y representa minutos estimados hasta completar la orden; no es una promesa transaccional.
- No se agregaron `block()` ni `subscribe()` a servicios productivos.

## Cambios de código

### `TacoOrder.java`

Se agregaron los datos mínimos de asignación y dos índices Mongo:

```java
@CompoundIndex(name="order_kitchen_queue_idx",
    def="{'status':1,'placedAt':1,'_id':1}")

@Indexed(name="active_kitchen_station_unique",unique=true,sparse=true)
private String activeKitchenStationKey;

private String stationId;
private String cookId;
```

El índice compuesto respalda la consulta FIFO. La clave única dispersa constituye la garantía final frente a dos claims concurrentes de una misma estación. Sólo está presente mientras la orden se encuentra activa en cocina y se elimina al llegar a `READY` o al cancelarse antes del cutoff.

### `KitchenProperties.java` y `application.yml`

La estación y la fórmula están centralizadas bajo `tacocloud.kitchen`:

```yaml
tacocloud:
  kitchen:
    station-id: ${TACOCLOUD_KITCHEN_STATION_ID:station-01}
    eta:
      base-minutes: ${TACOCLOUD_KITCHEN_ETA_BASE:2}
      minutes-per-queued-order: ${TACOCLOUD_KITCHEN_ETA_PER_QUEUED_ORDER:3}
      minutes-per-item: ${TACOCLOUD_KITCHEN_ETA_PER_ITEM:2}
      minutes-per-complexity-point: ${TACOCLOUD_KITCHEN_ETA_PER_COMPLEXITY:1}
```

La fórmula implementada es:

```text
ETA = baseMinutes
    + queueAhead * minutesPerQueuedOrder
    + totalQuantity * minutesPerItem
    + totalIngredientUnits * minutesPerComplexityPoint
```

`totalQuantity` suma las cantidades de TC-14. `totalIngredientUnits` suma `cantidad × número de ingredientes` por línea como medida pequeña y reproducible de complejidad.

### `KitchenQueueService.java`

La cola consulta exclusivamente documentos elegibles:

```java
Query.query(Criteria.where("status").is(Status.CREATED))
    .with(Sort.by(
        Sort.Order.asc("placedAt"),
        Sort.Order.asc("_id")));
```

El claim reutiliza primero la validación central de TC-25 y ejecuta después el adaptador atómico:

```java
workflow.validateTransition(CREATED, ACCEPTED, authentication);

mongo.findAndModify(
    createdQueueQuery(),
    new Update()
        .set("status", ACCEPTED)
        .set("stationId", stationId)
        .set("cookId", authentication.getName())
        .set("activeKitchenStationKey", stationId)
        .push("statusHistory", audit)
        .inc("version", 1L),
    FindAndModifyOptions.options().returnNew(true),
    TacoOrder.class);
```

La matriz sigue perteneciendo al workflow; `KitchenQueueService` sólo proporciona la ejecución Mongo especializada que TC-26 necesita para hacer selección y cambio indivisibles.

### `OrderWorkflowService.java`

`validateTransition` expone la misma matriz a adaptadores especializados. El camino normal de transición también usa ese método. Cuando una orden pasa a `READY` o `CANCELLED`, elimina `activeKitchenStationKey`, permitiendo que la estación reclame el siguiente trabajo.

## Cambios que no se realizaron

- **TC-27:** no se creó contrato único/versionado de eventos.
- **TC-28:** no se modificó la selección de broker ni los POM para cambiar transporte.
- **TC-29:** no se implementó outbox ni claim de eventos.
- **TC-30:** no se añadieron retry, DLQ o deduplicación de consumidores.
- No se implementó shortest-job-first, prioridades ni múltiples clases de scheduler.
- No se reemplazó `@Version`; el claim atómico y optimistic locking resuelven problemas distintos y se conservan ambos.

FIFO puro es simple, predecible, auditable y evita starvation de órdenes antiguas, pero una orden grande puede provocar *head-of-line blocking* sobre muchas pequeñas. Shortest-job-first o colas ponderadas podrían mejorar throughput, a costa de romper el orden percibido, aumentar complejidad y potencialmente causar starvation. TC-26 conserva FIFO porque es la política solicitada.

## Resultado

TC-26 queda completo: la cola es FIFO y se filtra en Mongo; el claim se ejecuta mediante una única operación condicionada y está probado bajo concurrencia real; estación, cocinero, auditoría y versión quedan persistidos sin modificar ownership; el ETA es configurable y determinista; y cocina sólo recibe un contrato operativo seguro. La solución reutiliza el workflow de TC-25 y no adelanta los retos de eventos, broker, outbox o resiliencia del consumidor.
