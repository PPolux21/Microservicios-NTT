# TC-23 — Historial paginado y privado de órdenes

## Descripción del TC

### Resultado funcional

El usuario autenticado consulta únicamente su historial mediante `/api/users/me/orders`, paginado y ordenado por fecha descendente con desempate estable por ID. El detalle reutiliza los snapshots económicos de la orden y nunca expone el usuario persistido ni información de pago. La consulta global quedó separada en `/api/admin/orders` y protegida para `ADMIN`.

### Trabajo solicitado

Se reemplazó el listado global para usuarios por rutas `/me`, se añadió detalle con ownership, paginación estable, resúmenes seguros, acceso administrativo explícito y UI mínima de historial. Las acciones existentes también resuelven la orden a través de ownership antes de modificarla o cancelarla.

### Restricciones técnicas obligatorias

- La identidad procede de `Authentication`; el cliente no envía `userId` en rutas USER.
- Mongo filtra por `userId` y aplica `Pageable`; no se usa `findAll()` seguido de filtros en memoria.
- Orden: `placedAt DESC`, `id ASC`.
- Página fuera de rango: `200` con `items: []` y metadata real.
- Orden ajena e inexistente: ambas producen `404` para evitar enumeración.
- `User` es transitorio dentro de `TacoOrder`; sólo `userId` se persiste como referencia de ownership.
- No se recalculan precios históricos ni se introducen operaciones bloqueantes en servicios.

### Criterios de aceptación

- [x] USER sólo obtiene sus órdenes.
- [x] `/me` deriva la identidad de la autenticación.
- [x] El historial es paginado y consulta Mongo ya filtrado.
- [x] Las órdenes más recientes aparecen primero.
- [x] El desempate por ID es determinista.
- [x] El resumen contiene únicamente datos necesarios.
- [x] El detalle conserva cantidades y snapshots económicos.
- [x] El JSON no contiene `User`, contraseña, token completo, PAN ni CVV.
- [x] Una orden ajena se oculta mediante `404`.
- [x] El acceso global está separado y limitado a `ADMIN`.
- [x] La UI usa `/api/users/me/orders` sin enviar `userId`.
- [x] No se adelantaron TC-24 ni TC-25.

### Pruebas mínimas

`OrderHistoryMongoIntegrationTest` usa Mongo embebido real para verificar aislamiento A/B, fecha descendente, desempate por ID, dos páginas, página fuera de rango, detalle ajeno como `404` e índice de historial. `OrderHistoryControllerTest` verifica el contrato paginado y serialización sin campos sensibles. `SecurityConfigTest` comprueba anónimo `401`, USER permitido en `/me`, USER rechazado en `/api/admin/orders` y ADMIN permitido. La prueba Angular comprueba rutas `/me` y ausencia de `userId`.

## Cambios de código

### `TacoOrder.java`

La orden persiste sólo la referencia segura del propietario y define el índice de la consulta principal:

```java
@CompoundIndex(name="order_user_placed_id_idx",
    def="{'userId':1,'placedAt':-1,'_id':1}")
private String userId;

@Transient
private User user;
```

`setUser` conserva compatibilidad en memoria y copia el ID, evitando guardar el perfil, hash y roles dentro de cada orden.

### `OrderRepository.java`

Se añadieron consultas directamente acotadas por propietario:

```java
Flux<TacoOrder> findByUserId(String userId, Pageable pageable);
Mono<Long> countByUserId(String userId);
Mono<TacoOrder> findByIdAndUserId(String id, String userId);
```

Así el camino USER nunca obtiene todas las órdenes para filtrarlas después.

### `OrderService.java`

Centraliza identidad, ownership, paginación y orden estable:

```java
Sort sort = Sort.by(Sort.Direction.DESC,"placedAt")
    .and(Sort.by(Sort.Direction.ASC,"id"));
```

`findOwnOrder` consulta por `id + userId`; un resultado vacío se traduce a `ORDER_NOT_FOUND`. `findAccessibleOrder` conserva acceso ADMIN y aplica la misma protección a PUT, PATCH y DELETE. El listado administrativo acepta un filtro opcional `userId` sin alterar `/me`.

### `OrderHistoryController.java`

Expone contratos separados:

```java
@GetMapping("/api/users/me/orders")
@GetMapping("/api/users/me/orders/{orderId}")
@GetMapping("/api/admin/orders")
```

También aplica el límite compartido `tacocloud.search.max-page-size`.

### `OrderApiController.java`

Se eliminó el antiguo `GET /api/orders` global. Las acciones existentes ahora llaman `findAccessibleOrder` antes de guardar o cancelar, evitando una ruta alternativa para operar sobre órdenes ajenas.

### `ApiDtos.java` y `ApiMapper.java`

Se añadieron `OrderSummaryResponse` y `OrderHistoryPageResponse`. El resumen sólo incluye ID, fecha, estado, cantidad, total y moneda. El detalle reutiliza `OrderResponse`, que no contiene propietario ni pago.

### `SecurityConfig.java`

Las reglas distinguen explícitamente:

```java
/api/users/me/orders/** -> USER o ADMIN
/api/admin/orders/**    -> ADMIN
```

### UI

`RecentTacosService` consulta listado y detalle bajo `/me`; el componente muestra un historial sencillo y sus líneas almacenadas. No envía ni mantiene un `userId` como fuente de ownership.

### Pruebas

Las pruebas nuevas cubren Mongo real, seguridad, serialización y UI. Las pruebas existentes de acciones se actualizaron para validar la política `404` y la resolución centralizada de ownership.

## Relación entre requisitos e implementación

| Requisito | Implementación |
| --- | --- |
| Historial propio | `/api/users/me/orders` |
| Identidad segura | `OrderService.currentUser(Authentication)` |
| No userId cliente | contrato `/me` y UI |
| Paginación | `PageRequest` + consultas de `OrderRepository` |
| Más reciente primero | `placedAt DESC` |
| Orden estable | `id ASC` |
| Resumen seguro | `OrderSummaryResponse` |
| Detalle seguro | `OrderResponse` + `ApiMapper` |
| Sin token/User | DTO, mapper y `User @Transient` |
| Ownership detalle | `findByIdAndUserId` |
| No `findAll` + filter | consulta Mongo por `userId` |
| Página fuera de rango | `200`, lista vacía y metadata |
| ADMIN separado | `/api/admin/orders` |
| USER no accede global | `SecurityConfig` y eliminación de `GET /api/orders` |
| JSON seguro | `OrderHistoryControllerTest` |

La política elegida para orden ajena es `404`. Un `403` confirmaría que el ID existe y sólo falta permiso, facilitando enumeración. Usar el mismo `404` para inexistente y ajena reduce esa información observable.

## Resultado

TC-23 queda implementado con historial privado, estable y paginado, detalle basado en snapshots, ownership desde autenticación, acceso ADMIN explícito y respuestas sin datos sensibles. Las pruebas específicas API, Mongo, seguridad y UI demuestran los criterios sin incorporar recompra ni estados avanzados.

La ejecución completa del reactor también se intentó. Conserva fallos previos fuera de TC-23 en `RegistrationControllerTest.shouldReturnConflictForDuplicates` y en tres casos de `ApiExceptionHandlerTest`; ninguno de esos archivos fue modificado por este reto. Las regresiones seleccionadas de DTO/TC-08, pago/TC-12, órdenes/TC-14 y catálogo/TC-19 sí finalizaron correctamente.
