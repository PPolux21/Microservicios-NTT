# TC-22 — Calificaciones y ranking de tacos

## Descripción del TC

### Resultado funcional

Los usuarios autenticados pueden establecer una calificación de 1 a 5 para un taco publicado mediante PUT. Repetir la operación modifica su único voto sin incrementar el conteo. El catálogo expone un top público agregado con taco, promedio, cantidad y distribución, excluyendo tacos con menos votos que el mínimo configurado.

### Trabajo solicitado

- Aceptar un score 1–5 en `PUT /api/tacos/{id}/rating` sin aceptar identidad del cliente.
- Mantener un voto persistente por usuario+taco y actualizarlo con PUT.
- Rechazar tacos inexistentes o no publicados.
- Calcular promedio, conteo y distribución mediante una agregación eficiente.
- Publicar `GET /api/tacos/top?limit=10` con mínimo de votos configurable.
- Aplicar orden determinista por promedio, conteo e ID.
- Mostrar calificación y top mediante cambios mínimos en la UI.

### Restricciones técnicas obligatorias

- El propietario procede de `Authentication.getName()` y se traduce a `User.id` mediante `UserRepository`.
- No existe `userId` en el request ni se exponen votantes en el response.
- Mongo impone unicidad sobre `(userId,tacoId)`.
- El PUT usa una query conjunta por propietario+taco y nunca actualiza sólo por `tacoId`.
- Score se valida en backend con `@Min(1)` y `@Max(5)`.
- El promedio se produce con `BigDecimal`, escala 2 y `RoundingMode.HALF_UP`.
- El ranking se calcula con un único pipeline Mongo; no consulta ratings o tacos una vez por resultado.
- `minimumVotes` y el límite máximo se configuran en `application.yml`.
- No se añadieron `block()` o `subscribe()` a servicios backend.

### Criterios de aceptación

- [x] `TacoRating` persiste únicamente `userId`, `tacoId` y `score`.
- [x] El índice `rating_user_taco_unique` impide más de un voto por usuario+taco.
- [x] Dos PUT concurrentes y los reintentos secuenciales dejan un documento.
- [x] Un PUT posterior actualiza el score del voto existente.
- [x] Un usuario no modifica la calificación de otro.
- [x] Scores 0 y 6 producen HTTP 400 y no invocan persistencia.
- [x] Un taco inexistente produce `TACO_NOT_FOUND` y no crea rating.
- [x] Un taco no publicado produce `TACO_NOT_PUBLISHED` y no crea rating.
- [x] Sólo USER o ADMIN autenticado puede escribir; un anónimo recibe 401.
- [x] GET top permanece público como el resto del catálogo.
- [x] Promedio, conteo y distribución coinciden con los votos persistidos.
- [x] El promedio usa escala 2 y `HALF_UP`, incluyendo el caso 13/3 = 4.33.
- [x] El ranking excluye resultados bajo `min-votes: 3`.
- [x] El desempate usa promedio DESC, conteo DESC e ID ASC.
- [x] `limit` se aplica en Mongo y se valida entre 1 y 50.
- [x] El pipeline incorpora `$group`, `$lookup`, `$sort` y `$limit`, sin N+1.
- [x] La UI envía únicamente `{score}` mediante PUT y recarga el top agregado.
- [x] No se implementaron TC-23 ni TC-24.

### Pruebas mínimas

`TacoRatingMongoIntegrationTest` ejecuta Mongo embebido real y demuestra:

- upsert concurrente protegido por el índice único;
- reintento y actualización 2 → 5 con conteo igual a 1 y promedio 5.00;
- aislamiento de dos usuarios, conservando scores 4 y 5, conteo 2 y promedio 4.50;
- exclusión por mínimo de votos y por taco no publicado;
- promedio exacto 4.00 para scores 5, 4 y 3;
- redondeo 4.33 para scores 5, 4 y 4;
- distribución completa con ceros explícitos;
- desempate por conteo y luego por ID;
- aplicación de `limit` dentro del pipeline;
- presencia de una sola agregación con lookup, en lugar de N+1.

`TacoRatingControllerTest` comprueba el body seguro, score 0/6, límites 0/51, valor válido y ausencia de `userId`. `SecurityConfigTest` comprueba anónimo 401, USER permitido y top público. La prueba Angular verifica PUT con `{score}` y GET del top sin identidad del cliente.

## Cambios de código

### `TacoRating.java`

Define el documento mínimo y la garantía final de unicidad:

```java
@Document("tacoRatings")
@CompoundIndex(
    name="rating_user_taco_unique",
    def="{'userId': 1, 'tacoId': 1}",
    unique=true)
public class TacoRating {
  private String id;
  private final String userId;
  private final String tacoId;
  private final int score;
}
```

No incorpora objetos `User` o `Taco`, nombres de usuario, roles ni información de perfil.

### `Taco.java`

El modelo no disponía de una condición de publicación distinta del inventario. Se añadió un único campo server-owned y compatible con tacos existentes:

```java
@JsonProperty(access=JsonProperty.Access.READ_ONLY)
private boolean published = true;
```

No se reutilizó `Ingredient.available` ni stock, porque describen disponibilidad de ingredientes y no la publicación del producto.

### `TacoRatingRepository.java`

Concentra el pipeline de ranking. Primero cuenta cada score, luego agrupa por taco, aplica el mínimo, une una sola vez con la colección de tacos, excluye no publicados, ordena y limita:

```java
@Aggregation(pipeline={
  "{ '$group': ... }",
  "{ '$match': { 'voteCount': { '$gte': ?0 } } }",
  "{ '$lookup': { 'from': 'taco', ... } }",
  "{ '$sort': { 'averageForSort': -1, 'voteCount': -1, '_id': 1 } }",
  "{ '$limit': ?1 }"
})
Flux<RatingAggregate> findTopRatings(long minimumVotes,long limit);
```

El `$lookup` devuelve el taco en la misma agregación. No hay una consulta de ratings ni una consulta de tacos por cada elemento.

### `TacoRatingService.java`

El ownership repite el patrón validado en TC-21:

```java
return userRepo.findByUsername(authentication.getName())
    .switchIfEmpty(Mono.error(ApiException.notFound(
        "USER_NOT_FOUND","Authenticated user does not exist.")));
```

La escritura es un upsert atómico acotado por ambas referencias:

```java
Query query = Query.query(Criteria.where("userId").is(userId)
    .and("tacoId").is(tacoId));
return mongo.upsert(query,update,TacoRating.class)
    .onErrorResume(DuplicateKeyException.class,
        error -> mongo.updateFirst(
            query,Update.update("score",score),TacoRating.class))
    .then();
```

Si dos altas compiten, una puede encontrar el índice único; el segundo camino actualiza exactamente la misma pareja y mantiene la semántica idempotente de PUT.

El promedio de salida evita `double`:

```java
BigDecimal average = BigDecimal.valueOf(scoreTotal)
    .divide(BigDecimal.valueOf(voteCount),2,RoundingMode.HALF_UP);
```

La distribución se completa para las cinco puntuaciones, incluyendo valores con cero votos.

### `TacoRatingController.java`

Publica los dos contratos sin aceptar propietario:

```java
@PutMapping(path="/{id}/rating",consumes="application/json")
public Mono<Void> rate(String id,@Valid @RequestBody RatingRequest request,
    Authentication authentication)

@GetMapping("/top")
public Mono<List<TopTacoRatingResponse>> top(
    @RequestParam(defaultValue="10") int limit)
```

PUT responde 204. El controlador devuelve `INVALID_LIMIT` con 400 si el valor queda fuera de 1–50.

### `ApiDtos.java` y `ApiMapper.java`

El DTO de entrada sólo declara score:

```java
public static class RatingRequest {
  @Min(1) @Max(5)
  private int score;
}
```

La respuesta reutiliza `TacoCatalogResponse` de TC-19 y añade únicamente `average`, `count` y `distribution`. El mapper no expone documentos individuales ni IDs de votantes.

### `SecurityConfig.java`

Se añadió una única regla de escritura antes del deny-by-default:

```java
.antMatchers(HttpMethod.PUT,"/api/tacos/*/rating")
.hasAnyRole("USER","ADMIN")
```

GET `/api/tacos/top` conserva la lectura pública ya establecida para `/api/tacos/**`.

### `application.yml`

Centraliza los parámetros comerciales y de protección de consulta:

```yaml
tacocloud:
  rating:
    min-votes: 3
    max-top-limit: 50
```

### `RecentTacosService.ts`, `recents.component.ts` y `recents.component.html`

La UI vuelve a usar PUT cuando cambia el score:

```typescript
rateTaco(tacoId: string, score: number) {
  return this.apiService.put(
      '/api/tacos/' + encodeURIComponent(tacoId) + '/rating',
      {score: score});
}
```

El componente presenta botones 1–5, vuelve a consultar `/api/tacos/top?limit=10` después de votar y muestra promedio y cantidad. No mantiene el ranking como fuente de verdad local.

### `TacoRatingMongoIntegrationTest.java`, `TacoRatingControllerTest.java`, `SecurityConfigTest.java` y `app.component.spec.ts`

Las pruebas separan persistencia/agregación real, contrato HTTP, autorización y cliente. La concurrencia usa dos publishers simultáneos y valida tanto el único documento como `IndexInfo.isUnique()`.

## Cambios que no se realizaron

TC-23:
historial privado de órdenes.

TC-24:
reordenar compras anteriores.

No se añadió un endpoint de votantes, un rol nuevo, un DTO con `userId`, cinco campos separados para distribución ni una consulta por cada taco.

No se implementó puntuación bayesiana. Para este reto el mínimo configurable de votos resuelve de forma suficiente el problema de muestras pequeñas sin incorporar una fórmula y configuración adicionales.

### ¿Ordenar por promedio puro es justo?

No siempre. Un taco con promedio 5.0 y un solo voto tiene menos evidencia que otro con 4.9 y cien votos. TC-22 exige `minimumVotes`, por lo que el primer taco no participa hasta reunir una muestra mínima. Una puntuación bayesiana podría combinar promedio del taco, cantidad y promedio global, pero supone una política más compleja que no es necesaria para cumplir este reto.

## Resultado

TC-22 queda implementado con un voto único y privado por usuario+taco, actualización atómica, validación 1–5, control de publicación, agregación Mongo sin N+1, promedio determinista, distribución, mínimo configurable y ranking estable. La UI permite volver a calificar mediante PUT y muestra los agregados públicos sin enviar identidad.

La validación final ejecutó 8 pruebas focalizadas de TC-22, 19 pruebas API combinadas de TC-19/TC-21/TC-22, 5 pruebas de seguridad y 7 pruebas Angular sin fallos. El empaquetado completo de los 16 módulos también terminó con `BUILD SUCCESS`.
